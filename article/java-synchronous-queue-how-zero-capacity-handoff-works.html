Java SynchronousQueue: How Zero-Capacity Handoff Works

Java’s SynchronousQueue is a specialized blocking queue that operates with an internal capacity of zero, meaning it cannot hold any elements on its own. Instead of acting as a buffer that stores data, it functions as a thread-to-thread rendezvous point where an inserting thread must pair directly with a removing thread to exchange a task or value. This article explains the internal mechanics of SynchronousQueue, covering how it utilizes dual data structures, Compare-And-Swap (CAS) operations, and thread parking to facilitate immediate task handoffs without traditional queue storage.

The Concept of Zero Capacity

In a standard BlockingQueue, such as ArrayBlockingQueue or LinkedBlockingQueue, an internal data structure (an array or a linked list) stores elements until consumer threads retrieve them. In contrast, SynchronousQueue returns true for isEmpty(), has a size() of 0, and returns null on peek().

Because there is no storage buffer, a thread attempting to insert an item using put() blocks until another thread executes take(). Conversely, a thread executing take() blocks until a producer calls put(). The queue acts as a direct handoff pipe, making it ideal for systems requiring strict backpressure, such as the worker threads managed by Executors.newCachedThreadPool().

The Dual Data Structure Engine

Under the hood, SynchronousQueue coordinates handoffs using an abstraction known as a "dual data structure." Rather than storing tasks, the queue stores representations of waiting threads and their states.

The queue operates in one of two modes based on fairness:

  1. Fair Mode (TransferQueue): Uses a FIFO (First-In-First-Out) dual queue. Waiting threads are matched in the order they arrived.
  2. Non-Fair Mode (TransferStack): Uses a LIFO (Last-In-First-Out) dual stack. The most recently blocked thread is paired first, which optimizes CPU cache locality and throughput at the expense of potential thread starvation.

Both implementations track nodes that represent one of two types of operations:

  • Data Node (Producer): A node created by a thread waiting to supply an item via put() or offer().
  • Request Node (Consumer): A node created by a thread waiting to receive an item via take() or poll().

The Handoff Lifecycle

When a thread interacts with the SynchronousQueue, it executes the following steps:

  1. State Evaluation: The arriving thread inspects the head or top of the transfer structure.
  2. Matching (Complementary Modes): If the structure contains nodes of the opposite mode (for example, a producer arrives when a consumer node is waiting, or vice versa), a rendezvous is possible. The arriving thread pairs with the waiting node, directly transfers the item reference, and attempts to fulfill the transaction using atomic Compare-And-Swap (CAS) instructions. Once successful, the arriving thread wakes (unparks) the waiting thread via LockSupport.unpark(), and both threads continue execution.
  3. Queueing (Same Mode or Empty): If the structure is empty, or if it already contains nodes of the same mode (for example, a producer arrives while only other producers are waiting), a handoff cannot happen immediately. The thread constructs a node representing itself, links it to the stack or queue using CAS, and parks itself using LockSupport.park(). It remains suspended until a complementary thread arrives to complete the exchange.

Direct Reference Transfer

The zero-capacity handoff is achieved because the task reference passes directly between thread call stacks. When the matching occurs, the item is transferred directly via an internal field on the transfer node rather than being placed into a shared intermediate collection.

This lock-free, CAS-driven architecture avoids the overhead of coarse-grained locking mechanisms, minimizes cache invalidation between CPU cores, and ensures that no task can be accepted into the system without an active consumer guaranteed to receive it immediately.
