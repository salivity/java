How Java Exchanger Coordinates Object Swaps

Java's Exchanger<V> class, located in the java.util.concurrent package, provides a synchronization point where exactly two threads can pair up and atomically swap objects of type V. Acting as a bidirectional rendezvous mechanism, it blocks the first arriving thread until a second thread arrives with its corresponding object, swaps their references, and allows both threads to proceed with each other's data. This article explains the internal mechanics, memory visibility guarantees, and practical usage of the Exchanger concurrency utility.

The Rendezvous Mechanism

The fundamental operation of an Exchanger revolves around the overloaded exchange() method:

  • exchange(V x): Waits indefinitely for another thread to arrive unless interrupted.
  • exchange(V x, long timeout, TimeUnit unit): Waits up to the specified duration before throwing a TimeoutException.

When Thread A invokes exchange(itemA), the Exchanger checks if another thread is already waiting. If the exchange point is empty, Thread A places itemA into an internal slot and parks (suspends execution).

When Thread B subsequently calls exchange(itemB), it detects Thread A's presence, reads itemA, overwrites the slot with itemB, and unparks Thread A. Thread B receives itemA, Thread A awakens to receive itemB, and the exchange completes symmetrically.

import java.util.concurrent.Exchanger;

public class ExchangerDemo {
    public static void main(String[] args) {
        Exchanger<String> exchanger = new Exchanger<>();

        new Thread(() -> {
            try {
                String myData = "Buffer from Producer";
                String receivedData = exchanger.exchange(myData);
                System.out.println("Thread 1 received: " + receivedData);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }).start();

        new Thread(() -> {
            try {
                String myData = "Empty Buffer from Consumer";
                String receivedData = exchanger.exchange(myData);
                System.out.println("Thread 2 received: " + receivedData);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        }).start();
    }
}

Memory Visibility Guarantees

The Exchanger enforces a formal happens-before relationship as defined by the Java Memory Model (JMM):

  1. Prior Actions Visible: Any action taken by a thread prior to calling exchange() happens-before the return of that exchange() call in the receiving thread.
  2. Safe Publication: If Thread A modifies fields within an object before passing it into exchange(), Thread B is guaranteed to see those updates without requiring additional external synchronization.

Internally, this is achieved using volatile reads/writes and atomic compare-and-swap operations through VarHandle or Unsafe, ensuring memory fences flush CPU caches appropriately.

Internal Architecture: Single-Slot vs. Arena

Under the hood, Exchanger avoids global synchronization bottlenecks by dynamically scaling its internal structure:

  • Single-Slot Exchange: In low-contention scenarios, threads interact over a single shared slot (volatile Node slot). The first thread parks on this node until the second thread updates it.
  • Arena-Based Multi-Slot Exchange: If multiple pairs of threads use the same Exchanger concurrently, a single slot suffers severe cache contention and false sharing. When contention is detected, the implementation switches to an Arena array. Threads hash to different slots within the array, allowing multiple independent pairs to exchange objects simultaneously without serializing execution across a single memory address.

Interruption and Timeout Handling

If a waiting thread is interrupted while parked in exchange(), it aborts the operation, clears its presence from the slot, and throws an InterruptedException. Similarly, if a timeout expires, the thread cleans up its slot state before throwing a TimeoutException. This state cleanup ensures that a late-arriving thread does not encounter stale references or deadlock waiting for a departed partner.
