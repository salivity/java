How Monitorenter Implements Java Synchronization

This article provides an in-depth look at how the Java Virtual Machine (JVM) uses the monitorenter bytecode instruction to enforce thread synchronization. You will learn how Java source-level synchronized blocks are translated into low-level bytecode, how the JVM manages object monitors and lock counters, the role of reentrancy, and how the runtime guarantees lock release even in the event of unexpected runtime exceptions.

Bytecode Translation of Synchronized Blocks

When the Java compiler (javac) encounters a synchronized(lock) statement, it does not rely on method-level modifiers. Instead, it explicitly wraps the block's instructions between paired monitorenter and monitorexit bytecode instructions.

The monitorenter instruction requires a reference to an object on top of the operand stack. Once executed, it attempts to acquire ownership of the monitor associated with that referenced object.

aload_1             // Push lock object reference onto the stack
monitorenter        // Acquire the monitor for the object
// ... synchronized block body ...
aload_1             // Push lock object reference
monitorexit         // Release the monitor

To guarantee that the monitor is released even if an exception occurs inside the block, the compiler automatically generates an exception table entry that routes any thrown exception to a cleanup block containing a second monitorexit instruction before re-throwing the exception.

The Object Monitor and Lock State

In the HotSpot JVM, every object has an object header that includes a "Mark Word." This Mark Word stores metadata about the object, including its hash code, garbage collection age, and synchronization state.

When a thread attempts to acquire an object's monitor via monitorenter, the JVM checks the status of the monitor associated with the object:

  1. Unassigned Monitor (Counter is 0): If the monitor has no owner, the calling thread successfully takes ownership. The monitor's reference is assigned to the current thread, and its entry count is set to 1.
  2. Reentrant Lock Acquisition: If the calling thread already owns the monitor, the JVM permits re-entry. It increments the monitor's entry count by 1 and continues execution without blocking.
  3. Contended Monitor: If another thread holds the monitor, the executing thread cannot proceed. It is placed into a blocked state and added to the monitor's wait list (an entry queue) until the owning thread releases the monitor and the entry count resets to 0.

Monitor Escalation

The JVM optimizes monitorenter execution through lock escalation:

  • Biased Locking / Lightweight Locking: In low-contention scenarios, HotSpot attempts to avoid costly OS-level thread synchronization. It uses atomic compare-and-swap (CAS) operations to write the thread ID directly into the object's Mark Word.
  • Inflation to Heavyweight Monitor: When multiple threads actively contend for the same lock, the JVM inflates the lock into a full ObjectMonitor structure (managed by the operating system's native mutexes and condition variables). At this stage, monitorenter interacts directly with OS primitives to park and unpark threads.

Reentrancy and the Exit Counter

Reentrancy is fundamental to how monitorenter works. Because each successful monitorenter invocation increments an internal recursion counter, a thread can enter nested synchronized blocks on the same object without deadlocking itself.

Full release of the lock occurs only when a corresponding number of monitorexit instructions have run. Each monitorexit decrements the counter; once the counter reaches 0, the current thread relinquishes ownership, allowing waiting threads to contend for the monitor.
