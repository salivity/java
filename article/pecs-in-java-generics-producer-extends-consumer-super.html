PECS in Java Generics: Producer Extends Consumer Super

The PECS principle—short for "Producer Extends, Consumer Super"—is a design guideline in Java generics that dictates whether to use ? extends T or ? super T wildcards. Coined by Joshua Bloch, PECS resolves the limitations of Java's invariant generics by enabling safe covariance and contravariance. This article explains how the principle works, why wildcards are necessary for flexible APIs, and how to determine whether a generic type acts as a producer or a consumer.

The Problem: Invariance in Java Generics

By default, generic types in Java are invariant. Even though Integer is a subtype of Number, a List<Integer> is not a subtype of List<Number>. Passing a List<Integer> to a method expecting List<Number> results in a compiler error. While this restriction prevents runtime type-safety violations, it makes APIs rigid. Bounded wildcards provide the necessary flexibility, and PECS is the mental model used to implement them correctly.

Producer Extends (? extends T)

Use the ? extends T wildcard when a generic structure acts as a producer—meaning your code reads data out of it.

When you declare a parameter as List<? extends Number>, you are telling the compiler that the list contains objects of type Number or some unknown subclass of Number. Because every element in the list is guaranteed to be at least a Number, you can safely read items:

public double sumOfList(List<? extends Number> list) {
    double sum = 0.0;
    for (Number n : list) {
        sum += n.doubleValue(); // Safe to read as Number
    }
    return sum;
}

Because the exact concrete type is unknown (it could be a list of Integer, Double, etc.), the compiler prohibits adding new elements to a producer, except for null.

Consumer Super (? super T)

Use the ? super T wildcard when a generic structure acts as a consumer—meaning your code writes data into it.

When you declare a parameter as List<? super Integer>, the list holds an unknown type that is an Integer or a superclass of Integer (such as Number or Object). Because the underlying list can hold an Integer, it is always type-safe to write Integer instances into it:

public void addNumbers(List<? super Integer> list) {
    for (int i = 1; i <= 5; i++) {
        list.add(i); // Safe to write Integer
    }
}

Conversely, reading from a consumer collection only yields elements typed as Object, because there is no way to know which specific superclass is backing the list.

PECS in Action: Collections.copy()

The standard Java library demonstrates PECS in java.util.Collections.copy:

public static <T> void copy(List<? super T> dest, List<? extends T> src) {
    for (int i = 0; i < src.size(); i++) {
        dest.set(i, src.get(i));
    }
}

In this method:

  • src is the producer: it produces elements via get(), so it uses ? extends T.
  • dest is the consumer: it consumes elements via set(), so it uses ? super T.

When Not to Use Wildcards

If a parameter needs to be both read from and written to within the same method, PECS does not apply. In this case, bounded wildcards cannot be used, and you must use an exact type parameter (T).
