Exhaustive Switch with Sealed Types in Java

Exhaustive switch evaluation in Java allows developers to process sealed classes and interfaces without relying on a defensive default clause. When a switch construct evaluates a sealed hierarchy, the Java compiler uses pattern matching to verify that every permitted subclass is explicitly handled. If a developer omits a subtype or later adds a new implementation to the sealed hierarchy, the compiler emits an error, guaranteeing complete type safety at compile time.

Understanding Sealed Types

Sealed classes and interfaces, introduced permanently in Java 17, restrict which other classes or interfaces may extend or implement them. By explicitly defining allowed implementations via the permits keyword, the developer creates a closed, finite domain of types:

public sealed interface Shape permits Circle, Rectangle, Square {}

public final class Circle implements Shape { /* ... */ }
public final class Rectangle implements Shape { /* ... */ }
public final class Square implements Shape { /* ... */ }

Because the compiler knows every possible implementation of Shape, this boundary sets the foundation for exhaustive evaluation in switch constructs.

How the Compiler Evaluates Exhaustiveness

Prior to pattern matching for switch, switch expressions required either an exhaustive set of enum constants or a mandatory default clause to catch unhandled values. When switching over a sealed type, the compiler verifies that all direct permitted subtypes are matched by case labels.

public double calculateArea(Shape shape) {
    return switch (shape) {
        case Circle c    -> Math.PI * c.radius() * c.radius();
        case Rectangle r -> r.width() * r.height();
        case Square s    -> s.side() * s.side();
    };
}

In this switch expression, all permitted implementations of Shape are accounted for. The compiler validates the coverage by cross-referencing the case types against the permits declaration:

  1. Full Coverage: Every direct subtype (Circle, Rectangle, Square) has a corresponding pattern label.
  2. No Default Clause Required: Because every possible case is represented, omitting default: is legal and preferred.
  3. Compile-Time Error on Missing Cases: If Square is removed from the switch expression, compilation fails with an error stating that the switch expression does not cover all possible input values.

Nuances Across the Hierarchy

The exhaustiveness algorithm adapts depending on the modifier applied to the permitted subtypes (final, sealed, or non-sealed):

  • Final Subclasses: A final subclass terminates that branch of the hierarchy. Matching the final class satisfies that portion of the domain.
  • Sealed Subclasses: If a permitted subclass is also sealed, the switch can achieve exhaustiveness either by matching that subclass directly or by matching all of its own permitted descendants.
  • Non-Sealed Subclasses: If a subtype is marked non-sealed, it opens that branch to an infinite number of unknown implementations. To maintain exhaustiveness, the switch must include a case for the non-sealed type itself (or a broad fallback like an unconditional pattern), rather than attempting to match its arbitrary children.

Advantages Over the Default Clause

In traditional switch logic, unhandled states are directed to a default label, often throwing an IllegalArgumentException or IllegalStateException. While this prevents silent runtime errors, it defers detection until execution time.

Exhaustive switch evaluation shifts this detection entirely to compile time. If a new subclass—such as Triangle—is added to the Shape interface's permits clause, every switch expression operating on Shape across the entire codebase immediately breaks compilation. Developers are forced to implement logic for Triangle before the application can be built, preventing missing-branch bugs during maintenance and refactoring.
