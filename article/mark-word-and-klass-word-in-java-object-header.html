Mark Word and Klass Word in Java Object Header

Every Java object created in memory on the HotSpot Java Virtual Machine (JVM) contains an object header preceding its instance data. This article explores the internal architecture of that header, focusing specifically on its two primary components: the Mark Word and the Klass Word. You will learn what data these structures store, how they handle runtime operations such as synchronization and garbage collection, and how the JVM uses them to manage object metadata efficiently.

The Java Object Memory Layout

In the HotSpot JVM, an object stored in the heap consists of three main segments:

  1. Object Header: Metadata used by the JVM to manage the object.
  2. Instance Data: The actual field data declared in the class and its superclasses.
  3. Padding: Optional alignment bytes added so that the total object size is a multiple of 8 bytes.

For regular objects, the header consists of the Mark Word and the Klass Word. For array objects, an additional 4-byte field is appended to store the array length.

What Is the Mark Word?

The Mark Word is a multi-use data structure that stores dynamic runtime information about an object. Its size matches the native pointer size of the host architecture: 32 bits on a 32-bit JVM and 64 bits on a 64-bit JVM.

Because memory overhead must be minimized, the JVM dynamically repurposes the bits inside the Mark Word depending on the object's current state. The final 2 or 3 bits act as a tag indicating which state the object is in.

Data Stored in the Mark Word

Depending on the state tag, the Mark Word can store:

  • Identity Hash Code: The default hash code generated by System.identityHashCode(obj).
  • GC Age: A 4-bit field recording how many minor garbage collection cycles the object has survived (used to determine promotion from the young generation to the old generation, capping at a maximum value of 15).
  • Locking States and Synchronization Pointers: Information tracking whether an object is locked, including:
    • Unlocked: Stores the identity hash code, GC age, and biased lock flags.
    • Biased Lock: Contains the thread ID to which the lock is currently biased.
    • Lightweight Lock: Contains a direct pointer to the lock record on the executing thread's stack frame.
    • Heavyweight Lock: Contains a pointer to an ObjectMonitor structure allocated in native memory.
    • Marked for GC: Tagged by the garbage collector during tracing and compaction.

What Is the Klass Word?

The Klass Word (often referred to as the Klass Pointer) is a direct metadata reference pointing to the instance's class metadata representation in native memory (Metaspace).

While the Mark Word tracks the object's dynamic lifecycle status, the Klass Word identifies what the object actually is.

Function and Size of the Klass Word

  • Type Resolution: When a method is invoked dynamically, the JVM uses the Klass Word to locate the Klass structure in Metaspace. This structure contains the virtual method table (vtable), static variables, and type definitions required for dynamic dispatch, type checks, and operations like instanceof or casting.
  • Size: On a 32-bit architecture, the Klass Word is 32 bits (4 bytes). On a 64-bit architecture, it is natively 64 bits (8 bytes).
  • Compressed Class Pointers: On 64-bit JVMs, the flag -XX:+UseCompressedClassPointers (enabled by default when Compressed OOPs are active) reduces the Klass Word from 8 bytes to 4 bytes by addressing 32-bit shifts within a base offset, significantly reducing memory consumption.

Mark Word vs. Klass Word: Key Differences

Feature Mark Word Klass Word
Primary Role Tracks runtime object state (locks, GC, hashing) Points to class metadata in Metaspace
Data Nature Dynamic (changes values and layouts at runtime) Static (remains constant throughout object lifecycle)
Native 64-bit Size 8 bytes 8 bytes (or 4 bytes with Compressed Class Pointers)
Target Consumer Execution engine, GC, thread synchronization JVM class loader, type system, dynamic dispatcher

Together, the Mark Word and the Klass Word provide the JVM with all the low-level metadata required to handle synchronization, memory reclamation, and polymorphic method execution without adding overhead to the object's explicit instance fields.
