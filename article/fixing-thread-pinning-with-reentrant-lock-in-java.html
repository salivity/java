Fixing Thread Pinning with ReentrantLock in Java

Migrating legacy Java applications to virtual threads often exposes severe scalability bottlenecks caused by thread pinning. Thread pinning occurs when a virtual thread cannot be unmounted from its underlying carrier thread during a blocking operation because it is executing inside a synchronized block or method. Refactoring legacy synchronized code to use java.util.concurrent.locks.ReentrantLock eliminates this issue by utilizing virtual-thread-aware locking primitives, allowing carrier threads to remain free to execute other workloads.

Understanding Thread Pinning

Project Loom introduced virtual threads to Java to provide high-throughput, lightweight concurrency. Under normal circumstances, when a virtual thread encounters a blocking operation—such as socket I/O or waiting on a concurrent primitive—it unmounts from its underlying platform thread (the carrier thread). The carrier thread then returns to the ForkJoinPool to execute other virtual threads.

However, in Java’s current implementation, a virtual thread cannot unmount if it is executing inside a synchronized block or method. When a blocking call occurs inside synchronized, the virtual thread is "pinned" to its carrier thread. If many virtual threads become pinned simultaneously, the carrier pool quickly starves, degrading throughput down to—or worse than—traditional platform thread levels.

Why ReentrantLock Avoids Pinning

ReentrantLock is implemented in pure Java on top of AbstractQueuedSynchronizer (AQS) and relies on LockSupport.park() and LockSupport.unpark() for thread suspension.

The Java runtime has updated LockSupport to be fully aware of virtual threads. When a virtual thread calls LockSupport.park()—which happens internally when waiting to acquire a contested ReentrantLock or waiting on a Condition—the runtime intercepts the call and unmounts the virtual thread.

Similarly, if a virtual thread acquires a ReentrantLock and subsequently performs a blocking I/O operation inside the critical section, the lock metadata does not bind the execution context to the native carrier thread. Because the monitor is managed in Java user space rather than by the JVM's internal object monitor infrastructure, the JVM can safely unmount the virtual thread from its carrier thread and resume it later on any available carrier thread.

Refactoring Synchronized to ReentrantLock

Refactoring legacy code requires replacing Java's intrinsic locks with explicit ReentrantLock instances while preserving identical reentrancy semantics.

Consider a legacy synchronized block:

public class LegacyAccountService {
    private final Object lock = new Object();
    private double balance;

    public void debit(double amount) {
        synchronized (lock) {
            // Blocking operation (e.g., database check, remote audit call)
            executeBlockingAudit();
            balance -= amount;
        }
    }
}

In the synchronized example, if executeBlockingAudit() performs blocking network I/O, the virtual thread running debit() pins its carrier thread.

Refactoring to ReentrantLock resolves the issue:

import java.util.concurrent.locks.ReentrantLock;

public class ModernAccountService {
    private final ReentrantLock lock = new ReentrantLock();
    private double balance;

    public void debit(double amount) {
        lock.lock();
        try {
            // Blocking operation unmounts cleanly without pinning
            executeBlockingAudit();
            balance -= amount;
        } finally {
            lock.unlock();
        }
    }
}

Critical Refactoring Considerations

  1. Mandatory Try-Finally Blocks: Unlike synchronized, which automatically releases locks upon exiting the block or throwing an exception, ReentrantLock requires an explicit unlock() invocation. Always place lock.unlock() inside a finally block immediately following the acquisition to prevent lock leaks.
  2. Reentrancy Preservation: ReentrantLock matches the reentrant behavior of synchronized. A thread holding the lock can re-acquire it without deadlocking, making it a safe direct replacement for recursive or nested locking patterns.
  3. Condition Variables: If the legacy code relies on Object.wait(), Object.notify(), or Object.notifyAll(), these must be replaced with java.util.concurrent.locks.Condition methods (await(), signal(), and signalAll()), which also unmount virtual threads safely.
