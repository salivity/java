Double-Checked Locking with Volatile in Java

The double-checked locking pattern is a software design pattern used to reduce synchronization overhead when implementing lazy initialization in multithreaded environments. While early implementations in Java suffered from subtle concurrency bugs due to compiler optimizations and processor memory models, the introduction of the enhanced volatile keyword in Java 5 made the pattern fully thread-safe. This article explains the mechanics of double-checked locking, the memory visibility problem that initially broke it, and how volatile field access resolves the issue.

The Purpose of Double-Checked Locking

In multithreaded applications, lazily initializing a heavy resource often requires synchronization to ensure that only one instance is created. Synchronizing the entire accessor method creates unnecessary overhead:

public synchronized Resource getInstance() {
    if (instance == null) {
        instance = new Resource();
    }
    return instance;
}

Once the instance is initialized, every subsequent call still pays the performance penalty of acquiring and releasing a lock. Double-checked locking solves this by checking if the instance is initialized before acquiring the lock, and checking again after acquiring the lock.

The Failure of the Classic Implementation

Before Java 5, the following implementation was considered standard, but it contained a critical flaw:

// Broken implementation prior to Java 5
public class ResourceFactory {
    private static Resource instance;

    public static Resource getInstance() {
        if (instance == null) { // First check (no lock)
            synchronized (ResourceFactory.class) {
                if (instance == null) { // Second check (with lock)
                    instance = new Resource();
                }
            }
        }
        return instance;
    }
}

The issue stems from instruction reordering performed by compilers and CPUs to optimize execution. The operation instance = new Resource() is not atomic; it consists of three distinct steps:

  1. Allocate memory for the Resource object.
  2. Execute the Resource constructor to initialize fields.
  3. Assign the memory address to the instance reference.

Without explicit memory barriers, the Java Virtual Machine (JVM) may reorder steps 2 and 3. If reordered, the instance reference becomes non-null before the constructor finishes executing.

If Thread A executes step 1 and step 3, and is preempted before step 2, Thread B can perform the first check (instance == null), find it to be false, and immediately return instance. Thread B then attempts to use an incompletely initialized object, leading to erratic runtime exceptions or corrupted state.

How volatile Fixes the Pattern

Under the Java Memory Model (JSR-133) introduced in Java 5, the semantics of the volatile keyword were extended to prevent these reordering issues.

Declaring a field as volatile provides two main guarantees:

  1. Visibility: Writes to a volatile variable are immediately flushed to main memory, and reads are always drawn from main memory rather than local processor caches.
  2. Instruction Ordering (Happens-Before Relationship): The JVM inserts memory barriers around reads and writes of volatile variables. Specifically, it establishes that all actions occurring before a write to a volatile variable happen-before any subsequent read of that same volatile variable.

When instance is marked as volatile, the compiler and CPU are strictly prohibited from reordering the constructor execution past the assignment write to the instance variable. The memory write to instance acts as a store barrier, ensuring the object is fully constructed in memory before its reference is published.

The Correct Implementation

Below is the standard, thread-safe implementation of double-checked locking using a volatile field:

public class ResourceFactory {
    // volatile ensures memory visibility and prevents instruction reordering
    private static volatile Resource instance;

    public static Resource getInstance() {
        // Local variable improves performance by reducing volatile reads
        Resource result = instance; 
        
        if (result == null) { // First check
            synchronized (ResourceFactory.class) {
                result = instance;
                if (result == null) { // Second check
                    instance = result = new Resource();
                }
            }
        }
        return result;
    }
}

Execution Flow Breakdown

  1. Initial Read: The method reads the volatile instance into a local variable result. Using a local variable ensures that once the instance is initialized, the volatile field is only read once rather than multiple times, providing a minor performance improvement.
  2. First Check: If result is not null, the object is already constructed, and it is returned immediately without entering the synchronized block.
  3. Lock Acquisition: If result is null, the thread acquires the class lock.
  4. Second Check: Inside the lock, instance is checked again. This protects against race conditions where another thread initialized the object between the first check and lock acquisition.
  5. Safe Publication: If the second check passes, new Resource() is executed. Because instance is volatile, the initialization of the object is guaranteed to complete before the reference is made accessible to other threads reading the volatile variable outside the lock.
