Java Write Barriers and Garbage Collection Explained

In Java, write barriers are low-level code snippets inserted by the Just-In-Time (JIT) compiler that execute whenever an application thread modifies an object reference. This article explores how write barriers assist the Java Garbage Collector (GC) during runtime pointer updates, explaining their role in maintaining generational tracking, facilitating concurrent marking, and preventing race conditions between application threads and garbage collection phases.

What Is a Write Barrier?

A write barrier is not a memory barrier in the hardware synchronization sense, but rather a small hook of instructions intercepted during reference assignments (such as object.field = newReference). When the runtime mutates a pointer in the Java heap, the write barrier informs the garbage collection subsystem about the modification. This mechanism enables GC algorithms to accurately track object graphs without constantly scanning the entire heap.

Tracking Inter-Generational References (Card Marking)

In generational garbage collectors like Serial, Parallel, and traditional CMS, the heap is split into Young and Old generations. Most objects die young, making minor garbage collections frequent and focused strictly on the Young generation. However, an object in the Old generation might hold a reference to an object in the Young generation.

Without a write barrier, a minor GC would have to scan the entire Old generation to ensure that young objects referenced by old objects are not prematurely discarded. The write barrier solves this through card marking:

  1. The heap is divided into fixed-size memory blocks called "cards" (typically 512 bytes).
  2. A corresponding byte array, known as the card table, tracks the status of each card.
  3. When a thread executes a reference write (oldObj.field = youngObj), the JIT-generated post-write barrier marks the corresponding entry in the card table as "dirty."
  4. During a minor collection, the GC only inspects the dirty cards in the Old generation instead of the entire generation, significantly reducing pause times.

Supporting Concurrent Collectors (G1 and Shenandoah)

Modern garbage collectors run marking and evacuation phases concurrently with application threads. When application threads alter object graphs while the GC is actively tracing them, inconsistencies can occur—specifically, the "lost object" problem, where a live object becomes invisible to the collector. Write barriers prevent these anomalies.

Pre-Write Barriers and Snapshot-At-The-Beginning (SATB)

The Garbage-First (G1) collector employs a pre-write barrier to implement SATB marking:

  • Before a field is overwritten (x.f = y), the pre-write barrier logs the previous value of x.f into a thread-local buffer.
  • The GC treats the state of the object graph at the start of marking as a snapshot. Preserving overwritten references ensures that reachable objects are not missed if an application thread moves a pointer while the collector is traversing the graph.

Evacuation and Forwarding Pointers

Collectors like Shenandoah utilize write barriers during concurrent evacuation:

  • When an object is copied from one region to another, its location changes.
  • If an application thread writes to an object while it is being moved, the write barrier checks whether the object resides in a collection set.
  • If so, the barrier updates the reference to the new forwarded copy (or performs the copy itself) before allowing the write operation to complete, preventing data corruption.

Performance Impact

Write barriers introduce a slight instruction overhead to reference modification operations. However, this cost is minimal—often consisting of just a few assembly instructions, such as bit shifts and byte stores. By spending a few cycles during runtime pointer updates, the JVM eliminates the need for exhaustive heap traversals and enables concurrent collection, resulting in drastically lower latency and predictable application performance.
