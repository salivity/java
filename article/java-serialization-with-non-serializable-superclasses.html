Java Serialization with Non-Serializable Superclasses

Standard Java object serialization allows a class to implement java.io.Serializable even if its superclass does not. When this happens, the serialization mechanism saves only the state of the serializable subclass, while the non-serializable superclass's state is ignored during the writing process. Upon deserialization, the superclass state is re-initialized by invoking its accessible no-argument constructor, making the presence of such a constructor an absolute requirement for successful object reconstruction.

Serialization Behavior

During serialization using an ObjectOutputStream, the runtime traverses the class hierarchy of the object being serialized. The stream serializes fields starting from the first class in the hierarchy that implements Serializable down to the concrete subtype. Any fields declared directly in a non-serializable superclass are completely skipped and omitted from the serialized byte stream.

Deserialization and Constructor Execution

When the object is deserialized via an ObjectInputStream, the process reconstructs the object differently depending on the serializability of each level in the class hierarchy:

  1. Locating the Constructor: The runtime walks up the inheritance chain to locate the first non-serializable superclass.
  2. State Initialization: The runtime invokes the accessible zero-argument constructor of that non-serializable superclass. This constructor runs normally, setting the superclass fields to their default or constructor-defined values.
  3. Subclass Population: After the superclass is initialized via its constructor, the ObjectInputStream reads the serialized stream data and directly populates the fields of the serializable subclass without invoking any subclass constructors.

The No-Argument Constructor Requirement

For this mechanism to function, the non-serializable superclass must declare a no-argument constructor that is accessible to the subclass. The constructor must have public, protected, or package-private (if both classes reside in the same package) access.

If the non-serializable superclass lacks an accessible no-argument constructor, serialization may proceed without error, but deserialization will fail immediately at runtime by throwing a java.io.InvalidClassException.

Preserving Superclass State

Because the standard serialization protocol ignores the fields of a non-serializable superclass, any state stored at that level is lost by default. If that state must be preserved across serialization, the subclass must implement custom serialization logic using the writeObject and readObject private methods:

  • In writeObject(ObjectOutputStream out): Call out.defaultWriteObject() to serialize the subclass fields, followed by explicitly writing the superclass fields to the stream using methods like out.writeInt() or out.writeObject().
  • In readObject(ObjectInputStream in): Call in.defaultReadObject() to populate the subclass fields, followed by explicitly reading the superclass values back from the stream and setting them on the superclass using accessible setter methods or reflection.
