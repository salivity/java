Java Sealed Classes and Interfaces Constraints

This article provides an overview of the structural constraints enforced by the Java compiler when defining sealed classes and interfaces. Sealed types, finalized in Java 17, allow developers to restrict which other classes or interfaces may extend or implement them. To ensure type safety, exhaustiveness, and controlled inheritance hierarchies, the Java language specification enforces strict constraints regarding declarations, module boundaries, package locality, and subtype modifiers.

1. Mandatory Declaration of Subtypes (The permits Clause)

A sealed class or interface must explicitly declare its allowed subclasses or subinterfaces using the permits clause:

public sealed class Shape permits Circle, Square, Rectangle { }

The only exception to explicitly using the permits keyword is when all permitted subtypes are declared within the same source file as the sealed type. In this scenario, the compiler can automatically infer the permitted subclasses, and omitting the permits clause is allowed.

2. Direct Inheritance Requirement

Every permitted class listed in the permits clause must directly extend the sealed class or directly implement the sealed interface. Indirect subtypes cannot be listed in the sealed type's permits list. Conversely, any class attempting to extend a sealed class or implement a sealed interface must be explicitly listed in that sealed type's permits clause (or defined in the same compilation unit).

3. Packaging and Modular Scoping

Java enforces strict co-location constraints to prevent external libraries from unpredictably extending sealed hierarchies:

  • In a Named Module: The sealed type and all of its permitted subtypes must belong to the exact same module. They do not, however, need to be in the same package within that module.
  • In an Unnamed Module (Classpath): If the sealed type is defined outside of a named module, all permitted subtypes must be located in the exact same package.

4. Explicit Hierarchy Modifiers on Subtypes

Every class or interface that extends or implements a sealed type must explicitly define how it handles further inheritance. It must declare exactly one of the following three modifiers:

  • final: The subtype cannot be extended any further, terminating this branch of the hierarchy. (Note that record classes are implicitly final and can implement sealed interfaces).
  • sealed: The subtype continues restricting inheritance by defining its own set of permitted subclasses using its own permits clause.
  • non-sealed: The subtype opens the hierarchy back up, allowing any arbitrary class to extend it.

Interfaces cannot be declared final, so a permitted subinterface must be declared either sealed or non-sealed.

5. Prohibition of Anonymous and Local Classes

Sealed classes and interfaces cannot be implemented or extended using anonymous classes or local classes. Because all subtypes must be known statically at compile time and explicitly bound to a named identifier, anonymous instantiations such as new Shape() { ... } will result in a compilation error.
