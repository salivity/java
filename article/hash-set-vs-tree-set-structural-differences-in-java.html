HashSet vs TreeSet: Structural Differences in Java

Java provides both HashSet and TreeSet as core implementations of the Set interface, but they rely on fundamentally different internal data structures to store and manage elements. While HashSet is built on an underlying hash table providing constant-time performance without ordering guarantees, TreeSet is implemented as a self-balancing binary search tree that maintains strict element ordering at logarithmic time complexity. Understanding these structural distinctions is essential for selecting the optimal collection based on memory, performance, and ordering requirements.

Underlying Data Structures

The most prominent difference lies in the foundational data structure each class uses:

  • HashSet (Hash Table): Internally, a HashSet is backed by a HashMap. Every element added to the set is stored as a key in the map, paired with a dummy Object as its value. The data is organized into an array of buckets. When an element is inserted, its hashCode() determines the target bucket index. Collisions are handled via linked lists that convert to balanced red-black trees ("treeification") when a bucket exceeds a specific threshold (typically eight nodes in modern Java runtimes).
  • TreeSet (Red-Black Tree): A TreeSet is backed by a NavigableMap, specifically a TreeMap. Like HashSet, elements are placed as keys alongside a dummy value. However, the data structure is a self-balancing Red-Black Tree. It does not use hash codes or buckets; instead, each node maintains references to its parent, left child, right child, and a boolean color flag used during rebalancing operations.

Element Storage and Node Layout

Because their underlying engines differ, the memory footprint and node architectures of HashSet and TreeSet diverge significantly:

  • HashSet Nodes: Elements are wrapped inside HashMap.Node<K, V> instances containing the key, the dummy value, a cached 32-bit hash value, and a reference to the next node in the bucket chain.
  • TreeSet Nodes: Elements reside in TreeMap.Entry<K, V> instances. These nodes contain the key, the dummy value, references to three adjacent tree nodes (left, right, and parent), and a color bit used to maintain black-height balance across the tree.

Ordering and Traversal

The physical arrangement of data directly dictates how each set iterates over elements:

  • HashSet: Iteration order is non-deterministic and can shift as the set resizes and rehashes elements. Traversal requires scanning through the entire backing bucket array, which means iterating over an empty or sparse HashSet with a large capacity carries an overhead proportional to the capacity itself.
  • TreeSet: Iteration strictly follows an in-order tree traversal, guaranteeing that elements are visited in ascending order according to their natural ordering (Comparable) or a custom Comparator. Navigational operations such as first(), last(), headSet(), tailSet(), higher(), and lower() are structurally supported directly by the tree layout.

Time Complexity

The structural differences determine algorithmic guarantees:

  • HashSet: Offers constant-time performance—\(O(1)\) on average—for basic operations like add(), remove(), and contains(). In the rare event of severe hash collisions, modern implementations degrade to \(O(\log n)\) for bucket lookup.
  • TreeSet: Guarantees \(O(\log n)\) time for add(), remove(), and contains(). The tree's height is strictly constrained to \(2 \log(n + 1)\), ensuring predictable performance regardless of element distribution.

Null Element Handling

  • HashSet: Allows one null element because the backing HashMap maps null keys explicitly to bucket index 0 without invoking hashCode().
  • TreeSet: Disallows null elements in standard configurations. Inserting a null value causes a NullPointerException because the Red-Black tree must compare each incoming key against existing nodes to determine its branch position.
