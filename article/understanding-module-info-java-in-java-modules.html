Understanding module-info.java in Java Modules

This article provides an overview of the module-info.java file, the foundational descriptor of the Java Platform Module System (JPMS) introduced in Java 9. It examines the file's role in establishing boundaries, managing explicit dependencies, controlling encapsulation, and configuring service providers to build secure and maintainable modular Java applications.

The Central Role of module-info.java

The module-info.java file serves as the blueprint for a Java module. Located in the root directory of the module's source hierarchy, this descriptor is compiled into a module-info.class binary alongside standard source code. Through this file, a developer explicitly dictates what the module needs to run, what it exposes to other modules, and what it keeps strictly private, replacing the historically fragile and flat classpath model with a structured graph of dependencies.

Explicit Dependency Management

In standard Java development prior to modularity, missing classes or version conflicts often resulted in runtime failures such as NoClassDefFoundError. The module-info.java file prevents this through the requires directive:

  • requires <module>: Declares that this module depends on another module at both compile-time and runtime. If a required module is missing, the Java compiler or runtime halts immediately with a clear error.
  • requires transitive <module>: Passes a dependency downstream, allowing any module that depends on this module to automatically read the specified transitive module without declaring it explicitly.
  • requires static <module>: Marks a dependency as mandatory at compile time but optional at runtime.

Strong Encapsulation

By default, everything inside a module is private and inaccessible to other modules, even if the classes and methods are marked public. The descriptor controls visibility using encapsulation directives:

  • exports <package>: Makes all public types and members within a specific package accessible to other modules. Any package not explicitly exported remains strictly internal.
  • exports <package> to <module>: Implements qualified exports, restricting access to a specific package exclusively to designated partner modules.
  • opens <package>: Permits deep reflection into the specified package at runtime, essential for frameworks like Spring, Hibernate, or Jackson that require access to private fields. An entire module can also be declared as open module to permit reflection across all its packages.

Service Provider Architecture

The module-info.java file natively integrates with the Java ServiceLoader API, decoupling service consumers from their implementations without requiring external configuration files:

  • uses <interface/abstract class>: Signals that the module consumes a specific service interface.
  • provides <interface> with <implementation>: Declares that the module provides a concrete implementation of a service interface.

Summary of Benefits

By serving as a formal, machine-readable contract, module-info.java delivers reliable configuration and strong encapsulation. It enables early detection of missing dependencies, protects internal implementation details from unauthorized access, and allows tools like jlink to produce minimal, custom runtime images containing only the necessary modules.
