Java Serialization Filters and Object Validation

Java serialization filters provide a defensive programming mechanism that validates incoming object graphs before classes are instantiated during deserialization. By inspecting critical metrics such as class types, graph depth, array lengths, and object reference counts, these filters intercept potentially dangerous data streams early. This article explores how Java serialization filters operate, why they are essential for mitigating deserialization vulnerabilities, and how they inspect object graphs in modern Java runtimes.

The Threat Model of Java Deserialization

Standard Java deserialization reconstitutes serialized byte streams back into live objects using ObjectInputStream.readObject(). Traditionally, this process automatically loads classes and invokes constructors or specialized read methods without prior validation. Attackers exploit this behavior using "gadget chains"—sequences of existing classes on the application's classpath that, when chained together through deserialization, execute unintended actions such as arbitrary code execution or denial of service.

What Are Serialization Filters?

Introduced in Java 9 via JEP 290 and refined in Java 17 via JEP 415, serialization filters allow applications to intercept and inspect serialized streams prior to object creation. Defined by the java.io.ObjectInputFilter functional interface, a filter acts as a security gatekeeper. Each time the stream encounters a class descriptor, array allocation, or reference in the stream, it queries the filter to determine whether to proceed.

The filter returns one of three statuses:

  • Status.ALLOWED: The element passes inspection and is deserialized.
  • Status.REJECTED: The element is immediately blocked, throwing an InvalidClassException and terminating deserialization.
  • Status.UNDECIDED: The filter defers the decision to another filter in the chain or accepts the default behavior.

Validating the Object Graph

Serialization filters validate incoming streams by inspecting an instance of ObjectInputFilter.FilterInfo. This interface provides two primary categories of metadata: class identifiers and stream resource metrics.

1. Type Filtering and Class Matching

Filters check incoming class names against patterns, allowlists, or denylists. Modern security practices emphasize allowlisting—only permitting classes explicitly needed for business logic. A pattern-based filter can be configured via a pattern string (e.g., com.example.model.*;java.lang.*;!* to accept specific packages and reject everything else). If a gadget class (like an unexpected Apache Commons Collections invocation handler) appears in the stream, the filter rejects it before the JVM instantiates it.

2. Resource Limit Enforcement

Attackers often craft malicious payloads that do not rely on gadget chains, but instead trigger resource exhaustion (e.g., "Billion Laughs" style deserialization bombs or deeply nested arrays). Serialization filters monitor structure-level metrics:

  • Graph Depth: Tracks the nesting level of objects within objects. Exceeding a defined limit stops deeply nested attacks.
  • Array Sizes: Monitors the requested allocation sizes when arrays are declared, preventing memory exhaustion attacks before the heap is consumed.
  • Object References: Limits the cumulative count of instantiated objects during a single deserialization call.
  • Stream Size: Inspects the total consumed bytes relative to configured safety thresholds.

Filter Application in Modern Java

Modern Java supports three levels of filter configuration:

  • JVM-Wide Global Filters: Configured via the system property jdk.serialFilter or the conf/security/java.security configuration file. This applies a universal baseline across the entire Java process.
  • Stream-Specific Filters: Explicitly attached to individual ObjectInputStream instances using setObjectInputFilter(filter). This allows localized filtering tailored to specific network sockets or files.
  • Context-Specific Filter Factories (JEP 415): Java 17 introduced ObjectInputFilter.Config.setSerialFilterFactory, which dynamically supplies filters based on execution context, thread, or library context. This resolves architectural issues where third-party libraries or frameworks might otherwise overwrite or bypass global serialization policies.

By pairing strict class allowlisting with stringent resource limits, serialization filters effectively neutralize the vast majority of object-injection and denial-of-service vectors inherent in legacy serialization protocols.
