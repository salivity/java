How LongAdder Minimizes Contention in Java

Java's LongAdder provides a highly scalable alternative to AtomicLong for multi-threaded counters by distributing updates across a striped set of internal storage locations called cells. Instead of forcing every thread to compete for a single memory address using repeated Compare-And-Swap (CAS) loops, LongAdder dynamically partitions writes across an array of 64-bit values. This article explains the internal mechanics of LongAdder, including its fallback mechanisms, thread probe hashing, false-sharing prevention, and eventual consistency model.

The Bottleneck of AtomicLong

AtomicLong relies on a single volatile long field updated via hardware-level CAS instructions. Under low contention, this is extremely fast. However, when dozens of threads attempt to increment the counter simultaneously, most CAS attempts fail because another thread has already modified the memory state. This triggers heavy spin-locking and forces cache coherency traffic (cache-line bouncing) across CPU cores, degrading overall throughput.

Internal Architecture: The Striped64 Foundation

LongAdder extends java.util.concurrent.atomic.Striped64, an internal class designed to hold 64-bit numeric data across multiple variables. The core components of this architecture are:

  • A base field: A 64-bit value updated when contention is absent or before the cell table is initialized.
  • A cells array: A lazily initialized array of Cell objects, each holding an independent 64-bit value.
  • A cellsBusy lock: A lightweight spin-lock flag used strictly when initializing or resizing the cells array, or creating new cells.

How Updates Are Routed to Cells

When a thread invokes add(long x) or increment(), LongAdder executes a specific decision path:

  1. Attempt Base Update: If the cells array is uninitialized, the thread attempts to update the base field using a standard CAS operation. If this succeeds, the operation completes without allocating memory.
  2. Contention Detection: If the CAS on base fails, contention is detected. The thread then inspects the cells array. If the array does not exist, it acquires the cellsBusy lock to allocate an initial array of size two.
  3. Thread Probe Hashing: Each thread is assigned an internal pseudo-random hash value called a probe, accessed through ThreadLocalRandom.getProbe(). The thread maps this probe to an index in the array using a bitwise mask: index = probe & (cells.length - 1).
  4. Target Cell CAS: The thread executes a CAS operation specifically on the value field of the assigned Cell. Because different threads hash to different slots, they execute CAS operations on distinct memory addresses, avoiding mutual interference.

Dynamic Resizing and Collision Resolution

If multiple threads hash to the exact same cell and their CAS operations fail, LongAdder resolves the collision dynamically:

  • Probe Re-hashing: The thread re-hashes its probe value using a secondary multiplier to find a different cell, attempting to succeed without allocating more memory.
  • Table Doubling: If collisions persist and the array size is smaller than the number of available CPU cores, the thread acquires the cellsBusy lock and doubles the size of the cells array.
  • Core Capacity Cap: The array never grows larger than the next power of two greater than or equal to the number of available processors. Because a machine cannot execute more threads concurrently than it has logical CPU cores, allocating more cells than cores provides no performance benefit and wastes memory.

Preventing False Sharing

Distributing values across an array introduces the risk of false sharing, where adjacent Cell objects reside on the same CPU cache line (typically 64 bytes). When one thread writes to its cell, it would inadvertently invalidate the cache line for a neighboring cell, reintroducing cache bouncing.

To prevent this, the Cell class is annotated with @jdk.internal.vm.annotation.Contended. The JVM automatically inserts padding around each Cell object to ensure it occupies an isolated cache line, ensuring that writes to one cell have zero impact on the cache status of adjacent cells.

Reading the Accumulated Value

The write path is optimized for speed at the expense of atomic reads. When sum() is called, LongAdder iterates through the base value and every non-null entry in the cells array, returning their cumulative sum:

public long sum() {
    Cell[] cs = cells;
    long sum = base;
    if (cs != null) {
        for (Cell c : cs)
            if (c != null)
                sum += c.value;
    }
    return sum;
}

The sum() method does not acquire locks, freeze threads, or take an atomic snapshot. If concurrent updates occur while sum() runs, individual updates may be included or omitted. Consequently, LongAdder is intended for throughput-heavy scenarios like metrics collection, telemetry, and high-frequency counters where fine-grained point-in-time synchronization is secondary to raw write performance.
