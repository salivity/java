Unnamed Patterns and Variables in Java

This article explores how unnamed patterns and variables, represented by the underscore character (_), enhance Java code readability and maintainability. Introduced as a preview in Java 21 and finalized in Java 22 via JEP 456, this feature allows developers to discard unused variables and pattern components explicitly. By replacing placeholder names with a single underscore, code becomes cleaner, developer intent is clarified, and unnecessary compiler warnings are eliminated.

The Problem with Unused Identifiers

Prior to Java 22, developers were forced to declare names for variables even when those variables were never intended to be used. Common examples include naming exception variables in catch blocks, loop indices, try-with-resources statements, and lambda parameters. Developers frequently used arbitrary names like ignored, unused, e, or dummy.

This approach introduces visual clutter and obscures the developer's intent. Future readers must scan the scope to verify whether the variable is truly unused or mistakenly referenced. Furthermore, static analysis tools and compilers frequently flag these identifiers as unused, requiring suppressions like @SuppressWarnings("unused").

Improving Code with Unnamed Variables

Using the underscore as an unnamed variable explicitly informs both the compiler and fellow developers that a value is intentionally ignored. Because an unnamed variable cannot be read or referenced, it completely eliminates accidental usage bugs.

Exception Handling

In try-catch blocks where only the occurrence of an exception matters, the exception variable name can be replaced:

try {
    return Integer.parseInt(userInput);
} catch (NumberFormatException _) {
    return defaultValue;
}

This syntax immediately signals that the details of NumberFormatException are irrelevant to the handling logic.

Lambdas with Multiple Parameters

When an API requires a lambda with multiple parameters but only a subset is needed, the underscore cleans up the signature:

// Map.computeIfPresent takes key and value, but only value is updated
map.computeIfPresent("total", (_, count) -> count + 1);

Enhanced For-Loops and Try-With-Resources

The underscore can be used to iterate over collections without binding a named element:

int total = 0;
for (Transaction _ : transactions) {
    total++;
}

try (var _ = ScopedContext.acquire()) {
    performTask();
}

Enhancing Pattern Matching with Unnamed Patterns

Pattern matching in modern Java allows for deconstructing complex objects such as records. Frequently, logic only depends on a specific component of the record, leaving other fields unnecessary.

Without unnamed patterns, developers must bind every component:

if (obj instanceof Point(int x, int y)) {
    System.out.println("X coordinate: " + x);
}

With unnamed patterns, unused record components can be omitted using the underscore:

if (obj instanceof Point(int x, _)) {
    System.out.println("X coordinate: " + x);
}

This also extends to full pattern matching in switch expressions, where matching the shape or type of an object is required, but extracting its inner data is not:

switch (shape) {
    case Circle(Point(int x, _), double r) -> drawCircle(x, r);
    case Rectangle(_, int width, int height) -> drawRect(width, height);
    case Box(_) -> processBox();
}

Key Readability Benefits

  1. Clear Developer Intent: A single underscore unequivocally communicates that a value is discarded by design, removing the ambiguity of identifiers like unused.
  2. Defensive Programming: Because the compiler forbids referencing _ as a variable, developers cannot accidentally read or mutate a variable that was meant to be ignored.
  3. Reduced Code Noise: Codebases become less verbose, making it easier for reviewers to focus on the business logic rather than boilerplate definitions.
  4. Cleaner Static Analysis: It natively prevents warnings from compilers and linters regarding unused local variables and parameters.
