Typical Java Cache Line Size for Data Alignment

In multi-threaded Java applications, CPU memory subsystem performance depends heavily on how data maps to CPU cache lines to prevent issues like false sharing. This article covers the cache line size typically assumed by the Java runtime when aligning data, the distinction between object alignment and cache line alignment, and the specific mechanisms HotSpot uses to isolate performance-critical variables in hardware memory structures.

The Typical Assumed Cache Line Size

The Java Virtual Machine (JVM), specifically the standard OpenJDK HotSpot implementation, typically assumes a cache line size of 64 bytes on modern hardware architectures, including x86-64 and ARM64.

While the exact size is ultimately determined by the host CPU, 64 bytes has been the industry standard for mainstream consumer and server processors for decades. The JVM queries the operating system and CPU capabilities at startup to confirm this geometry, but core HotSpot design heuristics and padding defaults are tailored around 64-byte boundaries.

Object Alignment vs. Cache Line Alignment

It is important to separate regular object alignment from cache-level alignment:

  • Object Alignment: By default, HotSpot aligns objects on an 8-byte boundary (-XX:ObjectAlignmentInBytes=8). This allows the JVM to use compressed object pointers (Compressed Oops) on heaps up to 32 GB. This alignment is designed for memory density and pointer addressing efficiency, not cache-line isolation.
  • Cache Line Alignment: Cache line alignment is applied to prevent two independent variables from residing within the same 64-byte chunk of memory, which avoids false sharing across CPU cores.

Cache Line Padding and False Sharing

When multiple threads read and write to independent fields located within the same 64-byte cache line, the CPU cores must continuously invalidate and synchronize that entire line across their L1/L2 caches. This phenomenon, known as false sharing, introduces substantial latency.

To address this, Java provides the @jdk.internal.vm.annotation.Contended annotation (originally @sun.misc.Contended). When a field or class is marked with this annotation, the runtime introduces padding to isolate the data.

Interestingly, while the baseline cache line size is 64 bytes, HotSpot's default padding configuration uses 128 bytes via the flag:

-XX:ContendedPaddingWidth=128

The runtime defaults to 128 bytes rather than 64 bytes to mitigate the effects of modern CPU hardware prefetchers (such as adjacent cache line prefetchers found in Intel and AMD processors). These hardware units frequently fetch two consecutive 64-byte cache lines at once. By enforcing a 128-byte padding isolation, the runtime guarantees that the annotated field will not share a line pair with any neighboring memory locations.

Runtime Configuration

Developers can inspect and modify these alignment behaviors using JVM command-line options:

  • -XX:ContendedPaddingWidth=<bytes>: Adjusts the padding width used by @Contended (default is usually 128, but can be set to 64 if adjacent prefetching is disabled).
  • -XX:-RestrictContended: Enables the use of @Contended outside the JDK internal packages in application code.

In summary, while the Java runtime assumes a base hardware cache line size of 64 bytes, it typically enforces 128-byte data isolation boundaries for concurrent padding to account for both the cache line size and hardware-level prefetching.
