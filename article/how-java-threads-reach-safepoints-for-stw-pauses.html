How Java Threads Reach Safepoints for STW Pauses

This article explains the internal mechanics used by the Java Virtual Machine (JVM) to halt application threads during Stop-the-World (STW) operations. It details what safepoints are, how the JVM signals threads to stop, where safepoint checks are placed in application code, and how threads in different states—such as executing compiled code, running native methods, or blocked on I/O—transition into a safe, suspended state.

What Is a Safepoint?

A safepoint is a designated point in a thread's execution where its execution state, memory references, and registers are consistent and fully known to the JVM. During a Stop-the-World event—such as Garbage Collection (GC) phases, thread dumps, code deoptimization, or biased lock revocation—all application threads (mutators) must stop at a safepoint so the VM thread can safely inspect or modify heap memory without concurrent interference.

The Safepoint Polling Mechanism

Instead of asynchronously interrupting threads via OS-level signals, the JVM relies on a cooperative polling mechanism. As threads execute Java code, they periodically check whether a safepoint has been requested.

1. In Compiled Code (JIT)

The Just-In-Time (JIT) compiler (C1/C2) automatically inserts safepoint checks (polling instructions) into generated machine code. These checks are typically placed at:

  • Method exits (returns): Ensuring a thread checks the safepoint flag before returning from a function call.
  • Loop back-edges: Ensuring that long-running or infinite loops do not prevent the thread from reaching a safepoint. (Note: Counted loops with int indices are sometimes unrolled and may omit safepoint checks unless configured otherwise via flags like -XX:+UseCountedLoopSafepoints).

2. In Interpreted Code

When running in bytecode interpretation mode, the interpreter dispatches instructions via a dispatch table. When a safepoint is requested, the JVM replaces the normal dispatch table with an alternate table that redirects bytecode execution to a safepoint handler, or checks a thread-state flag between bytecode instructions.

How the JVM Triggers the Pause

Historically, HotSpot used a global safepoint page. When a STW operation was needed, the VM thread modified the memory protection of this dummy page using an OS call (such as mprotect on POSIX systems) to make it unreadable. Any thread attempting to read from this page would trigger a page fault (SIGSEGV), which the JVM's signal handler intercepted, interpreting it as an order to park the thread until the safepoint ended.

In modern JVMs (Java 10+), HotSpot uses Thread-Local Handshakes (JEP 312). Rather than relying on page faults across all threads, each thread has its own individual polling page. This allows the JVM to initiate STW events by arming polling pages either globally or per-thread, greatly reducing overhead and improving pause coordination.

Thread Behavior by Execution State

Not all threads are actively executing Java bytecode when a safepoint is requested. The JVM handles different thread states as follows:

  • Running Java Code: Threads actively running interpreted or JIT-compiled code will execute until they hit the next injected poll instruction, acknowledge the armed safepoint, and block themselves on a synchronization lock held by the VM thread.
  • Executing Native Code (JNI): A thread in native code cannot directly manipulate Java heap references without invoking JNI functions. Because the heap is safe from native alterations, JNI threads are allowed to continue running during a safepoint. However, as soon as a native thread attempts to return to Java or access the Java heap via a JNI interface, it encounters a safepoint check and is blocked until the STW operation concludes.
  • Blocked or Waiting (System Calls, Locks, I/O): Threads that are blocked on operating system monitors, waiting on object monitors (Object.wait()), or blocked on network/disk I/O are already in a known, stable state. The JVM considers them to be at a safepoint implicitly. If they unblock while the safepoint is active, they will stall before transitioning back to active execution.

Time to Safepoint (TTSP)

The duration between the JVM requesting a safepoint and the final application thread successfully parking is known as Time to Safepoint (TTSP).

Because threads must reach an injected check cooperatively, delays can occur. Common causes of high TTSP include:

  • Long-running, counted loops that lack loop-strip mining or uncounted back-edges.
  • Lengthy JNI calls that do not interact with the JVM.
  • Page-fault delays or high operating system scheduling latency.

Once all mutator threads are confirmed to be parked or in safe native/blocked states, the VM thread executes the requested maintenance task.

Resuming Application Threads

After completing the maintenance operation, the VM thread disarms the polling mechanism—restoring memory permissions or resetting the thread-local handshake flags. It then signals the conditional variables or locks that parked the application threads. The threads wake up, resume normal execution from their saved register states, and continue processing instructions.
