Thread Pinning in Java Virtual Threads Explained

Java virtual threads significantly boost application throughput by decoupling lightweight threads from underlying operating system threads, but thread pinning presents a critical bottleneck to this model. Thread pinning occurs when a virtual thread becomes locked to its underlying platform carrier thread and cannot unmount during a blocking operation. This behavior deprives the carrier thread pool of execution capacity, directly undermining the concurrency and scalability benefits that virtual threads are designed to provide.

How Virtual Threads Work

Virtual threads operate using an M:N scheduling model managed by the Java Virtual Machine (JVM). Thousands or even millions of virtual threads are multiplexed across a small pool of carrier platform threads, typically sized to match the number of available CPU cores.

When a virtual thread executes a blocking operation—such as socket I/O, file operations, or Thread.sleep()—the JVM unmounts the virtual thread from its carrier thread. The carrier thread is then free to execute other runnable virtual threads. Once the blocking operation completes, the runtime remounts the virtual thread onto an available carrier thread to resume execution.

How Thread Pinning Occurs

Thread pinning happens when the JVM runtime is unable to unmount a virtual thread from its carrier thread during a blocking call. When a thread is pinned, both the virtual thread and its carrier thread remain blocked together.

There are two primary causes of thread pinning in the Java runtime:

  1. Synchronized Blocks and Methods: When a virtual thread executes inside a synchronized block or method and encounters a blocking operation, the thread is pinned. The internal monitor implementation holds references on the native call stack, which prevents the virtual thread frame from being safely unmounted and parked into the Java heap.
  2. Native Code and Foreign Functions: If a virtual thread invokes a native method via the Java Native Interface (JNI) or the Foreign Function & Memory (FFM) API, and subsequently blocks, the virtual thread cannot unmount because the execution context resides partly outside the JVM’s control on the native OS stack.

Why Pinning Impacts Scalability

Thread pinning directly degrades the scalability of virtual thread-based applications in several ways:

  • Carrier Thread Starvation: The carrier pool is intentionally small, often equal to Runtime.getRuntime().availableProcessors(). If all carrier threads become pinned by blocking operations, the scheduler cannot run other virtual threads, even if millions of them are waiting in the queue.
  • Loss of High Concurrency: Under normal conditions, a system can handle hundreds of thousands of concurrent I/O operations because unmounted virtual threads consume minimal heap memory and zero CPU cycles. Pinning reduces the practical concurrency limit back down to the size of the carrier pool, reverting application behavior to the traditional thread-per-request model.
  • Latency Spikes and Deadlocks: When carrier threads are blocked by pinned operations, non-pinned tasks experience severe scheduling delays. In worse cases, if pinned threads are waiting for responses or events generated by other virtual threads that cannot get scheduled onto a carrier thread, the system can experience thread starvation deadlocks.

Mitigating Thread Pinning

To prevent thread pinning from undermining scalability:

  • Use ReentrantLock Instead of Synchronized: Replace synchronized blocks that guard blocking I/O with java.util.concurrent.locks.ReentrantLock. Unlike object monitors, the locks in java.util.concurrent are designed to allow virtual threads to unmount freely when waiting to acquire a lock or performing I/O.
  • Diagnose Pinning with System Properties: Identify pinning occurrences by running the JVM with the flag -Djdk.tracePinnedThreads=full or -Djdk.tracePinnedThreads=short. This generates stack traces whenever a virtual thread pins its carrier thread during a blocking operation.
  • Avoid Blocking Inside Native Calls: Ensure that native libraries and JNI wrappers do not perform long-running or blocking network/file operations while running on virtual threads.
