How ConcurrentHashMap Achieves Thread Safety in Java

Java’s ConcurrentHashMap delivers thread-safe operations with high throughput by eliminating the need to lock the entire data structure during reads and writes. Instead of using a single global lock like Hashtable or Collections.synchronizedMap, it relies on fine-grained concurrency control. Historically implemented via lock striping (segments), modern Java versions (Java 8 and later) achieve this performance through a combination of non-blocking Compare-And-Swap (CAS) operations, bucket-level synchronization, and volatile memory semantics.

The Shift from Segmented Locking to Bucket-Level Locking

In Java 7, ConcurrentHashMap used an internal array of segments, where each segment acted as an independent ReentrantLock. A write operation only locked the specific segment containing the target key, typically allowing up to 16 concurrent writes by default.

Starting in Java 8, the segment approach was replaced with a flat array of bins (buckets) identical in layout to a standard HashMap. Thread safety is now managed at the individual bin level, reducing lock contention even further. If two threads write to different bins, they execute simultaneously without blocking one another.

Lock-Free Writes with Compare-And-Swap (CAS)

When an insertion occurs, the map checks if the target array index is empty:

  1. Empty Bin Detection: If the hash index contains no existing nodes (null), no lock is acquired.
  2. Atomic Insertion: The thread uses low-level CAS operations (via Unsafe or VarHandle) to atomically set the new node at that index.
  3. Collision Handling: If the CAS operation succeeds, the insertion completes without ever acquiring a monitor lock. If the CAS fails because another thread inserted a node simultaneously, the thread retries the operation within a loop.

Synchronized Bucket Heads for Collisions

When a hash collision occurs and the target bucket already contains one or more nodes (either as a linked list or a Red-Black Tree), CAS alone is insufficient. In this scenario, the map uses standard Java synchronized blocks, but locks only the first node (head) of that specific bucket.

  • Targeted Locking: Locking the head node prevents other threads from modifying only that specific bucket chain or tree.
  • Independent Access: All other buckets remain unlocked, allowing other threads to read or write to different parts of the map concurrently.
  • Low Overhead: Because modern JVMs optimize uncontended and lightly contended synchronized monitors via biased locking and adaptive spinning, the synchronization overhead is minimal.

Lock-Free Reads via Volatile Visibility

Read operations using get() are entirely non-blocking and acquire no locks whatsoever. This is accomplished using volatile memory semantics:

  • The node table reference itself is volatile.
  • The val (value) and next pointers within each Node are declared volatile.

When a thread modifies a value or appends a node, the changes are instantly visible to reading threads across CPU caches. Readers traverse the linked list or tree concurrently with active writes, safely reading the state without stalling.

Concurrent Resizing

Resizing a standard hash table is an expensive operation that normally requires full locking. ConcurrentHashMap avoids this through cooperative, multi-threaded resizing:

  • When the table needs to expand, the initiating thread allocates a new array twice the size and sets up a migration state.
  • The map introduces a special ForwardingNode at the head of bins that have already been migrated.
  • If another thread attempts to write to a bin that has a ForwardingNode, it does not block; instead, it actively assists the resizing process by transferring other buckets to the new table.
  • Reading threads encountering a ForwardingNode seamlessly redirect their search to the new table without waiting.
