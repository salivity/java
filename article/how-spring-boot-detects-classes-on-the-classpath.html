How Spring Boot Detects Classes on the Classpath

Spring Boot auto-configuration relies heavily on classpath detection to selectively activate configuration classes and register beans in the application context. By combining conditional annotations like @ConditionalOnClass with low-level bytecode inspection via the ASM library and standard Java ClassLoader queries, Spring Boot dynamically verifies whether a dependency is present at runtime. This process allows applications to automatically configure frameworks such as Hibernate, Jackson, or embedded web servers purely based on the presence of specific library JARs, all while avoiding runtime ClassNotFoundException errors.

The Entry Point: Conditional Annotations

Auto-configuration classes are marked with conditional annotations that dictate when they should be processed. The primary annotations for classpath inspection are:

  • @ConditionalOnClass: Activates a configuration only if the specified class or classes are present.
  • @ConditionalOnMissingClass: Activates a configuration only if the specified class or classes are absent.

These annotations accept either direct class references (e.g., @ConditionalOnClass(DataSource.class)) or fully qualified class names as strings (e.g., @ConditionalOnClass(name = "org.h2.Driver")).

Avoiding Premature Class Loading with ASM

A major challenge when inspecting the classpath is that attempting to load a non-existent class directly via the standard Java ClassLoader triggers a ClassNotFoundException or NoClassDefFoundError.

To prevent this, Spring Framework uses ASM, an internal bytecode manipulation library, accessed via SimpleMetadataReaderFactory and MetadataReader. When Spring evaluates configuration classes, it reads the .class files directly as raw byte streams without actually loading the classes into the Java Virtual Machine's memory. This allows Spring Boot to inspect the annotations and their attributes in a safe sandbox before determining whether the target classes are truly resolvable.

The Evaluation Engine: OnClassCondition

The core logic for checking class availability resides in the OnClassCondition class, which extends FilteringSpringBootCondition. During the context refresh phase, Spring Boot executes the getMatchOutcome method of OnClassCondition to evaluate matching criteria.

The evaluation process operates in two distinct ways depending on how the annotation was declared:

  1. Class Literals: When an annotation uses direct class references, the JVM resolves the class during the loading of the configuration class itself. If a class literal cannot be loaded, the entire configuration class is safely discarded by Spring's condition evaluator before it causes a fatal runtime exception.
  2. String Class Names: When specified as a string, OnClassCondition uses ClassUtils.isPresent(className, classLoader). This utility method attempts to load the class using Class.forName(className, false, classLoader). Passing false for the initialization parameter ensures the class is loaded into memory without running its static initializers, keeping the check lightweight and free of side effects.

ClassLoader Delegation

Spring Boot determines the runtime environment by querying the active ClassLoader. Typically, this is the Thread.currentThread().getContextClassLoader(), but it can fall back to the class loader that loaded the Spring application context itself.

The evaluation resolves the specified resource by asking the ClassLoader if the corresponding .class file path exists within any of the application's runtime dependencies or modules. If the ClassLoader successfully locates and loads the class metadata, the condition evaluates to a match; otherwise, it reports a mismatch, and the associated @Configuration or @Bean declaration is skipped.
