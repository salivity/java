Java Record Patterns: Deconstruct Compound Records

Record patterns, finalized in Java 21, allow developers to unpack and match components of record instances directly within instanceof and switch statements. When applied to compound—or nested—records, this feature enables deep deconstruction, breaking down multi-layered data structures into their primitive components in a single, declarative step. By eliminating tedious getter chains and intermediate null checks, nested record patterns significantly reduce boilerplate while improving type safety and code clarity.

Understanding Compound Records

A compound record is simply a record containing one or more other records as components. Consider the following domain model representing geometric shapes:

public record Point(int x, int y) {}
public record Rectangle(Point topLeft, Point bottomRight) {}

Before record patterns, accessing the primitive coordinates of a Rectangle required explicit casting, null checks, and sequential accessor calls:

if (obj instanceof Rectangle) {
    Rectangle r = (Rectangle) obj;
    Point tl = r.topLeft();
    Point br = r.bottomRight();
    int x1 = tl.x();
    int y1 = tl.y();
    // Use coordinates...
}

Deep Deconstruction with instanceof

With nested record patterns, you can deconstruct both the outer Rectangle and its inner Point components simultaneously:

if (obj instanceof Rectangle(Point(int x1, int y1), Point(int x2, int y2))) {
    System.out.println("Width: " + (x2 - x1));
    System.out.println("Height: " + (y2 - y1));
}

In this expression:

  1. Java verifies that obj is an instance of Rectangle.
  2. It deconstructs Rectangle into its topLeft and bottomRight components.
  3. It checks that both components match the Point pattern.
  4. It extracts x1, y1, x2, and y2 as local variables available inside the scope of the if block.

If any component in the chain is null or fails to match the expected type, the pattern fails gracefully and evaluates to false.

Using var for Type Inference

You do not need to explicitly declare the type of every inner component. The var keyword works seamlessly inside record patterns to infer component types automatically:

if (obj instanceof Rectangle(Point(var x1, var y1), var bottomRight)) {
    System.out.println("Top-left X: " + x1);
    System.out.println("Bottom-right: " + bottomRight);
}

This flexibility allows you to selectively deconstruct only the fields you need while keeping references to other objects intact.

Pattern Matching in switch Expressions

Compound record patterns shine brightest in pattern-matching switch statements and expressions, enabling clean data-driven branching:

public static double calculateArea(Object shape) {
    return switch (shape) {
        case Rectangle(Point(var x1, var y1), Point(var x2, var y2)) ->
            Math.abs((double) (x2 - x1) * (y2 - y1));
        case Point(var x, var y) -> 
            0.0;
        default -> 
            throw new IllegalArgumentException("Unknown shape: " + shape);
    };
}

You can also combine nested patterns with pattern guards (when clauses) to enforce business rules directly in the case label:

switch (shape) {
    case Rectangle(Point(var x1, var y1), Point(var x2, var y2)) when x1 == x2 && y1 == y2 ->
        System.out.println("Degenerate rectangle (zero area)");
    case Rectangle(Point(var x1, var y1), Point(var x2, var y2)) ->
        System.out.println("Valid rectangle");
    default -> {}
}

Key Advantages

  • Exhaustiveness and Safety: The compiler enforces exhaustive matching when used with sealed hierarchies, ensuring every possible nested state is accounted for.
  • Null-Hostile Matching: Record patterns do not match null values by default, eliminating unexpected NullPointerExceptions during extraction.
  • Readability: Nested structures mirror the shape of the data they inspect, making the logic transparent and easy to maintain.
