How Java HashMap Bucket Resizing Works

This article provides a comprehensive technical overview of the internal bucket resizing mechanism in Java's HashMap. It explains the conditions that trigger the resizing process, how capacity scales, and the internal algorithmic mechanics used in modern Java (Java 8 and later) to redistribute entries efficiently between old and new bucket arrays without costly hash recomputations.

Resizing Triggers and Capacity Thresholds

A HashMap in Java manages its key-value pairs using an underlying array of nodes, commonly referred to as buckets. Resizing is triggered during an insertion operation (put or putVal) when the total number of key-value mappings in the map exceeds a defined threshold:

\[\text{Threshold} = \text{Current Capacity} \times \text{Load Factor}\]

The default initial capacity is 16, and the default load factor is 0.75. Under these defaults, the resizing procedure executes as soon as the 13th element is inserted (\(16 \times 0.75 = 12\)).

Capacity Doubling

When the threshold is breached, the map invokes its internal resize() method. The primary operation is allocating a new bucket array with twice the capacity of the existing array:

\[\text{New Capacity} = \text{Old Capacity} \ll 1\]

Because capacity is strictly maintained as a power of two (\(2^n\)), the bitmask used to map a key's 32-bit hash code to an array index is always \(\text{Capacity} - 1\). Doubling the capacity shifts the index bitmask by exactly one bit to the left.

Bitwise Node Redistribution (Java 8+)

Prior to Java 8, each entry required recalculating its index via hash & (newCapacity - 1). Java 8 introduced an optimization that eliminates the need to re-index elements from scratch.

Because the capacity doubles, a node's new index in the enlarged array is either:

  1. Exactly the same as its original index, or
  2. The original index plus the old capacity.

To determine which of these two positions an element belongs to, the algorithm evaluates the single bit that was added to the bitmask:

if ((e.hash & oldCap) == 0) {
    // Stays at the same index
} else {
    // Moves to (original index + oldCap)
}

Bucket Splitting and Preservation of Order

During redistribution, the algorithm iterates through each bucket in the old table and splits chained collisions into two separate linked lists:

  • Low List (loHead, loTail): Contains nodes where (e.hash & oldCap) == 0. This sub-list is placed into the new table at the identical bucket index.
  • High List (hiHead, hiTail): Contains nodes where (e.hash & oldCap) != 0. This sub-list is placed at index + oldCap.

Java 8 constructs these lists while preserving original insertion order (tail insertion), preventing the cyclical pointer loops during concurrent access that famously caused infinite loops in Java 7's head-insertion implementation.

Handling Tree Buckets

If a bucket has already been converted into a Red-Black tree (TreeNode) due to high collision volume (exceeding 8 elements), the resize() method delegates to TreeNode.split().

The tree is divided into low and high bins using the same (e.hash & oldCap) logic. If the number of nodes in either split bin drops to 6 or fewer (UNTREEIFY_THRESHOLD), the tree is converted back into a standard singly linked list. If the count remains higher than 6, the bin is restructured as a new balanced Red-Black tree at the appropriate destination index.
