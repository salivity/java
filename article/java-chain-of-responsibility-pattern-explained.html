Java Chain of Responsibility Pattern Explained

The Chain of Responsibility pattern decouples request senders from receivers by passing a request along an ordered chain of potential handler objects until one or more handle it. In Java, this behavioral design pattern eliminates explicit bindings between the invoker of an operation and the concrete classes responsible for executing the business logic. Instead of a sender maintaining direct references to multiple target receivers, it only interacts with a shared handler abstraction, enabling dynamic workflow configuration, reduced code coupling, and improved adherence to the Open/Closed Principle.

The Decoupling Mechanism

In a traditional implementation without the pattern, a sender must contain conditional logic (such as nested if-else or switch statements) to identify which receiver should process a given request. This approach tightly couples the sender to every concrete receiver class.

The Chain of Responsibility pattern resolves this through three core architectural elements:

  1. A Common Handler Interface: The sender targets a uniform interface or abstract class rather than concrete implementations. This interface defines the contract for processing requests and setting the next link in the chain.
  2. Successor References: Each concrete handler holds a reference to another handler instance (its successor). Handlers self-manage the traversal: if a handler cannot process the request, it forwards the payload to its successor.
  3. Sender Agnosticism: The sender only requires a reference to the head of the chain. It submits the request without knowing which specific object will handle it, how many objects will evaluate it, or if it will be processed at all.

Implementation in Java

The following example demonstrates how an authentication workflow decouples the client from individual validation steps.

1. The Handler Abstraction

public abstract class RequestHandler {
    private RequestHandler nextHandler;

    public RequestHandler setNext(RequestHandler nextHandler) {
        this.nextHandler = nextHandler;
        return nextHandler;
    }

    public void handle(String requestType) {
        if (canHandle(requestType)) {
            process(requestType);
        } else if (nextHandler != null) {
            nextHandler.handle(requestType);
        } else {
            System.out.println("End of chain: Request unhandled.");
        }
    }

    protected abstract boolean canHandle(String requestType);
    protected abstract void process(String requestType);
}

2. Concrete Handlers

public class AuthenticationHandler extends RequestHandler {
    @Override
    protected boolean canHandle(String requestType) {
        return "AUTH".equalsIgnoreCase(requestType);
    }

    @Override
    protected void process(String requestType) {
        System.out.println("AuthenticationHandler: Authenticating identity.");
    }
}

public class AuthorizationHandler extends RequestHandler {
    @Override
    protected boolean canHandle(String requestType) {
        return "ROLE_CHECK".equalsIgnoreCase(requestType);
    }

    @Override
    protected void process(String requestType) {
        System.out.println("AuthorizationHandler: Checking user permissions.");
    }
}

3. Client Interaction

public class Application {
    public static void main(String[] args) {
        // Chain composition: can be modified without altering the client
        RequestHandler chain = new AuthenticationHandler();
        chain.setNext(new AuthorizationHandler());

        // The sender only interacts with the root of the chain
        chain.handle("AUTH");
        chain.handle("ROLE_CHECK");
        chain.handle("AUDIT_LOG");
    }
}

Core Decoupling Benefits

  • Zero Sender-Receiver Dependencies: The client class does not import, instantiate, or reference AuthorizationHandler directly. Changes to receiver class names, constructor parameters, or execution logic require no modifications to the sender.
  • Dynamic Pipeline Reconfiguration: Handlers can be inserted, reordered, or removed at runtime or via dependency injection (such as Spring configuration) without impacting the invocation point.
  • Single Responsibility Principle: Each concrete handler manages one specific evaluation or business rule. The sender is responsible solely for initiating requests, not determining routing logic.
