Compressed OOPs in 64-Bit Java Virtual Machines

Compressed Ordinary Object Pointers (Compressed OOPs) are an optimization technique used by 64-bit Java Virtual Machines (JVMs) to reduce memory overhead and improve CPU cache utilization. Transitioning from a 32-bit to a 64-bit architecture solves heap size limitations but doubles the size of object references from 4 bytes to 8 bytes. Compressed OOPs bridge this gap by enabling a 64-bit JVM to represent object references using 32-bit pointers, allowing applications to utilize heaps up to 32 GB without suffering the memory consumption penalties typical of 64-bit pointers.

The 32-Bit vs. 64-Bit Trade-Off

In a 32-bit JVM, an object pointer is 32 bits (4 bytes) wide, which limits the maximum addressable heap space to 4 GB (\(2^{32}\) bytes). Moving to a 64-bit JVM removes this limitation, allowing virtually unlimited heap allocation.

However, this transition causes every object reference (ordinary object pointer, or OOP) to expand from 4 bytes to 8 bytes. Because Java applications often contain a large volume of references, this doubling causes two major issues:

  1. Memory Bloat: The JVM can consume up to 40% to 50% more memory simply to hold the same number of objects.
  2. Reduced Cache Efficiency: Larger pointers mean fewer references fit inside the CPU's L1, L2, and L3 caches, which leads to increased cache misses and reduced execution performance.

How Compressed OOPs Work

Compressed OOPs resolve this inefficiency by taking advantage of memory alignment. In the HotSpot JVM, all objects allocated on the heap are aligned to 8-byte boundaries. Because every object address is a multiple of 8, the lowest 3 bits of any object's memory address are always zeros:

  • 0x00000000 (ends in 000 in binary)
  • 0x00000008 (ends in 000 in binary)
  • 0x00000010 (ends in 000 in binary)

Because these three bits never change, the JVM does not need to store them.

Instead of storing direct byte addresses, the JVM stores object references as zero-based indices of 8-byte blocks. When the JVM reads a compressed OOP from memory into a CPU register, it performs a bitwise logical shift to the left by 3 bits (<< 3). This restores the original 64-bit address. When writing an address back to memory, it shifts the value to the right by 3 bits (>>> 3) to compress it into a 32-bit integer.

By scaling 32-bit integers by a factor of 8 (\(2^{32} \times 8\)), a 32-bit reference can successfully address up to 32 GB (\(2^{35}\) bytes) of heap memory.

Address Ranges and JVM Modes

The JVM dynamically configures its addressing mode based on the maximum heap size (-Xmx):

  • Heaps under 4 GB: The JVM uses standard 32-bit pointers without shifting, as addresses naturally fit within 32 bits.
  • Heaps between 4 GB and 32 GB: The JVM activates Compressed OOPs with a 3-bit shift. This provides the memory density of a 32-bit JVM alongside the capacity to address up to 32 GB of memory.
  • Heaps above 32 GB: A standard 32-bit pointer can no longer reference every 8-byte aligned address. The JVM automatically disables Compressed OOPs and reverts to full 64-bit pointers, which causes an immediate jump in reference size and overall heap consumption.

Managing Compressed OOPs

Compressed OOPs are enabled by default in modern 64-bit Java versions for compatible heap sizes. They are controlled using the JVM flag:

-XX:+UseCompressedOops (enable)
-XX:-UseCompressedOops (disable)

Because of the 32 GB threshold, setting a Java heap to 33 GB often results in less usable object space than setting it to 31 GB, as the overhead of 64-bit pointers consumes the additional memory. Therefore, applications requiring close to 32 GB should generally be sized just below this boundary to retain the performance and memory savings of compressed references.
