Instance Initializer Block vs Constructor in Java

This article examines the execution order of instance initialization blocks compared to constructors in Java. When instantiating an object, Java executes instance initializers before the code inside the constructor body, but immediately after the constructor's implicit or explicit call to super(). Understanding this flow is essential for ensuring fields are set up in the correct sequence, avoiding NullPointerExceptions, and organizing reusable initialization code across overloaded constructors.

The Standard Execution Sequence

Whenever a class is instantiated using the new keyword, the Java runtime follows a strict sequence:

  1. Superclass Constructor Invocation: The constructor is called, and its first line—either an explicit super() call or an implicit one provided by the compiler—runs immediately, triggering the parent class constructor chain.
  2. Instance Initializers and Field Initialization: Once super() completes, all instance variables with initial values and all instance initialization blocks run in the order they appear in the source code (from top to bottom).
  3. Constructor Body Execution: The remaining statements within the constructor body execute.

Because of this order, instance initialization blocks always execute before the constructor body, but after the superclass constructor.

Code Example: Basic Flow

public class InitializationDemo {

    // Instance variable initialized inline
    private String message = "Field initialized";

    // Instance initialization block
    {
        System.out.println(message);
        System.out.println("Instance initialization block executed");
    }

    // Constructor
    public InitializationDemo() {
        System.out.println("Constructor body executed");
    }

    public static void main(String[] args) {
        new InitializationDemo();
    }
}

Output:

Field initialized
Instance initialization block executed
Constructor body executed

How the Java Compiler Handles Instance Blocks

Under the hood, Java bytecode does not maintain a separate execution phase for instance initialization blocks. During compilation, the Java compiler (javac) copies the code inside all instance initialization blocks and field declarations directly into every constructor of that class.

The compiler places this combined code immediately after the super(...) call and just before the first line of custom code written in that constructor's body. If a constructor delegates to another constructor in the same class using this(...), the instance block code is not duplicated into the delegating constructor to avoid multiple executions.

Execution Order with Inheritance

When inheritance is involved, the sequence cascades through the class hierarchy from top to bottom:

  1. Static initializers of the parent class, followed by the child class (only once, at class load time).
  2. Parent class super() constructor (recursing up to java.lang.Object).
  3. Parent class instance field initializers and instance initialization blocks (in textual order).
  4. Parent class constructor body.
  5. Child class instance field initializers and instance initialization blocks (in textual order).
  6. Child class constructor body.

Example with Parent and Child Classes

class Parent {
    {
        System.out.println("1. Parent instance block");
    }

    Parent() {
        System.out.println("2. Parent constructor");
    }
}

class Child extends Parent {
    {
        System.out.println("3. Child instance block");
    }

    Child() {
        System.out.println("4. Child constructor");
    }

    public static void main(String[] args) {
        new Child();
    }
}

Output:

1. Parent instance block
2. Parent constructor
3. Child instance block
4. Child constructor

When to Use Instance Blocks vs. Constructors

While constructors are the primary tool for object initialization, instance initialization blocks have specific use cases:

  • Sharing Code Across Overloaded Constructors: If multiple constructors exist and cannot easily delegate to a single master constructor via this(...), an instance block ensures initialization logic runs for all instances.
  • Anonymous Inner Classes: Anonymous inner classes cannot have declared constructors because they lack a name. Instance initialization blocks provide the only way to execute multi-statement setup logic for an anonymous class instance.
