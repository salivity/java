Java Decorator Pattern: Dynamic Object Extension

The Decorator design pattern in Java provides a flexible alternative to subclassing by enabling developers to attach new behaviors to objects dynamically at runtime. This article examines the core mechanics of the Decorator pattern, demonstrates how it bypasses the rigid constraints of traditional class inheritance through composition, and provides a concise code example illustrating how to layer object capabilities on demand.

The Problem with Subclassing

Inheritance binds behavior to a class statically at compile time. When you need to support multiple variations and combinations of features, inheritance quickly leads to an issue known as class explosion. For example, if you have a base notification service and want to support combinations of SMS, Email, and Slack alerts, subclassing requires dedicated classes for every possible permutation (SmsNotification, EmailNotification, SmsAndSlackNotification, etc.). Adding new features exponentially increases the number of required classes and prevents objects from changing their behavior while the application is running.

How the Decorator Pattern Works

The Decorator pattern resolves this limitation by utilizing object composition instead of class inheritance. It relies on four primary structural elements:

  1. Component Interface: Defines the common contract for both the core object and the decorators.
  2. Concrete Component: Implements the component interface and provides the fundamental, baseline behavior.
  3. Base Decorator: Implements the component interface and maintains a reference to a wrapped Component instance.
  4. Concrete Decorators: Extend the base decorator to add specific state or behavior before or after delegating work to the wrapped component.

Because decorators implement the same interface as the object they wrap, they can substitute for the target transparently. When a client invokes a method on the decorator, the decorator executes its own custom logic and forwards the call to the encapsulated object. Decorators can be nested arbitrarily, creating a pipeline of runtime enhancements.

Implementation in Java

Consider a basic coffee order system where an order can be dynamically customized with various condiments:

// 1. Component Interface
public interface Coffee {
    double getCost();
    String getDescription();
}

// 2. Concrete Component
public class SimpleCoffee implements Coffee {
    @Override
    public double getCost() {
        return 2.0;
    }

    @Override
    public String getDescription() {
        return "Simple Coffee";
    }
}

// 3. Base Decorator
public abstract class CoffeeDecorator implements Coffee {
    protected final Coffee decoratedCoffee;

    public CoffeeDecorator(Coffee coffee) {
        this.decoratedCoffee = coffee;
    }

    @Override
    public double getCost() {
        return decoratedCoffee.getCost();
    }

    @Override
    public String getDescription() {
        return decoratedCoffee.getDescription();
    }
}

// 4. Concrete Decorators
public class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public double getCost() {
        return super.getCost() + 0.5;
    }

    @Override
    public String getDescription() {
        return super.getDescription() + ", Milk";
    }
}

public class SugarDecorator extends CoffeeDecorator {
    public SugarDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public double getCost() {
        return super.getCost() + 0.2;
    }

    @Override
    public String getDescription() {
        return super.getDescription() + ", Sugar";
    }
}

Dynamic Assembly at Runtime

Because decorators and components share the same type, components can be assembled on the fly based on configuration, user input, or business logic:

public class Main {
    public static void main(String[] args) {
        // Base object
        Coffee coffee = new SimpleCoffee();

        // Dynamically add Milk
        coffee = new MilkDecorator(coffee);

        // Dynamically add Sugar
        coffee = new SugarDecorator(coffee);

        System.out.println(coffee.getDescription()); // Simple Coffee, Milk, Sugar
        System.out.println("$" + coffee.getCost());       // $2.7
    }
}

This design adheres to the Open/Closed Principle: new functionality can be introduced by writing new concrete decorators without altering existing code or disrupting existing classes. Java's standard library uses this design extensively in its I/O system, such as wrapping a FileInputStream within a BufferedInputStream and a DataInputStream.
