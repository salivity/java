How ZGC Colored Pointers Work in 64-Bit Java

The Z Garbage Collector (ZGC) achieves sub-millisecond pause times in 64-bit Java runtimes largely through a technique known as colored pointers. By embedding garbage collection metadata directly into standard reference addresses rather than object headers, ZGC can track object states—such as reachability and relocation—in real time. This architecture allows the garbage collector to inspect and manage heap references concurrently with application execution, virtually eliminating stop-the-world pauses during marking and compaction phases.

The 64-Bit Pointer Structure

Standard 64-bit operating systems and processors do not utilize the full 64-bit address space for virtual memory, typically using only 48 bits. ZGC takes advantage of these unused bits by partitioning a standard 64-bit object reference into address bits and metadata bits.

In early ZGC implementations, the reference layout is structured as follows:

  • Bits 0–41 (42 bits): Represent the actual object offset, supporting heaps up to 4 TB (expanded to 44 bits / 16 TB in later releases).
  • Bits 42–45 (4 bits): The "color" or metadata bits used by the garbage collector.
  • Bits 46–63 (18 bits): Reserved or unused.

The Metadata Bits (Colors)

The four metadata bits define the exact state of the referenced object:

  • Marked0 and Marked1: These alternating bits track object liveness across consecutive garbage collection cycles. By alternating between Marked0 and Marked1 from one cycle to the next, ZGC immediately knows whether a reference was validated in the current cycle or leftover from the previous one, without needing to clear marks globally.
  • Remapped: This bit indicates whether the reference has been updated to point directly to the object's current physical location. If set, the pointer is guaranteed to be pointing to the up-to-date address, bypassing additional forwarding lookups.
  • Finalizable: This bit denotes that the referenced object is only reachable through finalizers.

At any given stage of garbage collection, only one marking state is considered valid (the "good" color), while others are considered "bad."

Load Barriers and Self-Healing

Colored pointers operate hand-in-hand with JIT-compiled load barriers. Whenever application code reads a reference from the heap (e.g., executing obj.field), the load barrier tests the color bits of the pointer:

  1. Fast Path: If the color bits match the current GC phase's expected state (a "good" color), the reference is immediately usable. This is a fast, single-instruction bitwise check that introduces virtually no overhead.
  2. Slow Path: If the color bits are "bad," the load barrier triggers a native handler. This occurs if an object has been marked for relocation or requires marking. The handler consults a forwarding table, finds the object's new address (or moves it on the spot if it has not been relocated yet), and updates the pointer's color to the current good state.

This mechanism enables self-healing: the first read fixes the reference locally and updates the color bits, ensuring subsequent reads take the fast path.

Virtual Memory Mapping

Because the processor's memory management unit (MMU) would normally treat different color bit combinations as entirely distinct virtual memory addresses, ZGC employs multi-mapping at the operating system level. Using OS-level page mapping (such as mmap on Linux), ZGC maps the Marked0, Marked1, and Remapped address ranges to the exact same physical memory pages. As a result, dereferencing a pointer with any valid color resolves to the correct physical object without requiring the runtime to mask out color bits prior to memory access.
