Java Value Objects and the Identity Problem

In Java architecture, standard objects carry a distinct identity determined by their memory address, meaning two separate instances with identical state are treated as different entities. This article explores how this reference-based identity model introduces subtle bugs, aliasing issues, and domain inaccuracies, and details how the implementation of Value Objects resolves these challenges by replacing reference identity with attribute-based equality and immutability.

The Identity Problem in Java Architecture

By default, every object instantiated on the Java Virtual Machine (JVM) receives a unique object identity. This identity is inherently tied to the object's reference—its physical location in memory—rather than the data it encapsulates. Operators such as == evaluate whether two references point to the exact same memory address, not whether the contents of those references represent the same logical concept.

This reference identity becomes problematic when modeling domain concepts that do not naturally possess an inherent lifecycle or distinguishing identifier. In enterprise applications, treating every piece of data as an identity-bearing entity introduces several critical architectural challenges:

  • Aliasing Bugs: When multiple components hold a reference to the same mutable object, one component can alter the internal state without the knowledge of the others.
  • False Inequality: Two distinct objects representing the exact same conceptual data (such as two separate instances representing an amount of USD 50) fail equality checks unless explicitly handled via custom methods.
  • State Drift: Over time, objects intended to represent fixed values can undergo unexpected state changes, leading to unpredictable application behavior and complex debugging cycles.

Domain Misalignment: Entities vs. Values

In Domain-Driven Design (DDD) and robust object-oriented architecture, objects generally fall into two categories: Entities and Value Objects.

Entities possess an intrinsic identity that persists across state changes and over time. For example, a User or an Order typically possesses a unique ID (such as a UUID or database primary key). Even if every other attribute of a User changes, the entity remains the same unique user.

Conversely, many domain concepts are defined entirely by what they are, not by an arbitrary ID. Examples include:

  • Monetary values (Money: amount and currency)
  • Geometric coordinates (Point: x and y)
  • Communication endpoints (EmailAddress: string value)
  • Date and time ranges (DateRange: start and end dates)

When developers model these concepts as standard Java objects with identity, they misrepresent the domain. A $10 bill in a bank account calculation does not need a unique serial number or memory pointer; its identity is the combination of the number 10 and the currency USD.

How Value Objects Eliminate the Identity Problem

Value Objects eliminate the identity problem by consciously abandoning reference-based identity in favor of structural identity. This is achieved through three core design principles:

1. Equality by Value (Equivalence)

Value Objects override equals() and hashCode() so that two distinct instances containing identical data evaluate as equal. The framework or domain logic no longer cares where the object resides in memory, only what data it holds.

Money priceA = new Money(new BigDecimal("19.99"), Currency.USD);
Money priceB = new Money(new BigDecimal("19.99"), Currency.USD);

// Evaluates to true because identity is defined by attributes
priceA.equals(priceB);

2. Immutability

A Value Object is immutable once constructed. Since it cannot be modified, references can be shared freely across threads and services without defensive copying and without risk of unintended side-effects caused by aliasing. If the value must change, a new instance is created instead of mutating the existing one.

3. Self-Validation

Because a Value Object represents a specific value rather than a generic data container, its constructor enforces domain invariants. For example, an EmailAddress Value Object ensures it cannot be instantiated with an invalid format, guaranteeing that every instance that exists is inherently valid.

Value Objects in Modern Java

Java has evolved to provide first-class support for Value Objects:

  • Java Records (Java 14+): The record keyword provides a concise syntax for defining immutable data carriers. Records automatically generate value-based implementations of equals(), hashCode(), and toString(), substantially reducing the boilerplate required to discard reference identity.
  • Project Valhalla: While records eliminate the conceptual identity problem at the language level, the JVM still treats them as identity-bearing heap objects under the hood. Project Valhalla aims to complete this architectural shift by introducing primitive-like value classes (value class). These will allow the JVM to flatten objects in memory and discard object headers, eliminating identity at both the conceptual domain level and the physical hardware execution level.
