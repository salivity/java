G1 Garbage Collector Region Allocation in Java

Java's Garbage-First (G1) collector departs from traditional memory models by partitioning the Java heap into a large set of uniform, contiguous memory blocks called regions, rather than maintaining physically fixed generation spaces. This article breaks down how G1 determines region sizes, dynamically assigns roles to these regions, handles standard object allocations via Thread-Local Allocation Buffers, accommodates large data through humongous regions, and tracks cross-region references for predictable pause times.

Heap Partitioning and Region Sizing

Instead of dividing the heap into contiguous, physical segments for the Eden, Survivor, and Tenured generations, G1 splits the total available heap into approximately 2,048 equal-sized memory blocks.

The size of an individual region is determined at JVM startup based on the initial and maximum heap size (-Xms and -Xmx). A region's size is always a power of two, ranging from 1 MB to 32 MB (e.g., 1 MB, 2 MB, 4 MB, 8 MB, 16 MB, or 32 MB). While the JVM typically calculates this automatically to hit the target of roughly 2,048 regions, administrators can manually override this value using the -XX:G1HeapRegionSize flag.

Dynamic Generational Roles

In G1, generational boundaries are purely logical. Any region can be assigned a specific generational role at runtime and reassigned after its contents are reclaimed. At any given moment, a region belongs to one of the following categories:

  • Free: Unallocated regions available to be drafted into any generation role.
  • Eden: Regions allocated for newly created objects.
  • Survivor: Regions containing objects that have survived one or more collection cycles.
  • Old (Tenured): Regions holding long-lived objects that have exceeded the tenure aging threshold.
  • Humongous: Regions reserved specifically for objects larger than half of a standard region size.

Because these roles are non-contiguous, the G1 collector can freely reassign an evacuated Eden or Old region back to the free list, where it can later be reused as needed by any generation.

Thread-Local Allocation Buffers (TLABs)

For standard objects, G1 optimizes allocation throughput by minimizing synchronization bottlenecks across threads. It accomplishes this using Thread-Local Allocation Buffers (TLABs):

  1. Region Assignment: When a mutator thread requires space to create new objects, it requests a portion of an active Eden region.
  2. Buffer Reservation: The JVM assigns a dedicated TLAB inside an Eden region to that specific thread.
  3. Bump-the-Pointer: Within its assigned TLAB, a thread allocates memory using a fast "bump-the-pointer" technique—simply updating a pointer to the next free byte without acquiring global heap locks.
  4. Buffer Exhaustion: Once a thread fills its TLAB, it synchronizes with the heap manager to acquire a new TLAB from the current Eden region or prompts the allocation of a fresh Eden region from the global free list.

Humongous Allocations

Objects that exceed 50% of the configured region size are classified as "Humongous" objects. These allocations bypass the standard TLAB mechanism because placing them inside standard Eden regions would cause excessive fragmentation and trigger premature garbage collection cycles.

  • Contiguous Sequences: If an object is larger than a single region, G1 allocates a contiguous sequence of regions to hold it. The first region is marked as "StartsHumongous," and all subsequent regions in the sequence are marked as "ContinuesHumongous."
  • Immediate Placement: Humongous regions are allocated directly into the Old generation, skipping Eden and Survivor stages entirely.
  • Reclamation: Humongous objects are evaluated during cleanup pauses and concurrent mark cycles; if they are no longer referenced, they can be eagerly reclaimed to prevent the heap from running out of contiguous blocks.

Inter-Region Tracking with Remembered Sets

A critical component of G1's region architecture is the ability to collect individual regions without scanning the entire heap. G1 achieves this using Remembered Sets (RSets).

Each region has an associated RSet that tracks which external memory cards (512-byte segments of other regions) contain references pointing into that region. When G1 collects a specific set of regions (the Collection Set, or CSet), it uses these RSets to identify all incoming references from outside the CSet. This allows G1 to evacuate and compact specific regions independently, keeping stop-the-world pause times bounded and predictable.
