Maven Plugins: How to Bind Goals to Phases

This article explains the fundamentals of Apache Maven plugins and how they drive the Java build process. You will learn the relationship between build lifecycles, phases, and plugin goals, as well as how to explicitly bind plugin execution goals to specific build phases using the pom.xml configuration file to automate custom build tasks.

What Are Maven Plugins?

In Apache Maven, almost all build actions are executed by plugins. Maven itself is essentially an execution framework; it manages project dependencies and coordinates lifecycles, but it delegates the actual work—such as compiling Java code, running unit tests, creating JAR files, and deploying artifacts—to plugins.

A Maven plugin contains one or more goals. A goal represents a specific, granular task that performs an action on the project. Goals are referenced using the syntax plugin-prefix:goal-name (for example, compiler:compile or surefire:test).

Maven Lifecycles and Phases

To understand goal binding, you must first understand the Maven build lifecycle. Maven defines three built-in lifecycles:

  • clean: Handles project cleaning and removing previous build outputs.
  • default (or build): Manages the entire deployment and build process.
  • site: Handles the generation of project documentation and reports.

Each lifecycle consists of an ordered sequence of phases. For example, the default lifecycle includes sequential phases such as:

  1. validate
  2. compile
  3. test
  4. package
  5. verify
  6. install
  7. deploy

When you run a command like mvn package, Maven executes every phase up to and including package in the defined order.

How Goal Binding Works

Phases do not perform work on their own; instead, Maven executes the plugin goals that are bound to those phases.

1. Default Bindings

Depending on the project's <packaging> type (e.g., jar, war, pom), Maven provides default bindings. For example, in a project with jar packaging:

  • The compiler:compile goal is automatically bound to the compile phase.
  • The surefire:test goal is automatically bound to the test phase.
  • The jar:jar goal is automatically bound to the package phase.

2. Custom Goal Binding

When you introduce an external plugin or want an existing plugin to run at a specific point in the build, you explicitly bind the goal to a phase inside your pom.xml file using the <executions> block.

Here is an example configuring the maven-source-plugin to generate a source code archive during the package phase:

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.maven.plugins</groupId>
            <artifactId>maven-source-plugin</artifactId>
            <version>3.3.0</version>
            <executions>
                <execution>
                    <id>attach-sources</id>
                    <phase>package</phase>
                    <goals>
                        <goal>jar-no-fork</goal>
                    </goals>
                </execution>
            </executions>
        </plugin>
    </plugins>
</build>

In this configuration:

  • <execution>: Defines an isolated run configuration for the plugin.
  • <id>: A unique identifier for the execution context.
  • <phase>: Specifies which build phase triggers this execution. If omitted, the goal will run during its default phase as defined by the plugin author.
  • <goals>: Lists the specific plugin goals to execute when the specified phase is reached.

Execution Order Within a Phase

If multiple goals are bound to the same build phase, Maven executes them in the order they appear in the pom.xml. Default goals defined by Maven packaging are executed prior to custom-configured plugins unless overridden. This predictable execution pipeline allows developers to construct fully automated, consistent CI/CD workflows tailored to any Java application.
