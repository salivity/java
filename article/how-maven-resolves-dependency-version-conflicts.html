How Maven Resolves Dependency Version Conflicts

In modern Java development, managing transitive dependencies can quickly become problematic when multiple libraries require conflicting versions of the same artifact. This article explains how Apache Maven resolves these dependency conflicts using its core "nearest-wins" mediation strategy, details the tie-breaking rules based on declaration order, and outlines the precise mechanisms—specifically direct overrides, dependency management, and exclusions—that developers can use to enforce predictable builds.

The Core Rule: "Nearest Wins" (Dependency Depth)

Maven’s primary mechanism for resolving version conflicts is Dependency Mediation. Under this rule, Maven selects the version of a dependency that is closest to your project root in the dependency tree.

Consider this dependency hierarchy:

  • Your Project
    • Depends on Library A (Depth 1)
      • Library A depends on Shared-Lib 1.0 (Depth 2)
    • Depends on Library B (Depth 1)
      • Library B depends on Library C (Depth 2)
        • Library C depends on Shared-Lib 2.0 (Depth 3)

In this scenario, Maven selects Shared-Lib 1.0. Because it sits at Depth 2 via Library A, it is "nearer" to your root project than Shared-Lib 2.0, which sits at Depth 3. Maven does not compare release dates or semantic version numbers; it relies strictly on structural depth.

Tie-Breaking: First Declared Wins

When two conflicting versions appear at the exact same depth in the dependency tree, Maven uses the First Declared rule.

Consider this case:

  • Your Project
    • Depends on Library X (Depth 1)
      • Library X depends on Common-Util 1.5 (Depth 2)
    • Depends on Library Y (Depth 1)
      • Library Y depends on Common-Util 2.0 (Depth 2)

Both versions of Common-Util are at Depth 2. Maven resolves this by checking the order in your project's pom.xml. If <dependency> for Library X appears before Library Y, Maven chooses Common-Util 1.5. Swapping their order in the POM file will cause Maven to choose Common-Util 2.0.

Direct Dependencies Always Take Precedence

A direct dependency explicitly declared in your project's pom.xml resides at Depth 1. Because Depth 1 is closer to your project than any transitive dependency (Depth 2 or greater), a direct declaration will always override any transitive versions, regardless of what other libraries request.

<dependencies>
    <!-- Force this specific version project-wide -->
    <dependency>
        <groupId>com.example</groupId>
        <artifactId>shared-lib</artifactId>
        <version>2.5.0</version>
    </dependency>
</dependencies>

Overriding Resolution with <dependencyManagement>

In multi-module projects or enterprise applications, relying on depth or direct declarations can become brittle. The <dependencyManagement> block provides centralized version control.

When an artifact is specified inside <dependencyManagement>, Maven forces that specific version to be used whenever the artifact is encountered anywhere in the dependency tree—whether direct or transitive—unless explicitly overridden in a child module.

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.slf4j</groupId>
            <artifactId>slf4j-api</artifactId>
            <version>2.0.9</version>
        </dependency>
    </dependencies>
</dependencyManagement>

This bypasses the nearest-wins rule entirely for slf4j-api, ensuring version 2.0.9 is selected across all modules and transitive imports.

Explicit Exclusion of Transitive Dependencies

If a library brings in an incompatible or buggy transitive dependency, you can prune that specific branch of the dependency tree using <exclusions>.

<dependency>
    <groupId>com.example</groupId>
    <artifactId>legacy-library</artifactId>
    <version>1.0.0</version>
    <exclusions>
        <exclusion>
            <groupId>commons-logging</groupId>
            <artifactId>commons-logging</artifactId>
        </exclusion>
    </exclusions>
</dependency>

By excluding the artifact, you remove that path from the depth calculation, allowing Maven to resolve another version from a different branch or fall back to a direct declaration.

Diagnosing Conflicts

To view how Maven is resolving dependencies and identify where conflicts arise, run the following command in your terminal:

mvn dependency:tree

To see which specific versions were omitted or replaced due to conflict resolution, add the verbose flag:

mvn dependency:tree -Dverbose

This output displays the entire graph, annotating omitted versions with comments such as (omitted for conflict with ...) or (omitted for duplicate), allowing you to verify exactly which rule caused Maven to select a given artifact.
