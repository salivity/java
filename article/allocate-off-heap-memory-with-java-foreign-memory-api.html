Allocate Off-Heap Memory with Java Foreign Memory API

The Java Foreign Function & Memory (FFM) API, finalized in Java 22 under package java.lang.foreign, provides a safe and efficient way to allocate and manage native off-heap memory outside the garbage-collected Java heap. By replacing the error-prone and unsupported sun.misc.Unsafe and standard JNI workflows, the FFM API introduces two core abstractions—MemorySegment and Arena—to govern the allocation, spatial boundaries, and deterministic release of native memory resources.

Core Abstractions: MemorySegment and Arena

A MemorySegment models a contiguous region of memory, which can be either on-heap or off-heap. It guarantees spatial safety by enforcing bounds checks on every read and write operation, preventing buffer overflows.

An Arena governs the lifecycle and temporal safety of one or more native memory segments. When an arena is closed, all native segments allocated within that arena are invalidated and their underlying native memory is immediately released back to the operating system. Any subsequent access to those segments throws an IllegalStateException, completely preventing use-after-free bugs.

Allocating Native Off-Heap Memory

Native allocation is performed using factory methods on an Arena instance. An arena provides methods such as allocate() and allocateFrom() to reserve off-heap bytes:

try (Arena arena = Arena.ofConfined()) {
    // Allocate 1024 bytes of native off-heap memory
    MemorySegment segment = arena.allocate(1024);

    // Allocate and initialize off-heap memory with primitive values
    MemorySegment intSegment = arena.allocate(java.lang.foreign.ValueLayout.JAVA_INT, 42);

    // Read data safely
    int value = intSegment.get(java.lang.foreign.ValueLayout.JAVA_INT, 0);
}

Behind the scenes, the native arena delegates to platform-specific system calls (such as malloc or virtual memory allocation) to carve out address space outside the JVM heap.

Releasing Native Memory

Deallocation depends entirely on the type of Arena chosen. The API provides four distinct arena varieties to support different concurrency and lifecycle requirements:

  1. Confined Arena (Arena.ofConfined()): Designed for single-threaded use. It provides deterministic deallocation when closed. Allocation, access, and closure must all occur within the thread that created the arena.

  2. Shared Arena (Arena.ofShared()): Designed for multi-threaded environments. Multiple threads can concurrently access segments and allocate memory. When arena.close() is called, the runtime uses a safe coordination mechanism (handshake) across threads to ensure no thread is actively reading or writing to the memory before releasing the backing native address.

  3. Automatic Arena (Arena.ofAuto()): Provides non-deterministic, garbage-collected deallocation. It cannot be explicitly closed. Instead, the runtime associates a Cleaner with the arena; when the MemorySegment and the arena are no longer reachable on the Java heap, the native memory is freed automatically.

  4. Global Arena (Arena.global()): An unbounded, process-wide arena that is never closed. Memory allocated via the global arena lives for the entire duration of the JVM process.

Deterministic Lifecycle with try-with-resources

Because Arena extends AutoCloseable, explicit arenas should be paired with a standard Java try-with-resources block. When execution leaves the block, Arena.close() is invoked automatically. This guarantees that native memory is released immediately without waiting for garbage collection cycles, eliminating memory leaks while maintaining complete memory safety.
