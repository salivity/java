System.identityHashCode When Overriding Equals in Java

This article explains the purpose and practical utility of System.identityHashCode() in Java when a class overrides equals() and hashCode(). It outlines how the method bypasses overridden state-based logic to return an object's original, identity-based hash code. You will learn why this distinction is critical for object identity tracking, deadlock prevention, debugging, and maintaining distinct instance-level operations even when objects are logically equivalent.

The Contract Between equals() and hashCode()

In Java, the base Object class defines equals() and hashCode() based on reference identity. Two references are equal only if they point to the exact same memory location, and hashCode() returns an integer tied to that identity.

When you override equals() to compare logical state rather than object references, you must also override hashCode() to maintain the general contract: two objects that are equal according to equals() must produce the same hash code. Once this happens, the original identity information generated by the default Object.hashCode() implementation is masked.

What System.identityHashCode Does

System.identityHashCode(Object x) invokes the default hash code implementation provided by java.lang.Object, completely bypassing any overridden hashCode() method in the object's class hierarchy.

If the object is null, it returns 0. For any non-null instance, it returns the hash code that would have been produced had the class never overridden hashCode(), regardless of its current state or its overridden equals() logic.

Key Roles When equals() Is Overridden

1. Identity-Based Collections and Tracking

When equals() evaluates logical equality, data structures like HashMap and HashSet group objects by their content. However, certain frameworks and algorithms must track distinct object instances regardless of whether their content is identical.

For example, java.util.IdentityHashMap relies on reference equality (==) and identity hash codes to detect duplicate references, circular dependencies in object graph serialization, or distinct cache handles. System.identityHashCode() provides the hash value required for these operations without relying on the class's overridden hashCode().

2. Tie-Breaking in Concurrency

A classic concurrency challenge involves locking multiple objects in a consistent order to prevent deadlocks. If two objects must be locked simultaneously, threads must acquire them in a globally predictable sequence.

When objects override equals() and hashCode(), their hash codes might collide or change if the object is mutable. System.identityHashCode() provides a stable, per-instance integer across the lifecycle of the object, making it ideal for deterministic tie-breaking logic:

int hash1 = System.identityHashCode(resourceA);
int hash2 = System.identityHashCode(resourceB);

if (hash1 < hash2) {
    synchronized (resourceA) {
        synchronized (resourceB) { /* ... */ }
    }
} else if (hash1 > hash2) {
    synchronized (resourceB) {
        synchronized (resourceA) { /* ... */ }
    }
} else {
    // Rare identity hash collision: resolve with a secondary tie-breaker lock
}

3. Debugging and Logging Distinct Instances

When two objects have identical state, their overridden toString(), equals(), and hashCode() methods yield identical representations. This makes distinguishing between two separate instances difficult during debugging or log analysis. Calling System.identityHashCode() reconstructs the default ClassName@HexHashCode representation, allowing developers to verify whether two operations are modifying the same instance or distinct instances with identical fields.
