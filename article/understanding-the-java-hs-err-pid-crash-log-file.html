Understanding the Java hs_err_pid Crash Log File

When the Java Virtual Machine (JVM) terminates abruptly due to a fatal, unrecoverable error, it writes a post-mortem diagnostic log named hs_err_pid<pid>.log into the working directory or temporary storage. This article provides a comprehensive overview of the essential diagnostic data captured within this file. By learning what data the JVM records during a crash—such as the fatal signal, execution stack, register values, memory layout, and system state—engineers can rapidly isolate the root cause, whether it stems from native code (JNI), third-party drivers, hardware faults, or JVM bugs.

1. Crash Summary and Fatal Event

The top of the file provides the immediate context of the failure, allowing you to quickly identify why the process died.

  • Cause of Termination: The operating system signal or exception that triggered the crash, such as SIGSEGV (segmentation violation) on Linux or EXCEPTION_ACCESS_VIOLATION on Windows.
  • Crashing Thread Identification: The native thread ID and name of the thread that encountered the error.
  • Problematic Frame: The exact function and dynamic library where the execution halted (for example, C [libjvm.so+0x123456] or a call inside a native JNI library).

2. Current Thread Context

This section contains granular low-level debugging details for the thread that caused the crash.

  • Registers: The CPU register dump at the moment of failure (such as RAX, RBX, RIP, and RSP on x86_64 architectures), which reveals the memory addresses and values being manipulated.
  • Native and Java Stack Traces: The call sequence leading up to the crash. If the crash happened in native code, it prints the C/C++ call stack. Below that, it displays the corresponding Java stack trace, showing which Java method was invoking the native operation.
  • Stack Memory Dump: A raw hex dump of the memory surrounding the stack pointer, useful for identifying corrupted pointer references or stack overflows.

3. Virtual Machine (VM) State

The log records the internal condition of the JVM runtime at the point of failure.

  • VM Operation and Safepoint: Indicates whether the JVM was stopped at a global safepoint or running a specific operation, such as a full Garbage Collection or thread dump.
  • Heap Information: The state and memory utilization of every JVM memory pool, including the Eden, Survivor, and Tenured (Old) generations, as well as the Metaspace and CodeCache.
  • Active Compiler Tasks: Details on whether the Just-In-Time (JIT) compiler (C1 or C2) was actively compiling a method when the crash occurred, which helps detect JIT compiler bugs.
  • VM Arguments and Flags: All explicit command-line flags (-Xmx, -XX:+UseG1GC, etc.) and system properties configured for the JVM instance.

4. Other Threads

The log lists all other running threads in the process, providing their native thread identifiers, thread states (e.g., _thread_in_native, _thread_blocked, _thread_in_Java), and execution status. This helps identify whether a deadlocked thread or high thread contention contributed to the crash.

5. Loaded Dynamic Libraries

A complete list of all dynamic libraries (.so or .dll files) loaded into the process space, along with their virtual memory address ranges. This helps identify third-party native libraries, database drivers, or profiling agents that may have loaded unexpected versions or conflicted with the JVM runtime.

6. System and Environmental Data

The final section records the physical host environment to help diagnose resource starvation or OS-level incompatibilities.

  • Operating System: Kernel version, OS distribution, and glibc release.
  • CPU Specifications: Processor model, clock speed, core count, and supported instruction sets (such as AVX or SSE).
  • System Memory: Total physical RAM, free memory, and available swap space at the time of the event.
  • Resource Limits (ulimit): Process-level constraints including file descriptor limits, stack size limits, and maximum user processes.
  • Environment Variables: Selected shell and application environment variables that were set when the JVM launched.
