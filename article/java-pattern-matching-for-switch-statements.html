Java Pattern Matching for Switch Statements

Pattern matching for switch statements fundamentally improves Java control flow by allowing developers to test complex data structures, inspect types, and extract components directly within switch branches. Finalized in Java 21, this feature replaces verbose, error-prone chains of if-else statements and manual type casting with a declarative, highly readable syntax. By combining type patterns, guarded conditions, and compile-time exhaustiveness checking, it brings modern, expressive control flow patterns to the Java language.

Elimination of Boilerplate Casting

Traditionally, branching based on object types required checking types with instanceof and then explicitly casting the variable in a subsequent statement. Pattern matching for switch combines testing and extraction into a single, unified step:

switch (obj) {
    case Integer i -> System.out.println("Integer: " + (i * 2));
    case String s  -> System.out.println("String of length: " + s.length());
    default        -> System.out.println("Unknown type");
}

The switch matches the target against the type pattern and immediately binds it to a typed pattern variable, eliminating redundant casting and reducing the surface area for runtime errors.

Enhanced Type Safety and Exhaustiveness

When applied to sealed classes, sealed interfaces, or enums, pattern matching enforces exhaustiveness checking at compile time. The compiler evaluates all permissible subclasses or enum constants to guarantee every potential case is handled.

If a new subclass is added to a sealed hierarchy, the compiler immediately flags any switch expression missing the new variant, preventing missed edge cases and runtime fallbacks to generic defaults.

Refined Logic with Guarded Patterns

Control flow logic often requires matching a type and verifying a state simultaneously. Pattern matching for switch introduces guarded patterns using the when clause, allowing conditional checks alongside type patterns:

switch (response) {
    case HttpResponse r when r.statusCode() == 200 -> handleSuccess(r);
    case HttpResponse r when r.statusCode() >= 400 -> handleError(r);
    case HttpResponse r -> handleOther(r);
    default -> throw new IllegalStateException();
}

This prevents the nesting of conditional logic inside case blocks, keeping execution paths flat, isolated, and readable.

Direct Null Handling

Historically, passing a null reference to a switch statement resulted in an immediate NullPointerException. Pattern matching for switch allows null to be treated as an explicit case:

switch (input) {
    case null      -> System.out.println("Received null input");
    case String s  -> System.out.println("Valid: " + s);
    default        -> System.out.println("Other object");
}

This removes the need for defensive null checks prior to evaluating the switch, consolidating all branching decisions into one construct.
