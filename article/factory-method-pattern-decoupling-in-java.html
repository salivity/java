Factory Method Pattern: Decoupling in Java

The Factory Method pattern is a creational design pattern that provides an interface for creating objects in a superclass while allowing subclasses to alter the type of objects that will be created. This article explores the architecture of the Factory Method pattern in Java, demonstrating how it replaces direct object construction with polymorphic method calls to decouple object instantiation from business logic.

Understanding the Factory Method Pattern

In standard object-oriented programming, instantiating an object using the new operator binds the calling class directly to a concrete implementation. This tight coupling makes code difficult to maintain, test, and extend.

The Factory Method pattern resolves this issue by defining an abstract method—the "factory method"—inside a creator class. Instead of calling a constructor directly, client logic delegates the instantiation process to this specialized method. Subclasses then override this method to return specific instances of a common interface.

The pattern relies on four primary components:

  1. Product Interface: Defines the common interface for objects the factory method creates.
  2. Concrete Products: Distinct implementations of the Product interface.
  3. Creator: An abstract class or interface declaring the factory method, which returns an object of type Product. It often contains core business logic that relies on the Product interface.
  4. Concrete Creators: Subclasses that override the factory method to return an instance of a Concrete Product.

How It Decouples Instantiation from Usage

The core mechanism of decoupling in the Factory Method pattern is the inversion of control regarding object creation.

Without the pattern, high-level business logic must know about every concrete class it needs to instantiate:

// Tightly coupled approach
public class OrderProcessor {
    public void processOrder(String paymentType) {
        if (paymentType.equals("CREDIT")) {
            CreditCardPayment payment = new CreditCardPayment();
            payment.pay();
        } else if (paymentType.equals("PAYPAL")) {
            PayPalPayment payment = new PayPalPayment();
            payment.pay();
        }
    }
}

In the decoupled approach, high-level code interacts purely with abstractions. The creator class executes high-level workflows using the generic Payment interface, completely unaware of whether the concrete object is a credit card, PayPal, or crypto payment.

Implementation in Java

Here is how the pattern is implemented in Java:

1. Product Interface and Concrete Products

public interface Notification {
    void notifyUser();
}

public class EmailNotification implements Notification {
    @Override
    public void notifyUser() {
        System.out.println("Sending an email notification.");
    }
}

public class SMSNotification implements Notification {
    @Override
    public void notifyUser() {
        System.out.println("Sending an SMS notification.");
    }
}

2. Creator and Concrete Creators

public abstract class NotificationService {
    // Core business logic relies on the interface, not concrete classes
    public void sendAlert() {
        Notification notification = createNotification();
        notification.notifyUser();
    }

    // The Factory Method
    protected abstract Notification createNotification();
}

public class EmailNotificationService extends NotificationService {
    @Override
    protected Notification createNotification() {
        return new EmailNotification();
    }
}

public class SMSNotificationService extends NotificationService {
    @Override
    protected Notification createNotification() {
        return new SMSNotification();
    }
}

3. Client Execution

public class Application {
    public static void main(String[] args) {
        NotificationService service;

        // Configuration determines the concrete creator
        boolean preferSMS = true; 
        if (preferSMS) {
            service = new SMSNotificationService();
        } else {
            service = new EmailNotificationService();
        }

        // Client code uses the abstraction; instantiation details are hidden
        service.sendAlert();
    }
}

Architectural Benefits

  • Adherence to the Open/Closed Principle: New product types (such as push notifications) can be introduced into the system by creating new subclasses without modifying existing client code.
  • Adherence to the Single Responsibility Principle: The code responsible for product creation is isolated to specific classes, separating construction concerns from operational logic.
  • Simplified Unit Testing: Because creation is encapsulated within methods rather than hardcoded constructors, dependencies can easily be mocked or substituted during testing.
