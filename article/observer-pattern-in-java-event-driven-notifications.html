Observer Pattern in Java: Event-Driven Notifications

This article explains the Observer design pattern and its role in building responsive, decoupled Java applications. You will learn the core architectural components of the pattern, understand the mechanics of coordinating event-driven notifications between independent Java classes, and review a clean code implementation using modern Java practices.

What is the Observer Pattern?

The Observer pattern is a behavioral design pattern that defines a one-to-many dependency between objects. When the core object—known as the Subject or Observable—changes its state, all registered dependents—known as Observers or Listeners—are automatically notified and updated.

This pattern is fundamental to event-driven programming because it decouples the object producing data or events from the objects that consume that data. The Subject does not need to know the concrete classes of its Observers, their internal logic, or how many Observers exist at runtime.

Key Components of the Observer Pattern

Coordinating event notifications requires four primary roles:

  1. Subject Interface: Declares methods for attaching, detaching, and notifying observers.
  2. Concrete Subject: Maintains the state of interest and stores references to attached observers. When its internal state changes, it invokes the notification method to iterate through all active observers.
  3. Observer Interface: Defines an update contract (typically an update() method) that the Subject calls when dispatching notifications.
  4. Concrete Observers: Implement the Observer interface and define custom responses to the incoming updates.

Implementing the Pattern in Java

To avoid coupling concrete classes, define clear interfaces for both the Subject and the Observer.

1. Define the Interfaces

import java.util.List;

public interface Observer {
    void update(String eventData);
}

public interface Subject {
    void registerObserver(Observer observer);
    void removeObserver(Observer observer);
    void notifyObservers();
}

2. Create the Concrete Subject

The concrete subject maintains an internal collection of observers and notifies them whenever relevant state updates occur.

import java.util.ArrayList;
import java.util.List;

public class EventManager implements Subject {
    private final List<Observer> observers = new ArrayList<>();
    private String latestEvent;

    @Override
    public void registerObserver(Observer observer) {
        observers.add(observer);
    }

    @Override
    public void removeObserver(Observer observer) {
        observers.remove(observer);
    }

    @Override
    public void notifyObservers() {
        for (Observer observer : observers) {
            observer.update(latestEvent);
        }
    }

    public void setEvent(String newEvent) {
        this.latestEvent = newEvent;
        notifyObservers();
    }
}

3. Implement Concrete Observers

Each observer implements the specific action required when receiving an update.

public class LoggingService implements Observer {
    @Override
    public void update(String eventData) {
        System.out.println("LoggingService received: " + eventData);
    }
}

public class AlertService implements Observer {
    @Override
    public void update(String eventData) {
        System.out.println("AlertService triggered for: " + eventData);
    }
}

4. Coordinate Notifications

When wired together, changes in the EventManager automatically propagate to all registered services without hardcoded inter-class dependencies:

public class Main {
    public static void main(String[] args) {
        EventManager publisher = new EventManager();

        Observer logger = new LoggingService();
        Observer alerter = new AlertService();

        publisher.registerObserver(logger);
        publisher.registerObserver(alerter);

        // State change triggers notifications across both services
        publisher.setEvent("User Login Failed");

        // Observers can dynamically detach at runtime
        publisher.removeObserver(alerter);
        publisher.setEvent("System Maintenance Started");
    }
}

Built-in Java Alternatives: PropertyChangeListener

While Java previously provided java.util.Observer and java.util.Observable, these were deprecated in Java 9 due to limited flexibility and thread-safety concerns.

For standard desktop and enterprise applications, the standard Java API provides the java.beans.PropertyChangeSupport and java.beans.PropertyChangeListener classes. These classes encapsulate the registration and notification mechanics, allowing Java classes to broadcast state property changes without manually maintaining subscriber lists:

import java.beans.PropertyChangeListener;
import java.beans.PropertyChangeSupport;

public class SystemStatus {
    private String status;
    private final PropertyChangeSupport support = new PropertyChangeSupport(this);

    public void addPropertyChangeListener(PropertyChangeListener listener) {
        support.addPropertyChangeListener(listener);
    }

    public void setStatus(String newStatus) {
        String oldStatus = this.status;
        this.status = newStatus;
        support.firePropertyChange("status", oldStatus, newStatus);
    }
}

Benefits of the Observer Pattern in Java

  • Loose Coupling: Subjects and observers share only interface definitions, meaning modifications to one class do not break another.
  • Dynamic Subscriptions: Observers can be added, removed, or swapped at runtime based on application context.
  • Broadcast Communication: A single event can effortlessly notify any number of downstream consumers simultaneously.
  • Single Responsibility Principle: The data-holding class focuses purely on state management, while notification handling and downstream logic remain encapsulated within distinct observer components.
