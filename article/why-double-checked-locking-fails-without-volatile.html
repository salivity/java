Why Double-Checked Locking Fails Without Volatile

The double-checked locking idiom is a software design pattern intended to reduce the overhead of acquiring a lock by testing the locking criterion before acquiring the lock. In Java, this pattern is commonly used for lazy initialization of singleton instances. However, without the use of the volatile keyword, the idiom is fundamentally flawed and thread-unsafe because the Java Memory Model permits instruction reordering. This optimization allows a thread to observe a non-null reference to an object before that object has finished being constructed, leading to severe concurrency bugs.

To understand why the pattern fails, consider its typical implementation:

public class Singleton {
    private static Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) { // First check (no lock)
            synchronized (Singleton.class) {
                if (instance == null) { // Second check (with lock)
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

The issue lies entirely in the line instance = new Singleton();. At the bytecode and machine instruction levels, instantiating an object is not an atomic operation. Constructing an object generally involves three distinct steps:

  1. Allocate memory for the Singleton object.
  2. Execute the constructor to initialize the fields within the allocated memory.
  3. Assign the memory address of the allocated block to the instance variable.

Under the Java Memory Model, compilers and hardware processors are free to reorder instructions to optimize performance, provided that the reordering does not alter the execution result within a single thread. Because assigning the reference (step 3) does not depend on the constructor finishing its execution (step 2), the runtime environment may reorder the execution sequence to 1, then 3, then 2.

When this reordering occurs, a race condition emerges across multiple threads:

  1. Thread A enters getInstance(), finds instance is null, acquires the monitor lock, and proceeds to instantiate the object.
  2. The compiler or CPU reorders the steps, executing step 1 (allocation) and step 3 (assigning the pointer to instance). At this precise moment, instance is no longer null, but step 2 (the constructor) has not yet executed.
  3. Thread B calls getInstance(). It performs the first check: if (instance == null).
  4. Because Thread A has already written the memory address to instance, Thread B sees that instance is not null.
  5. Thread B skips the synchronized block entirely and immediately returns instance.
  6. Thread B attempts to read properties or call methods on this partially initialized object. Since the constructor has not finished running, Thread B encounters uninitialized data, default values, or unexpected NullPointerException errors.

Declaring the reference field as private static volatile Singleton instance; resolves this defect. Under the updated Java Memory Model introduced in Java 5, reads and writes to a volatile variable establish a "happens-before" relationship.

The volatile modifier introduces memory barriers that prevent the reordering of the write to the reference variable with the preceding initialization writes. Consequently, it guarantees that all constructor actions complete before the reference becomes visible to other threads, ensuring that any thread observing a non-null reference always sees a fully constructed object.
