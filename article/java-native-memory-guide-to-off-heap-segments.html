Java Native Memory: Guide to Off-Heap Segments

While developers typically focus on the Java heap, a significant portion of a Java application's overall memory footprint resides off-heap in native memory managed directly by the operating system and the Java Virtual Machine (JVM). When a Java process encounters Out-Of-Memory (OOM) errors or experiences unexpected memory growth, off-heap native memory is frequently the root cause. This article provides an overview of the distinct memory segments that constitute the off-heap native memory consumption of a Java application, including class metadata, thread stacks, JIT compilation caches, direct I/O buffers, and JVM internals.

Metaspace and Class Metadata

Metaspace holds the runtime representations of Java classes loaded by the application. Introduced in Java 8 to replace the PermGen space, Metaspace is allocated entirely out of native memory. It stores class metadata, method bytecode, runtime constant pools, annotations, and method tables. While Metaspace expands automatically by default, its growth can be capped using the -XX:MaxMetaspaceSize flag. Unbounded dynamic class generation—common in frameworks relying heavily on reflection, proxies, or bytecode manipulation—can lead to severe native memory bloat.

Thread Stacks

Every active thread in a Java application requires its own call stack allocated from native memory rather than the Java heap. The stack maintains execution frames, local primitive variables, and references to objects on the heap. The default stack size is typically 1 MB per thread on 64-bit systems, configured via the -Xss flag. In applications with high concurrency or thread pools containing thousands of threads, thread stacks alone can consume gigabytes of off-heap memory.

Code Cache

The Code Cache is native memory dedicated to the compilation and storage of native machine code produced by the Just-In-Time (JIT) compilers (C1 and C2). When the JVM detects frequently executed bytecode, it compiles that code into native instructions for better performance. The Code Cache also holds native method signatures and adapter code. It is bounded by the -XX:ReservedCodeCacheSize parameter, and exceeding this threshold forces the JVM to stop JIT compilation, falling back entirely to interpreted execution.

Direct Byte Buffers and Off-Heap I/O

Java NIO (New I/O) allows applications to allocate off-heap memory directly using ByteBuffer.allocateDirect() or low-level internal mechanisms like sun.misc.Unsafe. These Direct Byte Buffers bypass the Java heap to enable zero-copy network and disk I/O operations directly through operating system system calls. While highly performant for frameworks like Netty or gRPC, these allocations reside entirely in native memory and are only reclaimed during garbage collection cycles via phantom references or cleaner mechanisms, unless freed explicitly.

Garbage Collector Data Structures

The JVM's Garbage Collector (GC) requires native memory to track, manage, and compact the Java heap. Advanced collectors such as G1, ZGC, and Shenandoah use native memory structures to track object references across memory regions. Key structures include:

  • Remembered Sets (R-Sets): Track cross-region object references in G1 GC to facilitate concurrent and independent region collection.
  • Card Tables and Mark Bitmaps: Used during marking phases to record the liveness of objects.
  • GC Work Queues and Buffers: Coordinate task distribution among parallel GC worker threads.

The native memory footprint of the GC scales directly with the configured heap size and the complexity of object graphs.

JNI and Third-Party Native Libraries

Applications that utilize the Java Native Interface (JNI), Java Native Access (JNA), or the Foreign Function & Memory API interact with C/C++ libraries that manage memory independently via standard system calls like malloc and free. Common examples include embedded databases (e.g., RocksDB), native cryptography engines (e.g., OpenSSL via Netty), and compression algorithms (e.g., Zstandard). Memory allocated within these native libraries is invisible to standard JVM management tools and can easily leak if not paired with deterministic deallocation routines.

Internal JVM Allocations and Symbol Tables

The JVM maintains multiple native internal data structures necessary to coordinate core runtime operations:

  • Symbol and String Tables: Internal lookup tables that store interned string pointers and symbolic names for classes, fields, and methods.
  • Performance Counters and Profiling Data: Buffers utilized by runtime profilers and Java Flight Recorder (JFR) to track performance metrics.
  • Arena Allocators: Temporary native memory arenas used by the JVM during JIT optimization phases and class verification.
