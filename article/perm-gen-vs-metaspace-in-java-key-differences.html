PermGen vs Metaspace in Java: Key Differences

In Java 8, the Java Virtual Machine (JVM) underwent a major architectural shift with the complete removal of the Permanent Generation (PermGen) memory space and the introduction of Metaspace. This change was designed to address long-standing memory management issues, simplify garbage collection, and prevent common memory leaks caused by classloading in enterprise applications. Understanding the historical differences between PermGen and Metaspace clarifies how Java handles class metadata, memory limits, and runtime resource allocation.

Memory Location: JVM Heap vs. Native Memory

The most fundamental difference between PermGen and Metaspace lies in where the memory is physically allocated:

  • PermGen (Java 7 and earlier): PermGen was a contiguous, fixed-size memory region located directly inside the JVM heap. Because it shared the heap footprint, it required predefined boundaries that could not easily adapt to changing application demands at runtime.
  • Metaspace (Java 8 and later): Metaspace is allocated entirely out of native memory (off-heap memory provided directly by the underlying operating system). As a result, metadata allocation is no longer constrained by the JVM heap's boundaries.

Dynamic Sizing and OutOfMemoryError

Because PermGen lived on the heap, it had a fixed maximum size (typically 64 MB to 85 MB by default, depending on the platform). If an application dynamically generated classes—common with frameworks like Spring, Hibernate, or CGLIB—PermGen would quickly exhaust its allocation. This triggered the notorious java.lang.OutOfMemoryError: PermGen space.

Metaspace, by contrast, automatically resizes by default. It can expand dynamically to consume all available OS memory unless explicitly restricted. While an out-of-memory condition is still possible (java.lang.OutOfMemoryError: Metaspace), it occurs only when native system memory is genuinely exhausted or when an administrator sets a strict upper bound.

Relocation of Metadata and Static Artifacts

PermGen was responsible for storing several distinct types of data, which caused structural bottlenecks. Java 7 initiated the process of unbundling these elements, and Java 8 finalized it:

  • Class Metadata: In Java 8, runtime class definitions, method data, and annotations moved from PermGen directly into Metaspace.
  • Interned Strings: String pools were moved out of PermGen and placed into the standard Java Heap in Java 7, remaining there in Java 8 and beyond.
  • Class Statics: Static primitive variables and references to static objects were also moved out of PermGen to the regular Java Heap, where they are managed by standard heap garbage collection cycles.

Garbage Collection and Deallocation

In PermGen, reclaiming space required a full Garbage Collection (Full GC) cycle. Cleaning up stale classloaders and unloaded classes was inefficient and frequently failed in hot-redeploy scenarios (such as deploying new application versions to an application server without restarting the JVM), leading to leaks.

Metaspace improves this process by tying metadata allocation to the lifecycle of the classloader itself. When a classloader is no longer reachable and is marked for garbage collection, all metadata associated with that classloader in Metaspace is deallocated in bulk. Garbage collection in Metaspace is automatically triggered when native memory usage reaches a specific threshold (high-water mark), which dynamically adjusts upward or downward based on memory freed.

Configuration Flags

The replacement of PermGen with Metaspace retired old JVM startup arguments and introduced new ones:

  • PermGen Flags (Deprecated/Removed in Java 8):
    • -XX:PermSize: Set the initial PermGen allocation.
    • -XX:MaxPermSize: Set the hard ceiling for PermGen.
  • Metaspace Flags:
    • -XX:MetaspaceSize: Sets the initial threshold (high-water mark) that triggers the first Metaspace garbage collection.
    • -XX:MaxMetaspaceSize: Sets an optional hard upper limit on native memory consumed by Metaspace to prevent the JVM from consuming all host RAM.
