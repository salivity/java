Liskov Substitution Principle in Java Inheritance

The Liskov Substitution Principle (LSP), the "L" in the SOLID design principles, states that objects of a superclass should be replaceable with objects of a subclass without breaking application correctness. In Java, developers frequently misuse inheritance by modeling real-world taxonomies rather than behavioral compatibility, leading to fragile architectures and unexpected runtime failures. This article examines how LSP acts as a design rule to identify and eliminate improper inheritance hierarchies, using practical Java examples to demonstrate behavioral subtyping, the classic square-rectangle pitfall, and architectural alternatives like composition and interface segregation.

The Flaw of Naive "Is-A" Inheritance

In object-oriented programming, inheritance is often introduced as an "is-a" relationship: a Dog is an Animal, or a Square is a Rectangle. However, structural and behavioral compatibility are fundamentally different. Just because a concept sounds like a subtype in natural language does not mean it behaves as one in software.

LSP establishes that inheritance must be based on behavior. A subclass must fulfill the full behavioral contract established by its superclass. When a subclass alters, restricts, or violates that contract, the hierarchy is invalid, even if the Java compiler allows it to compile.

The Classic Anti-Pattern: Rectangle and Square

The most famous demonstration of an LSP violation involves a Rectangle and a Square. Mathematically, a square is a rectangle. In code, modeling this relationship through class inheritance creates severe bugs.

Consider this standard Rectangle implementation:

public class Rectangle {
    private int width;
    private int height;

    public void setWidth(int width) {
        this.width = width;
    }

    public void setHeight(int height) {
        this.height = height;
    }

    public int getWidth() {
        return width;
    }

    public int getHeight() {
        return height;
    }

    public int getArea() {
        return width * height;
    }
}

If Square inherits from Rectangle, it must enforce equal sides by overriding the setters:

public class Square extends Rectangle {
    @Override
    public void setWidth(int width) {
        super.setWidth(width);
        super.setHeight(width);
    }

    @Override
    public void setHeight(int height) {
        super.setWidth(height);
        super.setHeight(height);
    }
}

This breaks LSP. A client method expecting a Rectangle assumes that modifying the width leaves the height unchanged:

public void verifyArea(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    // Asserts 5 * 4 = 20. If r is a Square, area is actually 16 (4 * 4).
    assert r.getArea() == 20 : "Area calculation failed!";
}

Passing a Square into verifyArea alters the expected behavior of the program, proving that Square is not a true behavioral substitute for Rectangle.

Contract Rules Enforced by LSP

To prevent improper hierarchies, LSP sets strict rules regarding contracts in derived classes:

  1. Preconditions Cannot Be Strengthened: A subclass cannot require more restrictive input conditions than the base class. For instance, if SuperClass.process(int value) accepts any integer, SubClass.process(int value) cannot throw an IllegalArgumentException whenever value < 0.
  2. Postconditions Cannot Be Weakened: A subclass must deliver at least everything the base class promised. If SuperClass.save() guarantees that data is flushed to persistent storage, SubClass.save() cannot silently defer or skip this step.
  3. Invariants Must Be Preserved: Conditions that are always true for the base class must remain true for the subclass. If a base collection guarantees non-null elements, no subclass implementation can allow null values.
  4. No Unsupported Operations: Throwing UnsupportedOperationException in an overridden method (such as an unmodifiable collection implementing Java's java.util.List mutating methods) is a direct symptom of an LSP violation.

Fixing Improper Hierarchies

When LSP reveals an improper inheritance hierarchy, developers should refactor using one of two primary strategies.

1. Extracting a Common Abstraction

If two classes share characteristics but have distinct behaviors, inherit both from a higher-level, more general interface rather than from each other.

public interface Shape {
    int getArea();
}

public class Rectangle implements Shape {
    private final int width;
    private final int height;

    public Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }

    @Override
    public int getArea() {
        return width * height;
    }
}

public class Square implements Shape {
    private final int side;

    public Square(int side) {
        this.side = side;
    }

    @Override
    public int getArea() {
        return side * side;
    }
}

Both Rectangle and Square satisfy the Shape contract without imposing conflicting mutation semantics on each other.

2. Favoring Composition Over Inheritance

If a class requires functionality from another class but cannot maintain its contract, it should contain an instance of that class instead of extending it. For example, instead of extending a collection class to create a custom stack or queue, hold the collection as a private final field and expose only the specific operations that remain valid.

Summary

The Liskov Substitution Principle prevents improper inheritance hierarchies by shifting the focus from structural "is-a" assumptions to verifiable behavioral contracts. In Java, adhering to LSP eliminates defective method overrides, removes the need for defensive instanceof checks, prevents unexpected runtime exceptions, and results in a clean, polymorphic architecture.
