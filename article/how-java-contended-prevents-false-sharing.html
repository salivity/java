How Java @Contended Prevents False Sharing

This article explores how the @Contended annotation in Java mitigates false sharing, a subtle concurrency issue that severely degrades multi-threaded performance. False sharing happens when threads running on separate CPU cores modify independent variables that reside within the same CPU cache line, triggering constant and unnecessary cache invalidations. By applying the @Contended annotation, the Java Virtual Machine (JVM) introduces memory padding around critical fields, ensuring they occupy distinct cache lines and eliminating cache thrashing.

Understanding False Sharing and CPU Cache Lines

Modern processors do not read or write data to main memory one byte at a time; instead, they operate in blocks called cache lines, which are typically 64 bytes in size. When a thread accesses a variable, the CPU fetches that variable along with its neighboring data into the core's L1/L2 cache.

False sharing occurs in multi-threaded environments under the following conditions:

  1. Two independent variables exist physically next to each other in memory within the same 64-byte cache line.
  2. Core A modifies variable X while Core B reads or modifies variable Y.
  3. Because the cache-coherency protocol (such as MESI) operates at the cache-line level, Core A's write invalidates the entire cache line in Core B's cache.
  4. Core B must reload the cache line from L3 or main memory, even though Core B never accessed variable X.

This constant invalidation and reloading cycle introduces massive latency and limits the scalability of concurrent data structures.

How the @Contended Annotation Works

Introduced under JEP 142 in Java 8, the @Contended annotation directs the JVM to alter the memory layout of an object's fields.

When a field is annotated with @Contended, the HotSpot JVM injects empty memory padding—usually 128 bytes—before and after the field. This padding guarantees two things:

  • The annotated field is isolated from other fields in the same object.
  • The field spans an area larger than a typical cache line (and accounts for hardware prefetchers that might fetch two adjacent cache lines at once), preventing any other variable from sharing its cache line.

As a result, writes to an annotated variable will not invalidate the cache lines holding other variables, enabling concurrent threads to execute without inter-core cache interference.

Usage Modes: Fields, Groups, and Classes

The @Contended annotation provides granular control over memory layout:

1. Individual Field Isolation

Applying the annotation without arguments isolates that specific field from all other fields:

public class MetricCounters {
    @Contended
    private volatile long operations;

    @Contended
    private volatile long errors;
}

The JVM isolates both operations and errors into their own separate cache lines, allowing two threads to update them simultaneously without collision.

2. Contention Groups

You can pass a group name as a string to bundle related fields together while separating them from others:

public class ConnectionPool {
    @Contended("reader")
    private volatile long readBytes;
    @Contended("reader")
    private volatile long readCount;

    @Contended("writer")
    private volatile long writeBytes;
    @Contended("writer")
    private volatile long writeCount;
}

Here, readBytes and readCount reside together in one cache line, while writeBytes and writeCount are packed into another. Readers do not invalidate writers, but variables within the same operational path remain compact.

3. Class-Level Isolation

Annotating an entire class adds padding before and after all instances of that class. This prevents false sharing between array elements when storing objects in continuous memory arrays.

Practical Considerations and JVM Flags

By default, the HotSpot JVM restricts the use of @Contended to internal system classes (such as java.util.concurrent.atomic.LongAdder or ForkJoinPool).

To enable the annotation for user-defined code, you must pass the following JVM argument at startup:

-XX:-RestrictContended

You can also adjust the padding size using:

-XX:ContendedPaddingWidth=128

Trade-Offs

While @Contended significantly reduces latency in high-throughput, low-latency concurrent programs, it comes with a memory cost. Padding objects with 128 bytes increases overall heap consumption and reduces cache density. Therefore, it should be applied selectively to proven contention bottlenecks rather than as a general-purpose optimization.
