How Biased Locking Optimizes Java Synchronized Blocks

Biased locking was an optimization introduced in Java 6 to virtually eliminate the performance penalty of uncontended synchronized blocks. In many legacy Java applications, synchronization was used heavily for thread-safe collections (like Vector or StringBuffer) even when executed entirely by a single thread. This article explains how biased locking minimizes synchronization costs by avoiding atomic CPU instructions, details the mechanics of the object header, and outlines why modern Java runtimes eventually retired this technique.

The Cost of Traditional Synchronization

In standard Java synchronization, acquiring an uncontended lock relies on lightweight locking. Lightweight locking requires the JVM to execute atomic Compare-And-Swap (CAS) instructions to update the object header.

While atomic operations are much faster than operating system mutexes (heavyweight locks), they still incur noticeable hardware overhead. Atomic instructions lock the CPU memory bus or invalidate cache lines across processor cores, causing pipeline stalls. When a single thread repeatedly enters and exits synchronized blocks on the same object, executing repeated CAS operations wastes CPU cycles.

How Biased Locking Works

Biased locking operates on the observation that most locks are only ever acquired by a single thread throughout their lifecycle. Instead of using atomic operations every time a monitor is entered and exited, the runtime "biases" the object toward the first thread that locks it.

1. Initial Acquisition

Every Java object possesses a memory header containing a "mark word." The mark word stores runtime metadata such as the object’s hash code, garbage collection age, and locking state bits.

When an object is marked as biasable and a thread attempts to synchronize on it for the first time:

  1. The thread checks the bias pattern bits in the object's mark word.
  2. It executes a single CAS operation to write its own Thread ID directly into the mark word.
  3. If successful, the object becomes biased toward that specific thread.

2. Subsequent Acquisitions by the Biased Thread

Once the lock is biased, subsequent synchronized blocks entered by the same thread require almost zero overhead:

  1. The thread reads the object's mark word.
  2. It verifies that the bias pattern is enabled and that the recorded Thread ID matches its own.
  3. If both conditions match, execution proceeds directly into the critical section.

This validation requires only a few basic memory read and bitwise comparison instructions. It bypasses CAS operations, bus locking, and memory barriers entirely, making uncontended lock acquisition nearly as fast as non-synchronized code execution.

3. Exiting the Synchronized Block

When the biased thread exits the synchronized block, it performs virtually no cleanup. It leaves its Thread ID in the mark word. The bias remains intact until another thread attempts to access the object or a non-compatible operation (such as calling identity hashCode()) forces revocation.

Revocation of the Bias

The performance advantage of biased locking depends entirely on the absence of lock competition. When a second thread attempts to synchronize on a biased object, the runtime must revoke the bias before proceeding:

  1. Safepoint Pauses: In legacy runtimes, revoking a bias required bringing the JVM to a global safepoint (Stop-The-World pause) to safely inspect and alter the biased thread's stack.
  2. Re-evaluation: At the safepoint, the JVM checks if the thread holding the bias is still executing the synchronized block:
    • If inactive: The bias is cleared, and the object can either be rebound or converted to a normal unlocked state.
    • If active: The lock is upgraded to lightweight locking. The mark word is replaced with a pointer to a lock record on the thread's stack.
  3. Escalation to Heavyweight Locking: If true concurrent contention occurs between multiple active threads, the lock further inflates into an OS-level monitor (mutex), suspending competing threads.

Why Modern Java Deprecated Biased Locking

While biased locking yielded significant throughput improvements on older hardware and legacy coding patterns, changes in application design and CPU architectures diminished its benefits:

  • Costly Revocations: As modern systems scaled to dozens of CPU cores, the Stop-The-World safepoint pauses required to revoke biases often introduced latency spikes that outweighed the performance gained from avoiding CAS operations.
  • Modern Concurrency Patterns: Contemporary Java frameworks rely on non-blocking concurrency libraries (java.util.concurrent) rather than synchronized legacy classes, making single-threaded lock reuse less prevalent.
  • Cheaper Atomic Instructions: Newer processors drastically reduced the cycle cost of atomic CAS operations.

Because the complex synchronization logic was difficult to maintain inside the HotSpot JVM codebase, biased locking was disabled by default in Java 15 (JEP 374) and subsequently removed from modern Java runtimes.
