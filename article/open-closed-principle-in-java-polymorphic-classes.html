Open-Closed Principle in Java Polymorphic Classes

The Open/Closed Principle (OCP) states that software entities such as classes, modules, and functions should be open for extension but closed for modification. When applied to expanding polymorphic classes in Java, OCP dictates that you must introduce new functionality by creating new subclasses or implementing existing interfaces, rather than altering already tested and deployed code. This design approach minimizes the risk of introducing regressions and keeps the existing system architecture stable as requirements evolve.

The Core Rule: Extend via Abstraction

When expanding a system with new behaviors, OCP requires you to rely on abstractions—interfaces or abstract classes—rather than concrete implementations. Instead of modifying an existing class to handle a new variant or behavior, you write a new class that adheres to the established contract.

Avoiding Conditional Logic

The most common violation of OCP in object-oriented programming is using conditional logic (if-else or switch statements) to handle different types. When a new type is required, modifying these control blocks alters existing source code.

Under OCP, polymorphism replaces conditional logic entirely:

  • Violation: Adding a new case to a switch statement inside a service class to handle a new payment method.
  • Adherence: Creating a PaymentMethod interface and providing a distinct implementation (such as CreditCardPayment, PayPalPayment, or a new CryptoPayment) without touching the core payment processing logic.

Implementation Example

Consider an operation that calculates discounts. An OCP-compliant approach defines an interface:

public interface DiscountStrategy {
    double applyDiscount(double amount);
}

Existing implementations might include:

public class StandardDiscount implements DiscountStrategy {
    @Override
    public double applyDiscount(double amount) {
        return amount * 0.95;
    }
}

When a requirement emerges for a seasonal discount, OCP dictates that you should not modify StandardDiscount or the calling service. Instead, you expand the polymorphic structure by adding a new class:

public class SeasonalDiscount implements DiscountStrategy {
    @Override
    public double applyDiscount(double amount) {
        return amount * 0.80;
    }
}

The client code consumes the DiscountStrategy interface directly:

public class OrderService {
    public double calculateTotal(double amount, DiscountStrategy discountStrategy) {
        return discountStrategy.applyDiscount(amount);
    }
}

OrderService is closed for modification because its code does not change, yet it is open for extension because any new DiscountStrategy can be supplied seamlessly at runtime.

Key Rules When Expanding Polymorphic Classes

  1. Keep Base Contracts Stable: Do not add or change method signatures in established interfaces or abstract base classes, as doing so forces modifications across all existing implementations.
  2. Favor Composition and Interfaces: Use Java interfaces to define capabilities. This allows new classes to adopt polymorphic roles without inheriting unwanted state or implementation details.
  3. Preserve Subtype Behavior: Ensure that any new subclass conforms to the behavioral expectations of the parent type, fulfilling the Liskov Substitution Principle (LSP) alongside OCP.
