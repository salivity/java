JUnit 5: @BeforeEach vs @BeforeAll Differences

In JUnit 5, @BeforeEach and @BeforeAll are core lifecycle annotations used to execute setup logic, but they trigger at fundamentally different stages of the testing lifecycle. This article explains the key differences between @BeforeEach and @BeforeAll, detailing how their execution frequency, method requirements, and performance characteristics dictate when to use each annotation in your test suites.

Execution Frequency

The primary distinction between the two annotations lies in how often their annotated methods are executed:

  • @BeforeAll: Executes exactly once before any test method in the current test class is run. It acts at the container/class level.
  • @BeforeEach: Executes before every individual @Test, @RepeatedTest, @ParameterizedTest, or @TestFactory method. If a class contains five test methods, the @BeforeEach method executes five separate times.

Method Signature and Static Requirements

Because JUnit creates a new instance of the test class for each test method by default (TestInstance.Lifecycle.PER_METHOD), the methods bound to these annotations have different structural requirements:

  • @BeforeAll: Must be declared as static under the default lifecycle. It cannot access instance variables of the test class. However, if the test class is explicitly configured with @TestInstance(Lifecycle.PER_CLASS), the method can be non-static.
  • @BeforeEach: Must be an instance method (non-static). It operates directly on the current instance of the test class and has full access to instance fields.

Neither annotation allows the method to be private or return a value; both must return void.

Use Cases

Choosing between these annotations depends on resource costs and the necessity of test isolation.

When to Use @BeforeAll

Use @BeforeAll for heavy, expensive operations that do not need to be refreshed between individual test runs and do not suffer from state contamination across tests:

  • Starting external resources like Docker containers (e.g., Testcontainers).
  • Opening a database connection or establishing a shared connection pool.
  • Reading and parsing large static configuration files or dataset fixtures.
  • Starting an embedded web server or wiremock service.

When to Use @BeforeEach

Use @BeforeEach to ensure state isolation and test independence, preventing side effects from one test from impacting another:

  • Instantiating fresh instances of the class under test.
  • Resetting or re-initializing mock objects (e.g., MockitoAnnotations.openMocks(this)).
  • Seeding mutable test data that tests may modify, insert, or delete.
  • Resetting application contexts, caches, or security contexts.

Code Example

import org.junit.jupiter.api.*;

class OrderServiceTest {

    @BeforeAll
    static void initGlobalResources() {
        // Runs once before all tests
        System.out.println("Starting shared database connection...");
    }

    @BeforeEach
    void setUp() {
        // Runs before each @Test method
        System.out.println("Resetting state and creating fresh service instance...");
    }

    @Test
    void testCreateOrder() {
        System.out.println("Executing: testCreateOrder");
    }

    @Test
    void testCancelOrder() {
        System.out.println("Executing: testCancelOrder");
    }

    @AfterAll
    static void tearDownGlobalResources() {
        // Runs once after all tests complete
        System.out.println("Closing shared database connection...");
    }
}

Summary Comparison

Feature @BeforeAll @BeforeEach
Execution Count Once per test class Once per test method

Scope Class / Container level Method / Test level
Primary Purpose Heavy, shared resource initialization State isolation and fresh test fixtures
Teardown Counterpart @AfterAll @AfterEach
