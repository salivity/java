Java Dead Code Stripping and Unreferenced Constants

This article explores how Java handles unreferenced constants during compilation, distinguishing between standard javac dead code elimination and bytecode-level dead code stripping. You will learn how compile-time constant inlining works, why the standard compiler preserves unreferenced field declarations, and how post-compilation optimization tools ultimately prune unused constant values from the class file.

Compile-Time Constant Inlining

In Java, a constant is typically declared as static final with a primitive type or a String, initialized using a compile-time constant expression. When code references one of these constants, the standard Java compiler (javac) does not emit a field lookup instruction (getstatic). Instead, it copies the literal value directly into the calling bytecode instructions.

Because the values are directly inlined at call sites, the original field definition is technically decoupled from its consumers.

How javac Handles Unreferenced Constants

The standard Java compiler performs minimal dead code elimination on class members:

  1. Local Constants: If a final variable is declared inside a method and never used, javac removes it entirely. No trace of the local variable appears in the generated method bytecode or the local variable table (unless debug flags are specified).
  2. Class-Level Constants (static final fields): Even if a private static final field is never referenced within the class or anywhere else, javac does not delete it. The field remains declared in the class file's field table, and its value is stored in the ConstantValue attribute within the constant pool.

The Java compiler retains these fields primarily to preserve class structure, support reflection (java.lang.reflect), and maintain binary compatibility across separate compilation units.

Branch Pruning and Dead Code Removal

While javac does not strip unreferenced fields, it does perform dead code stripping on execution paths governed by constants. Consider the following conditional:

private static final boolean DEBUG = false;

public void run() {
    if (DEBUG) {
        System.out.println("Debugging...");
    }
}

Because DEBUG evaluates to false at compile time, the compiler strips the entire if branch. The bytecode for run() will contain no conditional check, no print statement, and no string reference to "Debugging...". However, the declaration of DEBUG itself will still occupy space in the compiled .class file.

Advanced Dead Code Stripping via Minifiers and Tree Shakers

True dead code stripping of unreferenced static constants occurs during post-compilation steps through optimizers like ProGuard, R8, or ahead-of-time (AOT) compilers like GraalVM Native Image.

These tools analyze the entire application call graph to perform tree shaking:

  • Removal of Unused Fields: If a static final field has no read occurrences and reflection is disabled or rule-excluded, the optimizer removes the field entry from the class file entirely.
  • Removal from Inlined Fields: If a constant was public, inlined into all call sites, and never accessed via reflection, tree shakers will safely remove the original field definition from the exporting class.
  • Constant Pool Compaction: Stripping unreferenced constants reduces the size of the class file’s constant pool, eliminating unused literals, method names, and type descriptors.

Summary of Impact

Standard javac compilation strips unreferenced local variables and dead code branches controlled by constants, but leaves unreferenced class fields and their constant pool entries intact. True elimination of unreferenced constant fields requires a secondary dead code stripping tool, which discards both the field metadata and its pool entries to reduce bytecode size and improve runtime memory efficiency.
