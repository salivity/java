Java Tiered Compilation: Startup vs Peak Performance

Java's tiered compilation is a dynamic optimization technique within the HotSpot Java Virtual Machine (JVM) designed to eliminate the historical trade-off between fast application startup and optimal steady-state performance. By orchestrating a multi-tiered compilation pipeline—transitioning code seamlessly from interpreted execution through intermediate client-level optimizations up to aggressive server-level machine code generation—the JVM ensures that programs start running immediately while still reaching peak execution throughput over time.

The Historical Trade-Off: C1 vs. C2

Prior to tiered compilation, Java developers had to select between two distinct Just-In-Time (JIT) compilers via JVM flags:

  • Client Compiler (C1): Designed for rapid startup and low memory overhead. It applies light optimizations and compiles bytecodes into machine code quickly, making it ideal for desktop applications and short-lived CLI tools, but sacrificing peak throughput.
  • Server Compiler (C2): Designed for high-throughput, long-running server workloads. It uses complex, compute-intensive optimizations such as deep inlining, loop unrolling, and escape analysis. While it produces highly optimized machine code, the compilation process introduces substantial latency and CPU overhead during startup.

Tiered compilation, introduced in Java 7 and enabled by default since Java 8, combines both compilers into a unified execution model.

The Five Execution Levels

Tiered compilation divides code execution into five discrete levels:

  1. Level 0 (Interpreted Code): The JVM executes raw bytecodes without compilation. Execution begins instantly with zero compilation latency.
  2. Level 1 (Simple C1): Code is compiled using C1 with no profiling code injected. Used primarily when C2 is overloaded or for trivial methods.
  3. Level 2 (Limited C1 Profiling): Code is compiled with lightweight profiling counters (such as invocation counts and basic branch statistics).
  4. Level 3 (Full C1 Profiling): Code is compiled using C1 with full profiling instrumentation, capturing comprehensive runtime execution profiles, branch probabilities, and type feedback.
  5. Level 4 (C2 / Server Optimization): Code is compiled using C2. It consumes the profiling data gathered during Level 3 to apply aggressive global optimizations, resulting in maximum execution speed.

How Tiered Compilation Balances the Workload

The JVM dynamically transitions methods across these tiers based on invocation frequency and workload demands:

  • Instant Startup: At launch, the application begins executing immediately at Level 0 (interpreted). There is no waiting for compilation queues to clear.
  • Rapid Acceleration: As methods are repeatedly executed, they quickly trigger compilation to Level 3 (C1 with full profiling). This produces machine code fast enough to eliminate interpreter overhead early in the application lifecycle while simultaneously measuring how the code actually behaves under load.
  • Progressive Peak Performance: Methods that remain "hot" over time are placed in the C2 queue and recompiled at Level 4. C2 uses the detailed runtime metrics gathered by Level 3 to generate peak-performance native code.
  • Dynamic Deoptimization: If the runtime behavior changes—such as a previously unseen subclass violating an inlining assumption—the JVM safely deoptimizes the code, falling back to Level 0 or Level 3 to re-profile before optimizing again.

By allowing C1 to absorb the initial execution burden and profile on the fly, C2 can run asynchronously in background threads without starving the application of CPU or stalling startup, successfully delivering the responsiveness of a lightweight client and the high-throughput performance of an enterprise server.
