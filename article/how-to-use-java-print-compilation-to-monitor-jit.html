How to Use Java PrintCompilation to Monitor JIT

The -XX:+PrintCompilation Java Virtual Machine (JVM) flag gives developers real-time visibility into the Just-In-Time (JIT) compilation process as an application runs. By emitting a continuous log of method compilation, tiered optimization changes, and deoptimization events directly to standard output, this diagnostic flag allows engineers to observe how bytecode is converted into native machine code. It is an essential tool for verifying JIT warm-up, diagnosing performance regressions, and understanding the execution profile of Java applications without the overhead of heavy external profilers.

Enabling the Flag

To observe JIT activity, append the flag to the java launch command:

java -XX:+PrintCompilation -jar application.jar

Because -XX:+PrintCompilation has negligible performance overhead, it can safely be used in benchmarking, staging environments, and even troubleshooting scenarios in production.

Decoding the Output Format

Each time the JIT compiler interacts with a method, it prints a single line to standard output. A typical output entry looks like this:

789   123    3       java.lang.String::hashCode (55 bytes)

The output is structured into standard columns:

  1. Timestamp: The first number (e.g., 789) indicates the elapsed time in milliseconds since the JVM started.
  2. Compilation ID: The second integer (e.g., 123) is an incremental identifier assigned to each compilation task.
  3. Attributes (Modifiers): Special characters may appear between the ID and the tier level, indicating specific method traits:
    • %: The method is compiled using On-Stack Replacement (OSR), meaning a hot loop inside the method was compiled while currently executing.
    • s: The method is synchronized.
    • !: The method contains exception handling logic.
    • b: Compilation occurred synchronously (blocking compilation).
  4. Compilation Tier: HotSpot uses tiered compilation, denoted by numbers 1 through 4:
    • Tier 0: Interpreted bytecode (does not appear in this output).
    • Tiers 1–3: Compiled by the C1 compiler with progressively deeper profiling instrumentation.
    • Tier 4: Compiled by the C2 (Server) compiler, applying aggressive optimizations like method inlining, loop unrolling, and escape analysis.
  5. Method Signature and Bytecode Size: Identifies the class, method name, and bytecode size in parentheses.

Monitoring Deoptimization Events

The flag also surfaces JVM deoptimizations—scenarios where the JIT reverts native code back to interpreted mode or a lower tier because speculative assumptions were violated. These appear with explicit textual markers:

  • made not entrant: Occurs when an optimized method is invalidated, often because a class hierarchy changed, dynamic class loading invalidated an inlined call site, or a branch assumption failed. Execution drops back to Tier 0 or C1 until re-profiled.
  • made zombie: Indicates that dead native code has been swept from the CodeCache and its memory reclaimed.

Frequent cycles of compilation, followed by "made not entrant" messages for the same method, indicate JIT thrashing. This thrashing introduces latency spikes and consumes CPU cycles, pointing to megamorphic call sites or unpredictable code paths that prevent stable C2 optimizations.

Practical Engineering Applications

Using -XX:+PrintCompilation enables developers to answer several critical runtime questions:

  • Warm-up Verification: During load testing, developers can observe when compilation activity subsides, signaling that hot paths have reached peak Tier 4 optimization and the application is fully warmed up.
  • Inline Evaluation: If a critical method shows up frequently with the % (OSR) flag rather than standard method-entry compilation, it may indicate a method that is too large to be inlined cleanly by the compiler.
  • CodeCache Sizing: Observing the pace and volume of compilations helps identify whether an application is approaching ReservedCodeCacheSize limits, which would halt further JIT optimizations entirely.
