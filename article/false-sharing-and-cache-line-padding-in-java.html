False Sharing and Cache Line Padding in Java

In multicore architectures, false sharing occurs when multiple threads independently modify distinct variables that reside within the same CPU cache line, causing silent and severe performance degradation. This article examines the mechanics of false sharing under hardware cache coherence protocols, demonstrates how it affects concurrent Java programs, and details how CPU cache line padding—both through manual field expansion and the JVM's @jdk.internal.vm.annotation.Contended annotation—resolves this concurrency bottleneck.

Understanding CPU Cache Lines and Cache Coherence

Modern CPUs do not read from or write to main memory one byte or word at a time. Instead, memory transfers between main memory and the CPU caches (L1, L2, and L3) occur in fixed-size blocks known as cache lines. On most modern x86 and ARM processors, a single cache line is 64 bytes.

To maintain a consistent view of memory across multiple CPU cores, hardware relies on cache coherence protocols, such as MESI (Modified, Exclusive, Shared, Invalid). Under MESI:

  1. When Core A writes to a variable inside a cache line, that entire line is marked as Modified.
  2. Any copy of that same cache line present in the local caches of Core B, Core C, or other cores is marked as Invalid.
  3. If Core B subsequently attempts to read or write to any data within that invalidated line, it incurs a cache miss and must stall while fetching the updated line from Core A or higher-level memory.

What is False Sharing?

False sharing occurs when two or more threads update completely independent logical variables, but those variables happen to be located close enough in memory to share the same physical 64-byte cache line.

Consider two threads and two distinct fields:

public class CounterHolder {
    public volatile long counterA = 0L;
    public volatile long counterB = 0L;
}

In Java, a long consumes 8 bytes. In a standard 64-bit JVM with compressed ordinary object pointers (OOPs), the object header takes 12 bytes. Consequently, counterA and counterB reside adjacent to each other well within a single 64-byte window.

If Thread 1 repeatedly updates counterA on Core 1, and Thread 2 repeatedly updates counterB on Core 2:

  • Core 1 marks the shared cache line as Modified, invalidating Core 2's cache line.
  • Core 2 attempts to write to counterB, encounters an invalidation, forces a cache sync, and marks its line as Modified, invalidating Core 1's cache line.
  • The cache line continuously bounces between cores over the interconnect bus (known as cache ping-ponging).

Although there is no logical race condition between counterA and counterB, the hardware treats the updates as conflicting, reducing multicore throughput to speeds often slower than single-threaded execution.

Resolving False Sharing with Cache Line Padding

The fundamental solution to false sharing is spatial separation: ensuring that concurrently modified independent variables are allocated to separate cache lines. This is achieved through cache line padding, which inserts unused space around sensitive variables to push them past the 64-byte boundary.

1. Manual Padding

In early versions of Java, developers manually padded classes by declaring unused dummy variables around the target field:

public class PaddedCounter {
    // 56 bytes of padding (7 longs * 8 bytes) to isolate counterA
    public long p1, p2, p3, p4, p5, p6, p7;
    public volatile long counterA = 0L;
    
    // Another 56 bytes of padding to isolate counterB
    public long p8, p9, p10, p11, p12, p13, p14;
    public volatile long counterB = 0L;
}

While functional in some scenarios, manual padding has severe limitations:

  • Field Reordering: The JVM specification allows the Just-In-Time (JIT) compiler and class loader to rearrange fields in memory to optimize layout, potentially clustering counterA and counterB together despite source-code ordering.
  • Inheritance Workarounds: Developers often had to distribute padding across multiple parent classes to prevent the JVM from compacting the layout.
  • Portability: Hardcoding padding sizes assumes a 64-byte line, which may not match architectures with 128-byte cache lines.

2. JVM-Managed Padding: @Contended

To provide a robust, architecture-agnostic solution, Java 8 introduced JEP 142 and the @Contended annotation (located in jdk.internal.vm.annotation.Contended in modern Java releases).

When applied to a field or class, @Contended instructs the JVM to automatically insert the required padding based on the target architecture's detected cache line size:

import jdk.internal.vm.annotation.Contended;

public class ContendedCounterHolder {
    @Contended
    public volatile long counterA = 0L;

    @Contended
    public volatile long counterB = 0L;
}

The JVM guarantees that counterA and counterB will not share a cache line with each other or with any other field in the object. You can also group fields using contention groups (e.g., @Contended("group1")), ensuring that fields within the same group share a cache line, while isolated from fields in other groups.

To use @Contended in application code outside the core JDK modules, you must explicitly enable it at runtime using the following JVM flag:

-XX:-RestrictContended

Trade-Offs and Best Practices

Cache line padding increases memory consumption per object to eliminate cache contention. It is not a generic optimization for all data structures; rather, it should be reserved for high-throughput, latency-critical components such as lock-free ring buffers, concurrent queues, and shared thread counters. High-performance Java libraries, such as the LMAX Disruptor and the JDK's own java.util.concurrent.atomic.LongAdder, rely directly on cache line padding to scale write operations linearly across CPU cores.
