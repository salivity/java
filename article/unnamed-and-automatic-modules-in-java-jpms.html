Unnamed and Automatic Modules in Java JPMS

The Java Platform Module System (JPMS), introduced in Java 9, provides two transitional concepts—unnamed modules and automatic modules—to bridge the gap between traditional classpath-based architectures and the strict modular system. These mechanisms allow legacy JARs and modern modular libraries to coexist and communicate seamlessly, enabling developers to adopt modularity incrementally rather than requiring a high-risk, all-at-once migration.

The Legacy Problem

Prior to Java 9, Java applications relied exclusively on the flat classpath. On the classpath, all types were visible to each other as long as they had public access, and there was no mechanism to declare dependencies explicitly or encapsulate internal packages.

The introduction of JPMS enforced strong encapsulation and explicit dependencies via module-info.java. Because millions of existing libraries could not update overnight, JPMS introduced unnamed and automatic modules to guarantee backward compatibility and support progressive migration.

The Unnamed Module: Classpath Compatibility

Any code loaded from the traditional classpath (using -classpath or -cp) is assigned to the unnamed module. The unnamed module acts as an adapter that allows legacy applications to run on modern Java runtimes without modifications.

Key characteristics of the unnamed module include:

  • Reads Everything: The unnamed module can read all named modules, automatic modules, and standard Java runtime modules. This allows legacy classpath code to invoke modularized APIs.
  • Exports Everything: All packages inside the unnamed module are automatically exported and opened to any other module that can access it.
  • Cannot Be Required: Explicit (named) modules cannot declare a requires directive targeting the unnamed module. Because the unnamed module has no official name, modular code cannot statically depend on classes residing on the classpath.

The unnamed module essentially preserves the historical behavior of the classpath, ensuring that older applications execute exactly as they did in Java 8 and earlier.

Automatic Modules: Bringing Legacy JARs to the Module-Path

When a modular application depends on a third-party library that has not yet adopted a module-info.java descriptor, that library can be placed on the module-path (--module-path) instead of the classpath. The JPMS automatically treats this legacy JAR as an automatic module.

Key characteristics of automatic modules include:

  • Automatic Naming: The module runtime determines the module name either from the Automatic-Module-Name manifest header in the JAR or by parsing the JAR's filename (stripping version numbers and non-alphanumeric characters).
  • Exports and Opens Everything: To ensure compatibility with reflection-heavy frameworks, an automatic module exports and opens all of its internal packages to all other modules.
  • Reads All Modules: An automatic module implicitly reads all other resolved modules, including other automatic modules, explicit modules, and the unnamed module.
  • Explicitly Required: Unlike the unnamed module, modular applications can declare requires <automatic-module-name>; in their module-info.java.

Bridging the Gap: Migration Strategies

Together, these mechanisms support two primary migration pathways:

  1. Top-Down Migration: An application can be modularized first while its dependencies remain legacy JARs. By placing those legacy dependencies on the module-path, they become automatic modules, allowing the application's module-info.java to declare dependencies on them directly.
  2. Bottom-Down Migration: Libraries can modularize before the consuming application does. Modular libraries placed on the module-path remain fully accessible to the legacy application running in the unnamed module on the classpath.

By using the unnamed module to preserve classpath dynamics and automatic modules to wrap legacy code with temporary module identities, Java allows teams to modernize their codebases at their own pace without breaking existing ecosystems.
