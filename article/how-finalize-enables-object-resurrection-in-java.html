How finalize Enables Object Resurrection in Java

In Java, the finalize method presents a notorious loophole in the standard object lifecycle by allowing an object marked for garbage collection to restore its own reachability. Under normal conditions, once an object becomes unreachable from any Garbage Collection (GC) roots, it is considered dead and scheduled for memory reclamation. However, the execution of finalize() temporarily provides the dying instance with an active thread context, enabling it to reassign a reference of itself (this) to a live, reachable variable. This process, known as object resurrection, breaks the linear progression of an object's lifecycle, leads to unpredictable application states, and is the primary reason the finalization mechanism was deprecated in modern Java.

The Normal Java Object Lifecycle

A standard Java object traverses a predictable lifecycle:

  1. Creation: Memory is allocated, and the constructor initializes the instance.
  2. Reachability: The object is actively referenced by running threads, static variables, or other live objects.
  3. Unreachability: All strong references to the object are dropped, making it a candidate for garbage collection.
  4. Reclamation: The JVM frees the object's allocated memory and returns it to the heap.

This lifecycle ensures memory safety by guaranteeing that once an object is no longer accessible, it cannot perform further work or alter the application state.

How finalize Intervenes

When a class overrides protected void finalize(), the JVM alters how its instances are collected:

  1. Finalization Registration: When the object is instantiated, the JVM registers it as finalizable.
  2. Identification by GC: When the garbage collector detects that the object is no longer reachable, it does not immediately free its memory. Instead, it moves the object to a finalization queue.
  3. Execution on the Finalizer Thread: A low-priority, JVM-managed thread runs the finalize() method for each queued object.

Because finalize() is an instance method, the object receives a valid, temporary this reference while the method executes.

The Mechanism of Object Resurrection

Object resurrection occurs directly inside the finalize() implementation. If the method assigns this to a live reference—such as a static collection, an active singleton, or any object reachable from a GC root—a new reference chain is created.

public class ResurrectedObject {
    public static ResurrectedObject liveHolder;

    @Override
    protected void finalize() throws Throwable {
        // Resurrects the object by exposing 'this' to an active GC root
        liveHolder = this;
    }
}

When the garbage collector inspects the heap in a subsequent cycle, it discovers a valid path from a GC root to the instance via liveHolder. Consequently, the JVM aborts the collection of the object, fully restoring it to the active pool of reachable memory.

Consequences and Lifecycle Breakage

Resurrection bypasses fundamental lifecycle safety in several distinct ways:

  • Single Execution Guarantee: The Java Virtual Machine guarantees that finalize() will run at most once per object. If a resurrected object becomes unreachable a second time, the JVM will reclaim it immediately without calling finalize() again. This leads to silent failures if cleanup logic was expected to run prior to actual reclamation.
  • Inconsistent State: Often, cleanup logic partially tears down the object's internal resources (closing file descriptors, clearing collections, or nullifying pointers) before or during the resurrection. The resurrected object re-enters the program in a corrupted or half-destroyed state.
  • Thread Safety Issues: The resurrection happens on the JVM's finalizer thread rather than the application thread that originally owned the object. Unless explicit, defensive synchronization is applied, publishing this across threads can result in memory visibility bugs and race conditions.

Modern Alternatives

To eliminate the safety hazards introduced by finalize(), modern Java applications rely on deterministic and safer mechanisms:

  • AutoCloseable with try-with-resources: Provides deterministic, synchronous resource reclamation as soon as a block of code completes.
  • java.lang.ref.Cleaner: Introduced in Java 9 to replace finalize(). Cleaners register cleanup actions that run asynchronously after an object becomes phantom-reachable, ensuring the object itself cannot be resurrected because the cleanup task never holds a strong reference to the target instance.
