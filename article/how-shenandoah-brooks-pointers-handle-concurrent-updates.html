How Shenandoah Brooks Pointers Handle Concurrent Updates

The Shenandoah Garbage Collector (GC) in OpenJDK achieves ultra-low pause times by performing heap compaction concurrently with running application threads. To safely manage concurrent object updates during evacuation, early implementations of Shenandoah introduced the "Brooks pointer"—an indirection reference prepended to every object header. This article explains the mechanics of the Brooks pointer, how it resolves race conditions between mutator threads and the garbage collector, and how atomic operations ensure data consistency during concurrent memory relocation.

The Anatomy of a Brooks Pointer

In traditional stop-the-world garbage collectors, moving an object is straightforward because application threads (mutators) are suspended. When moving objects concurrently, the challenge lies in ensuring that mutator reads and writes land on the correct version of an object while it is being duplicated and updated.

Shenandoah solved this by allocating an additional reference slot—the Brooks pointer—immediately preceding the object's standard header. Under normal conditions (when no collection or evacuation is occurring), an object's Brooks pointer references the object itself.

[Brooks Pointer -> Points to Self] [Mark Word] [Klass Word] [Fields...]

Every read and write operation executed by the application dereferences this forward pointer to locate the active, canonical version of the object.

The Evacuation Phase and CAS Resolution

When Shenandoah identifies a region of memory to evacuate, both GC worker threads and application mutators can participate in copying objects from the source region ("from-space") to the destination region ("to-space"). Managing concurrent updates relies on a strict sequence governed by atomic Compare-And-Swap (CAS) instructions:

  1. Allocating and Copying: A thread allocates space in the to-space and copies the payload of the from-space object into it. Initially, the to-space copy's Brooks pointer points directly to itself.
  2. Atomic Installation: The thread attempts a hardware-level CAS operation to update the original from-space object's Brooks pointer. The operation changes the pointer from its original self-reference to the memory address of the new to-space copy.
  3. Race Resolution: Multiple threads might attempt to evacuate the same object simultaneously:
    • The thread that succeeds in the CAS operation establishes its copy as the single canonical version of the object.
    • Any thread that fails the CAS operation knows that another thread won the race. The losing thread immediately frees its newly allocated to-space copy and updates its local reference to use the winner's to-space address.

Once the CAS succeeds, the from-space object is retired, though its Brooks pointer remains active to forward any lingering references to the to-space copy.

Managing Concurrent Writes with Barriers

To prevent data corruption where an application thread updates an outdated from-space object after an evacuation has begun, Shenandoah uses compiler-inserted write barriers (specifically, JIT-compiled instructions preceding write operations).

When an application thread attempts to write to an object field:

  1. The write barrier inspects whether the object is in a region marked for evacuation.
  2. If the object must be evacuated and has not yet been moved, the mutator thread itself participates in the evacuation process before writing, copying the object and executing the CAS.
  3. Once the forward pointer safely points to the to-space instance, the barrier dereferences the Brooks pointer and performs the field modification directly on the to-space object.

This design guarantees that writes are never applied to a stale copy in from-space, eliminating the risk of lost updates without requiring global locks.

Managing Concurrent Reads

Shenandoah also inserted read barriers into compiled code. Whenever an application thread accessed a field or checked reference equality, the read barrier dereferenced the target's Brooks pointer. If the object had already been evacuated, the pointer routed the read directly to the up-to-date to-space copy. This ensured that regardless of thread interleaving, every operation was strictly linearizable and observed the most recent state.

Modern Successor: Load-Reference Barriers

While the Brooks pointer design successfully demonstrated production-ready concurrent compaction with pause times independent of heap size, it introduced an 8-byte memory overhead per object on 64-bit systems and increased the cost of read barriers. In later versions of OpenJDK (starting with Shenandoah 2.0 in OpenJDK 13+), the Brooks pointer design was replaced by Load-Reference Barriers (LRB), which perform forwarding via the standard object header and reference loads directly, eliminating the memory footprint penalty while preserving the concurrent update guarantees pioneered by the original design.
