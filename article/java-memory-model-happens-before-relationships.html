Java Memory Model Happens-Before Relationships

The Java Memory Model (JMM) relies on the "happens-before" relationship to guarantee memory visibility and execution ordering across multiple concurrent threads. Without these guarantees, modern compilers, Java Virtual Machines (JVMs), and multi-core processors may reorder instructions or cache variable values in registers, leading to data races and stale reads. This article explains what the happens-before relationship is, why it is essential for concurrent programming, and the specific program rules defined by the Java language specification that establish these ordering guarantees.

What is a Happens-Before Relationship?

In Java, a happens-before relationship between two operations, \(A\) and \(B\) (denoted as \(A \prec B\)), ensures that memory writes performed by operation \(A\) are guaranteed to be visible to operation \(B\). It also ensures that the execution of \(A\) completes logically before the execution of \(B\) begins.

If no happens-before relationship exists between a write operation and a subsequent read operation on the same variable, the JVM makes no guarantees about when the write will be visible to the reading thread, resulting in a data race.

The Core Happens-Before Rules

The Java Language Specification (JLS §17.4.5) defines a set of specific rules that automatically establish happens-before orderings:

1. Program Order Rule

Within an individual thread, each statement happens-before every statement that appears later in that thread's program source order. While the runtime or CPU may reorder instructions internally for performance, it may only do so if the observable outcome within that single thread does not change (the "as-if-serial" semantics).

2. Monitor Lock Rule

An unlock action on an intrinsic lock (such as exiting a synchronized block or method) happens-before every subsequent lock acquisition on that same monitor. Any modifications made by a thread before releasing a lock are flushed to main memory and made visible to whichever thread acquires that same lock next.

3. Volatile Variable Rule

A write to a volatile variable happens-before every subsequent read of that same volatile variable. Writes to volatile fields bypass thread-local CPU caches and write directly to main memory, while reads invalidate local caches and pull directly from main memory.

4. Thread Start Rule

A call to Thread.start() on a new thread happens-before any action executed by that started thread. Variables initialized by the parent thread prior to calling start() are guaranteed to be visible inside the child thread's run() method.

5. Thread Termination Rule

All actions inside a thread happen-before any other thread detects that the thread has terminated, whether by returning successfully from Thread.join() or by observing Thread.isAlive() return false.

6. Interruption Rule

A thread invoking interrupt() on another thread happens-before the interrupted thread detects that interruption, whether by catching an InterruptedException or by querying Thread.isInterrupted().

7. Finalizer and Final Fields Rules

  • Object Construction: The end of a constructor for an object happens-before the start of the finalizer for that object.
  • Safe Publication: An object with final fields whose reference is properly constructed and safely published ensures that any thread reading the object will observe the correctly initialized values of those final fields without explicit synchronization.

8. Transitivity

If operation \(A\) happens-before operation \(B\), and operation \(B\) happens-before operation \(C\), then operation \(A\) automatically happens-before operation \(C\).

How Transitivity Creates Visibility Guarantees

Transitivity allows developers to create synchronization guarantees without marking every single variable as volatile or wrapping every line in a synchronized block.

Consider the following scenario:

  1. Thread 1 updates normal variable x = 42.
  2. Thread 1 writes to volatile variable flag = true.
  3. Thread 2 reads flag == true.
  4. Thread 2 reads variable x.

By the Program Order Rule, writing x = 42 happens-before writing flag = true. By the Volatile Variable Rule, writing flag = true happens-before Thread 2 reading flag. By the Transitivity Rule, the write to x = 42 happens-before Thread 2 reads x. Consequently, Thread 2 is guaranteed to observe x as 42.
