Handling Split Packages When Moving to Java Modules

This article provides an overview of how Java handles split packages during the transition from the legacy classpath to the Java Platform Module System (JPMS). It explains why split packages worked transparently on the classpath, why the module system fundamentally prohibits them, how the runtime behaves when code resides across both the classpath and module path, and the practical strategies developers can use to resolve split package conflicts during migration.

What is a Split Package?

A split package occurs when two or more distinct JAR files contain classes within the exact same package hierarchy (for example, com.example.util.StringUtils in core.jar and com.example.util.DateUtils in extra.jar).

The Classpath Approach: Permissive by Design

The traditional Java classpath treats all dependencies as a flat, unindexed collection of classes:

  • First-Come, First-Served Resolution: When the JVM looks for a class, it iterates through the classpath sequentially and loads the first matching class file it finds.
  • No Integrity Checks: The classpath does not verify whether a package is fragmented across multiple JARs. It merges all classes sharing a package name into a single runtime view.
  • Unintended Consequences: This model can easily lead to classpath hell, where shadow classes, conflicting versions, or missing components cause non-deterministic runtime bugs.

The Module Path Approach: Strict Encapsulation

Introduced in Java 9, the Java Module System prioritizes strong encapsulation and reliable configuration:

  • Package Uniqueness: Every package must belong to exactly one named module.
  • Hard Failures: If the module system detects two named modules containing or exporting the same package, it fails fast at compile-time or JVM startup with an error such as java.lang.module.ResolutionException or LayerInstantiationException.

How the JVM Handles Split Packages Across Classpath and Modules

During migration, applications rarely move to the module system all at once. When a project uses both the classpath and the module path simultaneously, the JVM applies specific boundary rules:

  1. Both JARs on the Classpath:
    If both JARs remain on the classpath, they are assigned to the unnamed module. The legacy behavior continues uninterrupted, and the split package is permitted.

  2. One JAR on the Module Path, One on the Classpath:
    If a package exists in a named module on the module path and also exists in a JAR on the classpath:

    • The named module takes strict precedence.
    • The package portion inside the unnamed module (classpath) becomes hidden and inaccessible to the named module.
    • If code on the classpath attempts to access the classpath-version of the split package, runtime errors such as NoClassDefFoundError or ClassNotFoundException often occur because the module system resolves the package boundary strictly through the named module.

  3. Both JARs on the Module Path:
    The JVM immediately halts resolution. Two named modules—whether explicitly defined via module-info.java or automatically derived as automatic modules—cannot contain the same package.

Strategies to Resolve Split Packages

When migrating an application to Java modules, developers must resolve split packages using one of several approaches:

1. Package Refactoring

The most robust solution is to rename packages so that each module has a globally unique package structure (e.g., renaming com.example.util to com.example.core.util and com.example.extra.util).

2. Merging Artifacts

If two JARs are tightly coupled and split a package, combine them into a single JAR file and assign a single module-info.java descriptor.

3. Using the --patch-module Flag

For legacy or third-party dependencies that cannot be modified, the JVM provides the --patch-module command-line option. This flag merges classes from a directory or JAR into an existing target module at startup or compilation:

java --module-path mods --patch-module target.module=legacy-split.jar -m target.module/com.example.Main

--patch-module is intended primarily as a migration bridge or test utility and should not be relied upon as a permanent architectural design.

4. Leaving Split Libraries on the Classpath

If a third-party library relies heavily on split packages and cannot be patched easily, keep that dependency on the traditional classpath. Classes in the unnamed module can read all named modules, allowing legacy components to function while the rest of the application modernizes.
