How jdeps Analyzes Static Java Dependencies

This article explores how the Java Dependency Analysis Tool (jdeps) processes compiled bytecode to track and map static package-level relationships within Java applications. Introduced in Java 8 and enhanced in subsequent releases, jdeps operates directly on compiled .class files, JAR archives, or directories without running the code. The following sections explain the internal mechanics of how jdeps inspects bytecode, extracts package boundaries, surfaces modular dependencies, and navigates the limitations of static analysis.

Bytecode Parsing and Constant Pool Inspection

jdeps works by disassembling compiled Java class files and inspecting their constant pools. The constant pool acts as a symbol table for a compiled class, containing symbolic references to other classes, interfaces, field names, method signatures, and descriptors.

When jdeps scans a .class file, it parses the constant pool entries—specifically CONSTANT_Class_info, CONSTANT_Fieldref_info, CONSTANT_Methodref_info, and CONSTANT_InterfaceMethodref_info. It also scans the bytecode instructions within code attributes, identifying operations like new, anewarray, checkcast, instanceof, and various invoke* instructions (invokevirtual, invokestatic, invokespecial, invokeinterface). Furthermore, it extracts type signatures from method parameters, return types, generic signatures, exception specifications, and runtime-visible annotations.

Translating Class References to Package Dependencies

Every discovered class reference is stored internally as a fully qualified binary name (e.g., com/example/service/OrderService). To perform package-level analysis, jdeps strips the simple class name from the fully qualified name to determine the enclosing package (e.g., com.example.service).

jdeps aggregates these individual type references across every class file in the targeted scope:

  1. Source Package Identification: It determines the package of the class currently being analyzed.
  2. Target Package Identification: It groups all external classes referenced by that source class into their respective target packages.
  3. Graph Construction: It builds a directed dependency graph where nodes represent packages and directed edges represent references from a class in package A to a class in package B.

Package-Level Analysis Modes

jdeps provides specific CLI options to control the granularity of package inspection:

  • -verbose:package: Prints package-level dependencies, listing each source package and all target packages it relies on, alongside the target archive or module.
  • -package <name> or -p <name>: Restricts the output to dependencies originating from or pointing to a specific package or package pattern.
  • -filter:package: Filters out dependencies within the same package, highlighting only cross-package coupling.
  • -summary / -s: Collapses package details into a high-level overview of archive-to-archive or module-to-module dependencies.

For example, running:

jdeps -verbose:package -filter:package my-application.jar

instructs jdeps to inspect all .class files in my-application.jar, suppress intra-package dependencies, and display every distinct external package invoked by each local package.

Module and JDK Internal Dependency Detection

Beyond user-defined packages, jdeps compares referenced packages against the Java runtime's module system (java.base, java.sql, etc.). It cross-references target packages with JDK modules using the system's runtime image (jrt:/ filesystem).

A key utility of this mapping is detecting non-standard or encapsulated APIs. Using flags like --jdk-internals, jdeps flags package references pointing to internal JDK packages (such as sun.misc.*), often suggesting standard replacements available in modern Java versions.

The Limits of Static Analysis

Because jdeps relies entirely on static bytecode inspection, it only captures dependencies explicitly compiled into the binary. It cannot detect dynamic dependencies introduced at runtime through:

  • Reflection (Class.forName(...), Method.invoke(...))
  • Service-provider lookups (java.util.ServiceLoader) without declared module descriptors
  • Dynamic bytecode generation or runtime proxies (such as cglib or Byte Buddy)
  • Dependency injection frameworks that resolve implementations dynamically through external configuration

For static structures, however, jdeps provides a precise, deterministic map of compile-time package couplings across individual classes, libraries, and modular application layers.
