Java add-opens Flag Explained for Modular Apps

This article explores the purpose and functionality of the --add-opens command-line flag in the Java Platform Module System (JPMS). It covers why the flag was introduced in Java 9, how it overrides strong encapsulation to permit deep reflection on private members, the syntax required to use it, and how it differs from similar migration flags like --add-exports.

Strong Encapsulation in the Java Module System

Starting in Java 9, the Java Platform Module System introduced strong encapsulation by default. Under JPMS, a class cannot access non-public members (fields, methods, constructors) of a class in another module using reflection via setAccessible(true). Attempting to reflectively access these private internals without explicit permission results in an InaccessibleObjectException.

While strong encapsulation significantly improves application security and maintainability, it breaks many existing libraries and frameworks—such as Spring, Hibernate, Jackson, and Mockito—that rely heavily on "deep reflection" to inspect or manipulate private fields and methods.

What --add-opens Achieves

The --add-opens flag acts as a runtime override to JPMS boundaries. It instructs the Java Virtual Machine (JVM) to open a specific package within a module to another module, or to all unnamed code on the classpath, specifically for deep reflection at runtime.

When a package is "opened" using this flag:

  • Reflective access to all types and members (including private, protected, and package-private) within that package is granted.
  • Compile-time access is not granted; the compiler will still reject direct references to private members.
  • It achieves the same effect dynamically at launch time as declaring opens <package> inside a module-info.java file.

Syntax and Usage

The command-line syntax for the flag is:

--add-opens <source-module>/<package>=<target-module>(,<target-module>)*
  • <source-module>: The name of the module containing the code you want to open (e.g., java.base).
  • <package>: The specific package to open (e.g., java.lang).
  • <target-module>: The module that requires reflective access. If the dependent library resides on the traditional classpath rather than the module path, use ALL-UNNAMED.

Example: Opening a Core Java Package to the Classpath

If an older serialization library on the classpath requires access to private fields in java.lang:

java --add-opens java.base/java.lang=ALL-UNNAMED -jar my-application.jar

Example: Opening to a Specific Named Module

To open an internal package of your own module com.example.core exclusively to a testing module named com.example.test:

java --add-opens com.example.core/com.example.core.internal=com.example.test -jar app.jar

--add-opens vs. --add-exports

It is common to confuse --add-opens with --add-exports. They serve distinct access levels:

  • --add-exports: Exports a package, making only its public and protected types and members accessible at both compile time and runtime. It does not permit deep reflection on private members.
  • --add-opens: Opens a package exclusively for runtime deep reflection on all members (including private ones). It does not alter compile-time access.

When to Use --add-opens

The --add-opens flag is primarily intended as a migration aid and a workaround:

  1. Running Third-Party Frameworks: Allowing older frameworks that have not been updated for JPMS to inspect domain models or internal JDK types.
  2. Testing: Permitting test frameworks to inject mocks or inspect private state in modular environments without having to permanently modify production module-info.java definitions.

Using --add-opens should be considered a temporary measure. The preferred long-term solution is to update target libraries to versions that respect JPMS boundaries or to explicitly declare necessary opens directives inside the application's module-info.java descriptors.
