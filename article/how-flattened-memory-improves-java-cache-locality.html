How Flattened Memory Improves Java Cache Locality

This article explores how flattened in-memory data layouts enhance CPU cache locality for Java value objects. Traditional Java objects rely on reference-based memory models that create pointer indirection and scattered heap allocations, leading to frequent CPU cache misses. By eliminating object headers and storing data fields contiguously—an architecture introduced by Project Valhalla—flattened value objects allow modern CPU architectures to maximize cache line utilization, leverage hardware prefetchers, and significantly reduce memory access latency.

The Bottleneck of Traditional Java Memory

In the traditional Java Virtual Machine (JVM) model, every non-primitive entity is an identity object allocated on the heap. This architecture imposes two primary costs:

  1. Object Overhead: Every object requires metadata headers (the mark word and class word), typically consuming 8 to 16 bytes depending on compressed OOPs (Ordinary Object Pointers).
  2. Pointer Indirection: An array of objects, such as Point[], is stored as an array of 64-bit or 32-bit references pointing to disjoint memory locations scattered across the heap.

When a CPU executes operations over an array of standard objects, it must read a reference, traverse to that memory address, and load the payload into the CPU cache. Because heap allocations are rarely contiguous, sequentially reading these elements results in frequent CPU cache misses, forcing the processor to wait hundreds of cycles to fetch data from main memory.

What Is a Flattened In-Memory Data Layout?

A flattened data layout stores the internal fields of a value object directly within the enclosing structure, eliminating both the object reference and the object header.

Without identity (such as mutability, locking capabilities, or reference equality ==), a value object requires no header. When stored in an array or embedded inside another object, its primitive-like fields are inlined directly into contiguous memory.

For example, an array of two-dimensional points containing two 64-bit integers (long x, long y) transforms from an array of disparate memory pointers into a contiguous sequence of primitive values: [x0, y0, x1, y1, x2, y2, ...].

How Flattening Enhances CPU Cache Locality

CPUs do not read memory one byte or word at a time; they fetch data in fixed chunks called cache lines, which are typically 64 bytes wide. Flattening directly optimizes how these cache lines are populated and used.

1. Superior Spatial Locality

Spatial locality dictates that if a memory location is accessed, nearby memory locations are likely to be accessed soon.

  • Reference Arrays: Fetching a 64-byte cache line for a standard object array fills the cache primarily with memory pointers, not the actual object data. Loading the object's fields requires subsequent memory fetches to completely different addresses.
  • Flattened Arrays: A single 64-byte cache line fetch loads the actual payload of multiple consecutive value objects. For a 16-byte Point (two long values), a single cache line holds four complete objects. Iterating through the array consumes data already resident in L1 or L2 cache, minimizing trips to DRAM.

2. Predictable Hardware Prefetching

Modern CPU architectures feature aggressive hardware prefetchers that detect linear memory access patterns (strided access). When iterating through a flattened array, memory is read sequentially at a fixed stride. The CPU's stream prefetcher easily predicts the upcoming memory addresses and speculatively loads future cache lines from RAM into L3/L2/L1 caches before the execution pipeline even requests them. With pointer-based indirection, prefetchers struggle because memory addresses do not follow a predictable, sequential stride.

3. Increased Cache Density

CPU caches (L1, L2, L3) are strictly constrained in size. Standard Java objects waste valuable cache capacity by storing redundant object headers and reference addresses. Flattened value objects eliminate headers and pointers entirely, drastically reducing the overall memory footprint of data structures. Consequently, a fixed-size L1 cache (typically 32KB to 64KB per core) can hold significantly more domain data, reducing cache eviction rates and keeping hot working sets inside the fastest tiers of memory.

Summary

Flattened in-memory data layouts bridge the gap between Java’s high-level object-oriented abstractions and hardware-level performance. By removing identity, eliminating headers, and packing data fields contiguously, flattened value objects convert random pointer traversal into predictable, linear memory streams that fully leverage CPU cache hierarchies.
