Why Synchronization Pins Virtual Threads in Java

Virtual threads in Java, introduced via Project Loom, provide lightweight concurrency by unmounting from their underlying carrier threads during blocking operations. However, when a virtual thread acquires a monitor using the synchronized keyword, it becomes "pinned" to its carrier thread and cannot unmount during subsequent blocking tasks. This article explores the internal mechanisms that cause synchronization locks to pin virtual threads, the architectural limitations within the Java Virtual Machine (JVM) responsible for this behavior, and how developers can address the issue.

The Mechanism of Carrier Threads and Unmounting

Virtual threads are managed by the Java runtime rather than the underlying operating system. To execute code, the JVM mounts a virtual thread onto an OS-level platform thread known as a carrier thread. Under normal circumstances, when a virtual thread encounters a blocking operation—such as socket I/O, a sleep command, or blocking concurrent primitives—the runtime unmounts the virtual thread. Its stack frame is stored in the heap, freeing the carrier thread to execute other virtual threads.

Why the synchronized Keyword Causes Pinning

Pinning occurs primarily due to the internal architecture of HotSpot's object monitors. The synchronized construct relies on built-in JVM object monitors implemented in native C++ code rather than Java bytecode.

When a thread enters a synchronized block or method:

  1. Native Call Frames: HotSpot’s object monitor implementation links monitor ownership directly to the native execution stack of the carrier thread.
  2. Inability to Park the Stack: Because the native frame of the monitor is tied to the platform thread, the virtual thread scheduler cannot safely copy the call stack frames to the heap. Unmounting would corrupt the monitor’s internal ownership metadata.
  3. Forced Blocking: If the virtual thread initiates a blocking operation (such as blocking I/O) while holding an object monitor, the carrier thread cannot be released. Instead, the carrier thread itself blocks at the operating system level until the operation completes.

This phenomenon is not limited to synchronized; calling native code via the Java Native Interface (JNI) or the Foreign Function & Memory API also pins a virtual thread for identical reasons regarding native stack frames.

Performance Impact of Pinning

Occasional pinning for sub-millisecond computations does not severely degrade performance. The problem arises when a pinned thread executes long-running or blocking I/O tasks.

Because the default carrier thread pool size is scaled to the number of available CPU cores, pinning quickly exhausts available carrier threads. Once all carrier threads are tied up by pinned, blocked virtual threads, the entire application suffers from thread starvation, nullifying the high-throughput advantages of virtual concurrency.

Mitigating Pinning Issues

Developers can identify and eliminate synchronization-induced pinning using targeted practices:

  • Adopt ReentrantLock: Replace synchronized blocks with explicit locks from java.util.concurrent.locks, primarily ReentrantLock. Unlike object monitors, ReentrantLock is implemented in pure Java using AbstractQueuedSynchronizer (AQS). AQS park operations yield cleanly, allowing the virtual thread to unmount without pinning its carrier.
  • Detect Pinning with JVM Flags: Run applications with -Djdk.tracePinnedThreads=full or -Djdk.tracePinnedThreads=short to print stack traces whenever a virtual thread is pinned to its carrier.
  • JDK Improvements: Modern Java versions (beginning with enhancements in JEP 491) actively refactor HotSpot's object monitor infrastructure to allow virtual threads to unmount even while holding monitors, gradually eliminating synchronization-based pinning in newer runtime environments.
