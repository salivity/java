Java Exception Table: Mapping Bytecode to Handlers

In the Java Virtual Machine (JVM), exception handling does not rely on runtime branching instructions embedded directly within the normal execution path. Instead, the Java compiler records structural metadata within the class file known as the exception table. This table explicitly maps ranges of bytecode instruction offsets representing protected try blocks to the entry point offsets of their corresponding catch or finally blocks. This article breaks down the structure of the JVM exception table, how the runtime engine searches this table when an exception occurs, and how bytecode offsets determine execution flow.

Structure of the Exception Table

When a method containing try-catch or try-finally blocks is compiled, the compiler attaches an exception table to the method's Code attribute. The exception table is an array of entries, where each entry consists of four 16-bit fields:

  • start_pc: The inclusive starting offset in the method's bytecode array representing the beginning of the monitored range (the try block).
  • end_pc: The exclusive ending offset in the method's bytecode array where the monitored range terminates.
  • handler_pc: The bytecode offset designating the first instruction of the catch block that handles the specified exception.
  • catch_type: An index into the runtime constant pool pointing to a CONSTANT_Class_info structure that identifies the exception class. If the value is 0, the entry catches all exceptions, which is used to implement finally blocks and synchronized blocks.

The Offset Mapping and Lookup Mechanism

When an exception is thrown—either via the athrow bytecode instruction or through a native VM error—the execution engine initiates a dispatch process:

  1. Retrieve Current Offset: The JVM identifies the current program counter (PC), which corresponds to the exact bytecode offset of the instruction that triggered the exception.
  2. Sequential Range Verification: The JVM iterates through the exception table entries in top-to-bottom order. For each entry, it evaluates whether the current PC falls within the entry's defined interval: \[\text{start\_pc} \le \text{current\_pc} < \text{end\_pc}\]
  3. Type Evaluation: If the PC falls within the boundaries, the JVM resolves the catch_type:
    • If catch_type is non-zero, the JVM checks whether the thrown exception's class is an instance of the class referenced by catch_type (either the exact class or a subclass).
    • If catch_type is zero, the entry matches any exception unconditionally.
  4. Transfer of Control: Upon identifying the first entry that satisfies both the range and type conditions, the JVM clears the method’s operand stack, pushes the reference to the thrown exception object onto the empty stack, updates the program counter to the value of handler_pc, and resumes execution at that handler instruction.

Order and Precedence

The order of entries in the exception table is critical. The Java compiler writes entries to the table in the exact order that catch blocks are defined in the source code.

Because the JVM searches the table linearly and selects the first matching entry:

  • Subclasses must precede superclasses in the table (and in source code) to ensure more specific handlers execute before broader ones.
  • In nested try-catch structures, the innermost protected ranges appear earlier in the table than outer enclosing ranges, ensuring that inner handlers take precedence.

Unhandled Exceptions and Stack Unwinding

If the JVM iterates through the entire exception table of the current method without finding a matching [start_pc, end_pc) interval and compatible catch_type, the search within that method terminates. The JVM pops the current frame from the call stack, restoring the caller frame.

The JVM then reads the caller's program counter—the offset of the invoke* instruction that called the failed method—and initiates the same exception table lookup procedure within the caller's method code. This process repeats recursively until a match is found or the thread's call stack is exhausted.
