IdentityHashMap vs HashMap Comparisons in Java

In Java, the primary distinction between IdentityHashMap and a standard HashMap lies in how keys are compared and hashed. While a standard HashMap relies on object value equality using equals() and hashCode(), IdentityHashMap strictly enforces reference equality using the == operator and System.identityHashCode(). This fundamental difference alters how key collisions occur, how duplicate keys are identified, and how memory references are tracked throughout an application.

Key Equality: Reference (==) vs. Value (equals)

The most critical difference is the equality condition used to look up, insert, and remove entries:

  • Standard HashMap: Compares keys using k1 == null ? k2 == null : k1.equals(k2). If two distinct object instances have different memory addresses but represent the same logical value according to their overridden equals() method, HashMap treats them as the same key.
  • IdentityHashMap: Compares keys using reference identity: k1 == k2. Two keys are considered equal if and only if they point to the exact same memory location. Even if two objects evaluate to true with equals(), IdentityHashMap treats them as entirely separate keys if they are separate instances.

Hashing Mechanism: hashCode() vs. System.identityHashCode()

The hashing algorithm directly dictates bucket placement and collision handling:

  • Standard HashMap: Invokes key.hashCode(). If a class overrides this method, the custom hash code determines bucket placement. If the key's state changes and alters the hash code, the entry becomes unretrievable.
  • IdentityHashMap: Invokes System.identityHashCode(key). It ignores any custom hashCode() implementation defined on the object. Because System.identityHashCode() relies on the internal identity of the object (often based on memory address), the hash value remains consistent regardless of any internal state changes to the key.

Concrete Behavior with Objects and Strings

The practical impact of these differences is evident when handling newly instantiated objects and strings:

String key1 = new String("example");
String key2 = new String("example");

// Standard HashMap
Map<String, String> standardMap = new HashMap<>();
standardMap.put(key1, "First");
standardMap.put(key2, "Second");
// Result: standardMap.size() is 1 because key1.equals(key2) is true.

// IdentityHashMap
Map<String, String> identityMap = new IdentityHashMap<>();
identityMap.put(key1, "First");
identityMap.put(key2, "Second");
// Result: identityMap.size() is 2 because key1 != key2 (distinct memory references).

If string literals are used (e.g., "example"), the Java compiler interns them, causing key1 == key2 to evaluate to true. In that specific case, both map types would yield a size of 1.

Internal Data Structures

Beyond equality semantics, their internal architectures differ:

  • HashMap: Uses an array of buckets, where each bucket holds a linked list or a red-black tree (for high-collision buckets) containing node entries.
  • IdentityHashMap: Uses a flat, alternating array ([key1, val1, key2, val2, ...]) with linear probing. It does not use chained nodes or trees, prioritizing cache locality and fast reference checks.

Intentional Violation of the Map Interface

The Java Map interface is defined in terms of the equals() contract. Because IdentityHashMap uses == instead of equals(), it intentionally violates the general contract of the Map interface. It is not intended for general-purpose key-value storage.

When to Use Each

  • Use HashMap: For typical application logic where keys represent data values (e.g., IDs, names, or domain models) and need to be resolved based on logical equivalence.
  • Use IdentityHashMap: For specialized tasks such as serialization frameworks, object-graph traversals, or proxy maintenance, where it is necessary to track individual object instances uniquely—such as detecting circular references—regardless of their internal values.
