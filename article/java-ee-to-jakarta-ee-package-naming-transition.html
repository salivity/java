Java EE to Jakarta EE Package Naming Transition

The transition from Java EE to Jakarta EE marked one of the most significant architectural shifts in enterprise Java history, primarily defined by the mandatory renaming of package namespaces from javax.* to jakarta.*. When Oracle transferred governance of Java EE to the Eclipse Foundation, trademark constraints prevented the community from modifying existing javax packages. Consequently, Jakarta EE 9 executed a clean break by adopting the jakarta.* namespace across all standard APIs. This change required the entire Java ecosystem—including enterprise frameworks, runtimes, and application developers—to undertake substantial code updates, configuration revisions, and dependency realignments to maintain compatibility with modern Java platforms.

The Origin of the Namespace Conflict

In 2017, Oracle contributed Java EE to the open-source community under the stewardship of the Eclipse Foundation. While the technology specifications, codebases, and TCKs (Technology Compatibility Kits) were handed over, Oracle retained the legal rights to the "Java" trademark.

Negotiations between Oracle and the Eclipse Foundation concluded with an agreement that the community could not evolve specifications within the javax.* namespace. While existing APIs could remain untouched for legacy maintenance, any new features, bug fixes, or behavioral changes had to occur under a new namespace. To avoid creating a confusing, fragmented hybrid where legacy classes remained under javax.* while new additions moved elsewhere, the Jakarta EE Working Group opted for a complete, uniform migration to jakarta.*.

The "Big Bang" Shift in Jakarta EE 9

Jakarta EE 8 served as a transitional baseline, maintaining identical specifications and package names (javax.*) to Java EE 8 to prove the viability of the Eclipse Foundation's release process.

The structural break occurred in Jakarta EE 9 with the execution of the "Big Bang" approach. Rather than phasing the change over several releases, every enterprise package was renamed simultaneously. Key examples include:

  • javax.servlet.* transitioned to jakarta.servlet.*
  • javax.persistence.* transitioned to jakarta.persistence.*
  • javax.ws.rs.* transitioned to jakarta.ws.rs.*
  • javax.inject.* transitioned to jakarta.inject.*
  • javax.annotation.* transitioned to jakarta.annotation.*

Certain foundational APIs that resided within the core Java Standard Edition (Java SE), such as javax.sql.* and javax.crypto.*, remained unchanged because they were outside the scope of the enterprise transfer.

Impact on Frameworks and Runtimes

Because the namespace change broke binary compatibility, third-party libraries and runtime environments had to create distinct versions to support either the legacy or the modern specifications:

  • Application Servers and Web Containers: Apache Tomcat 9 (using javax.servlet) and Tomcat 10 (using jakarta.servlet) diverged, as did Jetty 11/12 and WildFly variants.
  • Frameworks: Spring Framework 6.0 and Spring Boot 3.0 made the transition mandatory, dropping all support for javax.* enterprise packages in favor of jakarta.*.
  • Object-Relational Mapping (ORM): Hibernate ORM 6 transitioned entirely to the jakarta.persistence namespace.

Consequences for Application Developers

The package migration introduced a hard boundary in Java development:

  1. Source Code Changes: Developers must rewrite all enterprise imports across their application codebases.
  2. Configuration Descriptors: Deployment descriptors, such as web.xml, persistence.xml, and beans.xml, required updated XML namespaces and schema references to point to the Eclipse Foundation specifications instead of Sun/Oracle schemas.
  3. Transitive Dependencies: Applications cannot easily mix libraries; a single third-party dependency still utilizing javax.* can fail at runtime in a modern jakarta.* container unless managed through bytecode transformation tools or compatibility layers.

To ease this friction, migration tools such as the Eclipse Transformer, OpenRewrite recipes, and built-in IDE refactoring actions were developed to automate import and configuration updates, allowing organizations to modernize legacy enterprise codebases for current runtimes.
