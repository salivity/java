Java Thread Dump Analysis and Thread States Guide

Thread dump analysis is a diagnostic technique used by software engineers to inspect the execution state of all active threads within a Java Virtual Machine (JVM) at a specific moment in time. This article explains the fundamentals of Java thread dump analysis, how it helps identify performance bottlenecks such as deadlocks and CPU spikes, and details the primary thread states defined in the Java specification that appear across stack traces.

What is Thread Dump Analysis?

A Java thread dump is a snapshot of the execution state of all threads running within a JVM process. Each thread entry in the dump reveals critical diagnostic data, including:

  • Thread identity: Thread name, thread ID (tid), native OS thread ID (nid), and priority.
  • Thread state: The operational condition of the thread based on the java.lang.Thread.State enum.
  • Stack trace: The exact sequence of method calls, line numbers, and lock synchronizations the thread was executing when the snapshot was taken.

Thread dump analysis involves examining one or multiple sequential thread dumps to diagnose runtime issues, such as application hangs, resource contention, deadlocks, and excessive CPU usage. Comparing multiple dumps taken a few seconds apart reveals whether threads are actively progressing or remaining permanently blocked on specific resources.

Java Thread States Identified in Stack Traces

The JVM categorizes every thread into one of six distinct lifecycle states. A thread dump explicitly records these states, allowing developers to understand application behavior at a glance.

1. NEW

A thread that has been instantiated using the new Thread() constructor but has not yet been started via its start() method. Threads in this state do not yet consume significant operating system resources and rarely appear in production thread dumps.

2. RUNNABLE

A thread that is actively executing in the JVM or is ready and waiting for its turn on the operating system's CPU processor.

  • Diagnostic meaning: If a high number of threads remain in the RUNNABLE state across multiple dumps and CPU utilization is near 100%, the application is likely suffering from inefficient algorithms, infinite loops, or heavy mathematical computation.

3. BLOCKED

A thread that is currently suspended, waiting to acquire an intrinsic monitor lock (synchronized block or method) that is currently held by another thread.

  • Diagnostic meaning: A single thread in the BLOCKED state is normal in concurrent environments. However, a large cluster of threads blocked on the same memory address indicates severe lock contention. If two or more threads are mutually waiting on locks held by one another, this signals a deadlock condition.

4. WAITING

A thread that is waiting indefinitely for another thread to perform a specific action before it can resume execution. A thread enters this state by calling:

  • Object.wait() without a timeout

  • Thread.join() without a timeout

  • LockSupport.park()

  • Diagnostic meaning: Threads in thread pools often remain in the WAITING state when there are no incoming tasks in the queue. If application threads remain unexpectedly in this state, it may indicate a missing notify() call, an unreleased lock, or an incomplete asynchronous task.

5. TIMED_WAITING

A thread that is paused for a specified duration, waiting for a timeout to elapse or for an explicit signal from another thread. Common triggers include:

  • Thread.sleep(millis)

  • Object.wait(timeout)

  • Thread.join(timeout)

  • LockSupport.parkNanos() or LockSupport.parkUntil()

  • Diagnostic meaning: Many threads (such as scheduler workers, background pollers, or database connection pools) naturally spend time in TIMED_WAITING. If threads unexpectedly pile up in this state while waiting on I/O operations or network calls, it points to external service latency or missing timeout configurations.

6. TERMINATED

A thread that has completed its execution, either by returning successfully from its run() method or by throwing an unhandled exception. These threads have released their allocated stack memory and native resources.

Common Issues Identified During Analysis

  • Deadlocks: Multiple threads in BLOCKED or WAITING states holding circular dependencies on resources. Most modern thread dumps automatically append a "Found one Java-level deadlock" section at the bottom.
  • Thread Leaks: An ever-increasing thread count dominated by TIMED_WAITING or RUNNABLE states, often caused by unmanaged thread creation rather than using bounded thread pools.
  • Database/Network Bottlenecks: Threads stuck in RUNNABLE or TIMED_WAITING performing socket read operations (java.net.SocketInputStream.socketRead0), indicating slow downstream dependencies.
