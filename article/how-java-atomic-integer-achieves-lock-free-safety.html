How Java AtomicInteger Achieves Lock-Free Safety

This article explains how the Java AtomicInteger class achieves thread safety without using traditional synchronization locks. It covers the mechanics of hardware-level Compare-and-Swap (CAS) instructions, the role of memory visibility via the volatile keyword, and how optimistic retry loops enable high-performance, non-blocking concurrent operations.

The Cost of Traditional Locking

In concurrent programming, ensuring that multiple threads safely modify a shared integer typically requires synchronization primitives like synchronized blocks or ReentrantLock. While effective, these mechanisms rely on pessimistic locking. When a thread encounters a locked resource, the operating system may suspend the thread, causing an expensive context switch. When the resource becomes available, the thread must be woken up and rescheduled. For high-throughput, low-latency applications, this overhead significantly degrades performance.

The Foundation: The Volatile Value

To provide lock-free thread safety, AtomicInteger maintains its underlying state using a single primitive integer variable:

private volatile int value;

The volatile keyword ensures memory visibility across CPU caches. According to the Java Memory Model (JMM), writes to a volatile variable establish a happens-before relationship with subsequent reads. This guarantees that any thread reading value immediately observes the most recent update made by another thread, avoiding stale data caused by local CPU core caching.

However, volatile alone does not make compound operations—such as read-modify-write (e.g., value++)—atomic. That is where Compare-and-Swap comes into play.

Hardware-Level Compare-and-Swap (CAS)

Compare-and-Swap (CAS) is an atomic CPU-level instruction (such as CMPXCHG on x86 architectures) supported directly by modern processors. It operates using three operands:

  1. Memory Location (\(V\)): The address where the value is stored.
  2. Expected Old Value (\(A\)): The value the calling thread believes is currently at \(V\).
  3. New Value (\(B\)): The updated value to store at \(V\).

The processor evaluates the memory location atomically: if the current value at \(V\) equals the expected value \(A\), it updates \(V\) with \(B\) and signals success. If another thread has modified the value at \(V\) in the interim, the comparison fails, the memory remains untouched, and the instruction signals failure. Because this check and update happen in a single, indivisible hardware step, no locks are required.

Low-Level Access: Unsafe and VarHandle

Java code running in the JVM cannot directly execute CPU instructions. Historically, AtomicInteger bridged this gap using sun.misc.Unsafe, which provides low-level, hardware-near operations. In modern Java versions (Java 9 and later), this functionality is managed internally through java.lang.invoke.VarHandle.

The class calculates the exact memory offset of the value field within the AtomicInteger instance during initialization:

private static final long VALUE = U.objectFieldOffset(AtomicInteger.class, "value");

Using this memory offset, the internal low-level API exposes methods like compareAndSetInt, which translate directly into the platform's atomic CAS machine instructions.

The Optimistic CAS Loop

Instead of blocking threads, AtomicInteger employs an optimistic concurrency control strategy known as a CAS loop (or spin-retry loop). Operations assume no contention will occur, attempt the update, and retry if contention is detected.

Consider the implementation of an increment operation:

public final int incrementAndGet() {
    return U.getAndAddInt(this, VALUE, 1) + 1;
}

Under the hood in the JVM, the logic inside getAndAddInt resembles the following loop:

int current;
do {
    current = this.getIntVolatile(o, offset);
} while (!this.compareAndSetInt(o, offset, current, current + 1));

The workflow proceeds as follows:

  1. The thread reads the current volatile value from memory.
  2. The thread computes the updated value (current + 1).
  3. The thread attempts to write the new value using compareAndSetInt.
  4. If the value has not changed since step 1, the CAS instruction succeeds, the loop terminates, and the operation returns.
  5. If another thread updated the value between steps 1 and 3, the CAS instruction fails. The loop discards the computation, reads the updated value, and tries again immediately.

Performance Characteristics and Trade-Offs

By eliminating thread blocking, AtomicInteger prevents thread descheduling, kernel context switches, and deadlocks. This makes it significantly faster than lock-based synchronization under low to moderate thread contention.

However, the CAS approach has distinct trade-offs:

  • High Contention Overhead: If many threads continuously attempt to modify the same AtomicInteger, multiple threads will spin in retry loops, consuming CPU cycles without making progress. In such high-contention scenarios, classes like LongAdder (which divide work across cells) are preferable.
  • The ABA Problem: A CAS operation checks whether a value is still \(A\), but cannot detect if the value changed from \(A\) to \(B\) and then back to \(A\). While this does not impact simple numeric counters, it can corrupt complex linked data structures. In Java, this edge case is solved using AtomicStampedReference.
