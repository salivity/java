Optimistic Locking in Java with @Version

Optimistic locking in Java manages concurrent database modifications without acquiring costly database-level locks during read operations. By using the @Version annotation provided by Jakarta Persistence (JPA) and Hibernate, an application tracks an entity's state changes using an internal counter or timestamp. This mechanism prevents the "lost update" problem by detecting conflicting writes at commit time and automatically aborting transactions that attempt to overwrite newer data.

The Mechanism Behind @Version

Optimistic locking operates on the assumption that data conflicts are infrequent. Instead of locking a record when it is read (pessimistic locking), the application verifies that no other transaction has modified the entity between the time it was read and the time it is updated.

To enable this behavior, JPA requires an entity to designate a version attribute using the @Version annotation:

import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.Version;

@Entity
public class Product {

    @Id
    private Long id;

    private String name;

    private Double price;

    @Version
    private Long version;

    // Getters and setters omitted
}

The version field can be an int, Integer, short, Short, long, Long, or java.sql.Timestamp. Numeric types are strongly recommended because timestamps rely on system clocks, which may lack sufficient resolution in high-throughput environments.

How Concurrent Updates Are Handled at the Database Level

When an entity with a @Version field is modified, the persistence provider automatically appends the version check to the generated SQL UPDATE statement and increments the version value.

For example, when an entity with id = 1 and version = 3 is updated, the provider executes:

UPDATE Product 
SET name = 'New Name', price = 19.99, version = 4 
WHERE id = 1 AND version = 3;

If two transactions, Transaction A and Transaction B, concurrently read the same product with version = 3:

  1. Transaction A completes first: It issues the UPDATE query matching version = 3. The database updates the row and sets version = 4. The database returns an updated row count of 1.
  2. Transaction B attempts to update: It attempts to execute its update using the initial state it loaded (version = 3). However, the database row now has version = 4.
  3. Detection: Because the WHERE clause condition version = 3 is no longer met, the database updates 0 rows.
  4. Failure Trigger: The persistence provider expects exactly 1 affected row. Seeing 0 affected rows, it determines that a concurrent modification occurred and rolls back Transaction B.

Exception Handling and Recovery

When the row count check fails, JPA immediately throws an OptimisticLockException (which Spring translates into an ObjectOptimisticLockingFailureException).

Applications typically handle this exception in one of two ways:

  • Automatic Retries: For automated processes, the application catches the exception, reloads the fresh entity state with the updated version from the database, re-applies the business logic, and attempts the commit again. In Spring-based applications, this can be automated using annotations like @Retryable.
  • User Notification: For user-facing forms, the application alerts the user that another user or process updated the record while they were viewing it, prompting them to refresh the page and review the changes before resubmitting.

When to Use Optimistic Locking

Optimistic locking is ideal for systems with high read-to-write ratios and low-to-medium contention. Because it avoids holding open database locks while transactions are in progress, it reduces database connection pool exhaustion, maximizes throughput, and prevents deadlocks. If a system experiences high contention where multiple workers constantly update the same rows, pessimistic locking is typically preferred to avoid the overhead of repeated rollbacks and retries.
