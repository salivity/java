Collections.unmodifiableList vs List.of in Java

In modern Java, both Collections.unmodifiableList and List.of are used to prevent modifications to collections, but they serve fundamentally different architectural purposes. While Collections.unmodifiableList provides a read-only wrapper around an existing, potentially mutable backing list, List.of produces a truly immutable, standalone collection with strict constraints on null values and optimized memory usage. Choosing the correct approach depends on whether you require a dynamic read-only view of mutable data or a fixed, thread-safe snapshot.

Unmodifiable View vs. Truly Immutable

The primary distinction between the two approaches lies in how they handle mutability:

  • Collections.unmodifiableList (A View): This method does not create an independent copy. It wraps an existing list in an adapter that throws an UnsupportedOperationException if modification methods like add() or remove() are invoked directly on the wrapper. However, if the underlying list changes, those changes are immediately visible through the unmodifiable wrapper. Consequently, it is not truly immutable.
  • List.of (Truly Immutable): Introduced in Java 9, List.of produces an internal, proprietary implementation that cannot be modified under any circumstances. It does not wrap an external collection; instead, it holds its own elements. There is no underlying reference that can be altered to change its state.

Null Value Handling

Null handling differs strictly between the two options:

  • Collections.unmodifiableList: It permits null values as long as the underlying list permits them (e.g., an ArrayList).
  • List.of: It strictly prohibits null elements. Passing null to List.of immediately results in a NullPointerException. This enforces modern Java best practices regarding null safety.

Memory and Performance

List.of is substantially more efficient in terms of memory footprint and execution speed:

  • Optimized Internal Representations: For lists with zero, one, or two elements, List.of uses specialized internal classes (List0, List1, List2) that avoid allocating an internal array altogether, storing elements directly in fields.
  • Reduced Overhead: Using Collections.unmodifiableList requires allocating both the underlying collection (such as an ArrayList) and the wrapper object itself, leading to higher garbage collection overhead and memory consumption.

Defensive Copying with List.copyOf

Before Java 10, creating a safe, unmodifiable copy of an existing collection required manual duplication:

List<String> defensiveCopy = Collections.unmodifiableList(new ArrayList<>(originalList));

Java 10 introduced List.copyOf(Collection<? extends E> coll), which combines the safety of an immutable list with performance optimizations. If the collection passed to List.copyOf is already an unmodifiable list produced by the factory methods, it returns the collection itself without re-allocating memory.

Choosing the Right Approach

  • Use List.of: When instantiating new, fixed collections with known elements, or when designing APIs where data integrity, immutability, and thread safety are required.
  • Use List.copyOf: When you need a defensive, immutable snapshot of an existing collection.
  • Use Collections.unmodifiableList: Primarily when maintaining legacy codebases prior to Java 9, when you intentionally need to expose a live, read-only window into a list that updates elsewhere, or when elements must contain null values.
