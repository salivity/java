How Carrier Threads Run Java Virtual Threads

Java virtual threads are lightweight concurrency primitives designed to dramatically increase application throughput by decoupling Java threads from underlying operating system threads. Instead of assigning each thread directly to an OS thread, the Java runtime manages virtual threads internally and executes them on a small pool of standard platform threads known as carrier threads. This article explains how the Java runtime schedules virtual threads using an internal ForkJoinPool, how threads mount and unmount from carrier threads during blocking operations, and how thread state is preserved across transitions.

The Role of Carrier Threads

A carrier thread is simply a standard platform thread (which maps 1:1 to an operating system thread) that temporarily "carries" a virtual thread to execute its bytecode. The virtual thread represents the actual task, holding its own call stack and execution state, while the carrier thread provides the physical CPU execution context.

From the perspective of running code, the virtual thread is unaware of which carrier thread is executing it. The Thread.currentThread() API returns the virtual thread instance, not the underlying carrier thread.

The Work-Stealing Scheduler

By default, the Java runtime schedules virtual threads using a dedicated ForkJoinPool configured in FIFO (first-in, first-out) mode. The scheduler operates with a parallelism level matching the number of available CPU cores by default, though this can be tuned via system properties.

Each worker thread in this pool acts as a carrier thread. Tasks submitted to the scheduler are the continuation tasks of virtual threads. When a virtual thread is ready to execute, its continuation is placed into the scheduler's task queues, where carrier threads pick it up using standard work-stealing algorithms.

Mounting and Execution

The process of binding a virtual thread to a carrier thread is called mounting:

  1. Scheduling: When a virtual thread transitions to a runnable state, it is enqueued in the scheduler.
  2. Mounting: An available carrier thread picks up the virtual thread. The runtime loads the virtual thread's stack frames from the Java heap onto the carrier thread's native execution stack.
  3. Execution: The carrier thread runs the virtual thread's bytecode instructions until the task either finishes or encounters a blocking operation.

Unmounting During Blocking Operations

The primary advantage of virtual threads is their ability to yield execution when encountering blocking calls without blocking the underlying OS thread:

  1. Yielding: When a virtual thread performs a blocking I/O operation, waits for a lock, or invokes Thread.sleep(), the runtime intercepts the operation via low-level continuation primitives.
  2. State Preservation: The virtual thread yields. Its call stack frames are evacuated from the carrier thread's native stack and saved back into the heap.
  3. Unmounting: The virtual thread detaches from the carrier thread.
  4. Reusing the Carrier: The carrier thread is now completely free to take another runnable virtual thread from the scheduler's queue and execute it immediately.

Resuming and Remounting

When the event the virtual thread was waiting for finishes (such as network data arriving on a non-blocking socket poll), the runtime marks the virtual thread as runnable again.

The virtual thread is resubmitted to the ForkJoinPool work queue. When any carrier thread becomes available, it mounts the virtual thread, restores its execution stack from the heap, and resumes execution from the exact instruction where it yielded. Notably, a virtual thread does not have thread affinity; it may resume execution on a completely different carrier thread than the one it started on.

Thread Pinning Exceptions

In certain edge cases, a virtual thread cannot be unmounted when it blocks, a state known as pinning. Pinning occurs when:

  • The virtual thread executes inside a synchronized block or method.
  • The virtual thread executes a native method or a foreign function call.

When a pinned virtual thread blocks, it cannot evacuate its stack to the heap. Consequently, its carrier thread remains blocked alongside it, temporarily reducing the scheduler's capacity until the operation completes or the scheduler compensates by creating additional carrier threads. Replacing synchronized blocks with java.util.concurrent.locks.ReentrantLock resolves this limitation and ensures normal unmounting behavior.
