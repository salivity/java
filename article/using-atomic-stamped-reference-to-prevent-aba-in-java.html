Using AtomicStampedReference to Prevent ABA in Java

In concurrent programming, non-blocking data structures rely on Compare-And-Swap (CAS) operations to achieve lock-free thread safety. However, standard CAS operations are vulnerable to the ABA problem, where a memory location is read as value A, modified to B, and restored back to A, causing a thread to mistakenly assume no changes have occurred. Java addresses this issue with the AtomicStampedReference class, which pairs an object reference with an integer "stamp" acting as a version counter. By requiring both the reference and the stamp to match before an update can succeed, non-blocking algorithms can reliably detect intermediate state changes and maintain data integrity.

Understanding the ABA Problem

The ABA problem typically arises in memory management and lock-free data structures like stacks and queues. Consider a scenario involving a lock-free stack using a standard AtomicReference:

  1. Thread 1 reads the top of the stack, finding node A. Node A points to node B.
  2. Before Thread 1 can execute its CAS operation, it is preempted.
  3. Thread 2 pops node A, pops node B, and then pushes node A back onto the stack (or allocates a new node that reuses memory address A).
  4. Thread 1 resumes and performs compareAndSet(A, B). Because the reference still points to A, the CAS succeeds.
  5. The stack's top is set to B, even though B may have already been freed, modified, or placed into an inconsistent state.

Standard CAS checks value equality (or reference equality in Java), not whether the value was modified and restored in the interim.

How AtomicStampedReference Works

AtomicStampedReference resolves this vulnerability by encapsulating an object reference and an integer stamp into an immutable internal pair. When performing an update, both components must match their expected values simultaneously.

Its signature method is:

public boolean compareAndSet(V expectedReference,
                             V newReference,
                             int expectedStamp,
                             int newStamp)

The update succeeds only if:

  1. expectedReference == currentReference
  2. expectedStamp == currentStamp

If either condition is false, the CAS fails, signaling to the calling thread that concurrent modifications occurred.

Implementing Non-Blocking Algorithms with Stamps

To integrate AtomicStampedReference into a non-blocking algorithm, threads maintain both the reference and the version counter throughout the operation lifecycle:

  1. Read Current State: A thread retrieves both the current reference and its associated stamp. Because Java methods can return only one value, AtomicStampedReference provides a method where the stamp is returned via an array parameter:

    int[] stampHolder = new int[1];
Node currentTop = atomicStampedRef.get(stampHolder);
int currentStamp = stampHolder[0];

  2. Compute New State: The thread prepares the next node reference and computes the next stamp, typically by incrementing the current stamp (currentStamp + 1).

  3. Execute CAS: The thread executes compareAndSet:

    boolean success = atomicStampedRef.compareAndSet(
    currentTop, 
    newTop, 
    currentStamp, 
    currentStamp + 1
);

  4. Retry Loop: If compareAndSet returns false, the operation retries from step 1, reading the new reference and updated stamp.

Practical Impact

By incrementing the stamp on every write, a state transition from A to B and back to A creates a progression of stamps (e.g., (A, 0) -> (B, 1) -> (A, 2)). When a lagging thread attempts to complete an operation with the outdated stamp 0, the CAS fails immediately because the reference matches A, but the stamp 0 does not match 2.

This mechanism allows non-blocking algorithms to recycle nodes and handle transient states safely without introducing blocking synchronizations or locks.
