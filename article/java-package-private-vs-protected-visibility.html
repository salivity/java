Java Package-Private vs Protected Visibility

This article examines how Java enforces package-private (default) visibility compared to protected visibility, outlining the architectural and operational differences between the two access levels. It explores the scope of each modifier, how the Java compiler validates these boundaries at build time, and how the Java Virtual Machine (JVM) maintains access restrictions at runtime during class loading and bytecode execution.

Access Scopes Defined

In Java, access modifiers determine whether a class, field, or method can be referenced by other types.

  • Package-Private (Default): When no access modifier is declared, a member is package-private. It is accessible only by classes residing in the exact same package. Subclasses defined outside of this package have no access to these members.
  • Protected: Declared using the protected keyword, this level grants the same access as package-private (allowing any class within the same package to access the member) while also extending access to subclasses located in different packages.

Enforcement at Compile Time

The Java compiler (javac) serves as the first line of enforcement by checking access rules against symbol tables generated during parsing:

  1. Package-Private Checks: If a class attempts to access a package-private member, the compiler checks the fully qualified package name of both the calling class and the target class. If the package strings do not match identically, the compiler halts with an error stating that the member is not public and cannot be accessed from outside the package.
  2. Protected Checks: For protected members, the compiler permits access if the caller shares the package. If the caller is in a different package, the compiler verifies that the calling class is an inheritor (subclass) of the declaring class. Furthermore, the compiler strictly enforces that access through a reference must be of the subclass type (or one of its descendants), rather than a direct reference to a generic superclass instance. This prevents unrelated code from bypassing package boundaries simply by operating inside a subclass.

Enforcement at Runtime by the JVM

Java does not rely solely on the compiler; access rules are enforced directly inside the JVM to prevent unauthorized access via manually altered bytecode or runtime manipulation.

  • Class File Access Flags: Inside the compiled .class file, every field, method, and class contains an access flags bitmask. A protected member is marked with the ACC_PROTECTED flag. A package-private member is denoted by the absence of ACC_PUBLIC, ACC_PRIVATE, and ACC_PROTECTED.
  • Bytecode Resolution: When executing instructions such as invokevirtual, getfield, or putfield, the JVM dynamically resolves symbolic references. During resolution, the JVM checks the runtime package (defined by the package name combined with the defining ClassLoader) and the class inheritance hierarchy.
  • Runtime Verification Failures: If bytecode attempts to call a package-private member from outside its runtime package, or a protected member without satisfying the subclass relationship, the JVM throws an IllegalAccessError.

Through this dual-layer verification—combining compiler-level symbol resolution with bytecode flag validation in the JVM—Java maintains strict isolation boundaries for package-private encapsulation while allowing controlled extensibility for protected members.
