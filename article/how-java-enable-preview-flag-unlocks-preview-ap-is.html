How Java enable-preview Flag Unlocks Preview APIs

The --enable-preview flag in Java provides a controlled mechanism for developers to test upcoming, non-final language features and APIs before they become permanent components of the Java platform. By requiring this flag at both compile time and runtime, the Java Virtual Machine (JVM) prevents experimental code from inadvertently running in production environments. This article details the internal mechanics of how the flag functions, how class file versioning enforces preview boundaries, and how the runtime gates access to experimental APIs.

The Lifecycle of Preview Features

Preview features are fully specified and fully implemented language changes, JVM modifications, or API additions introduced to gather real-world developer feedback. Because these features are subject to breaking changes or complete removal in subsequent releases, they are strictly quarantined. The --enable-preview flag serves as the explicit opt-in mechanism required to interact with this quarantined code.

Compile-Time Enforcement

Access to preview APIs begins during the compilation phase with javac. To use a preview API or language feature, you must compile your source code using both the target release version and the preview flag:

javac --release <version> --enable-preview YourClass.java

When javac compiles code with --enable-preview, it modifies the compiled bytecode's binary header:

  1. Major Version: Corresponds to the specific Java version (for example, Java 21 uses major version 65).
  2. Minor Version: Rather than using the standard minor version 0, javac sets the minor version to 65535 (0xFFFF).

This special minor version permanently marks the .class file as a preview artifact tied directly to that specific major Java release.

Runtime Verification and Class Loading

When launching an application using java, the JVM’s class verifier reads the bytecode header before loading any class file into memory:

  1. Header Inspection: The class loader inspects the major and minor version numbers of the incoming .class file.
  2. Flag Check: If the minor version is detected as 65535, the JVM checks whether the --enable-preview flag was provided on the command line.
  3. Execution or Rejection:
    • If --enable-preview is present and the major version matches the JVM’s version, the class is loaded, verified, and executed.
    • If the flag is missing, the JVM immediately terminates the class loading process and throws an UnsupportedClassVersionError, stating that preview features are not enabled.

Because preview bytecode is tied to an exact major version, a preview class compiled on one Java version will not run on a newer Java version, even if --enable-preview is supplied. The code must be recompiled for the newer runtime.

API-Level Gating with @PreviewFeature

At the library level, preview classes, methods, and fields inside the Java standard library are annotated with the internal @PreviewFeature annotation.

During compilation, javac consults this metadata:

  • If a program references an element marked with @PreviewFeature without the --enable-preview compiler flag, the compiler raises a compilation error.
  • When both --enable-preview and a compatible --release or -source value are present, the compiler allows the symbol resolution, issues a preview warning, and tags the generated bytecode with the preview minor version.

Through this combination of binary file tagging, strict class loader checks, and metadata-driven compilation, the --enable-preview command-line flag ensures experimental APIs remain strictly isolated until they are standardized.
