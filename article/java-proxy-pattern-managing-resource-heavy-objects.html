Java Proxy Pattern: Managing Resource-Heavy Objects

This article provides an overview of the Proxy design pattern and its practical application in Java. It explores how developers can utilize the Virtual Proxy variant to control access, optimize memory consumption, and implement lazy loading for resource-intensive objects such as large files, remote network services, and expensive database connections.

Understanding the Proxy Pattern

The Proxy pattern is a structural design pattern that provides a surrogate or placeholder for another object to control access to it. Instead of a client directly instantiating and calling methods on an object, the client communicates with a proxy object that implements the exact same interface. The proxy intercepts calls, performs ancillary operations (such as authentication, caching, or deferred loading), and forwards the request to the underlying target object when necessary.

The Problem with Resource-Heavy Objects

In enterprise Java applications, certain objects require significant system resources:

  • Memory footprint: Storing large datasets, high-resolution multimedia, or deep object graphs.
  • Initialization overhead: Establishing database connections, parsing massive XML/JSON files, or initializing cryptographic contexts.
  • Network latency: Communicating with remote microservices or external APIs.

Instantiating these objects eagerly upon application startup degrades performance and consumes memory needlessly, especially if the user never accesses the functionality associated with those objects.

The Virtual Proxy Solution

A Virtual Proxy delays the creation and initialization of an expensive resource until the moment it is actually required (lazy initialization). It acts as a lightweight stand-in. When a method is called that requires the actual resource, the proxy checks whether the real object exists. If not, it instantiates the heavy object and then delegates the method call.

Java Implementation

To implement the Proxy pattern, both the real subject and the proxy must implement a common interface.

1. The Common Interface

public interface DocumentViewer {
    void display();
}

2. The Real Subject (Resource-Heavy Object)

The RealDocumentViewer loads a large document into memory during initialization, representing an expensive operation.

public class RealDocumentViewer implements DocumentViewer {
    private final String fileName;

    public RealDocumentViewer(String fileName) {
        this.fileName = fileName;
        loadFromDisk();
    }

    private void loadFromDisk() {
        System.out.println("Loading heavy file from disk: " + fileName);
        // Simulating heavy I/O or memory allocation
        try {
            Thread.sleep(2000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    @Override
    public void display() {
        System.out.println("Displaying document: " + fileName);
    }
}

3. The Proxy Object

The ProxyDocumentViewer maintains a reference to the RealDocumentViewer. It delays instantiation until display() is called.

public class ProxyDocumentViewer implements DocumentViewer {
    private final String fileName;
    private RealDocumentViewer realDocumentViewer;

    public ProxyDocumentViewer(String fileName) {
        this.fileName = fileName;
    }

    @Override
    public void display() {
        if (realDocumentViewer == null) {
            realDocumentViewer = new RealDocumentViewer(fileName);
        }
        realDocumentViewer.display();
    }
}

4. Client Usage

public class Client {
    public static void main(String[] args) {
        // Instant creation; heavy object is not yet loaded into memory
        DocumentViewer viewer = new ProxyDocumentViewer("massive_archive.pdf");

        System.out.println("Application started. Proxy instantiated.");

        // Heavy object is loaded only when the method is invoked
        viewer.display();

        // Subsequent calls reuse the already instantiated object
        viewer.display();
    }
}

Key Benefits

  • Lazy Initialization: Reduces initial startup time and avoids allocating memory for objects that might not be used during execution.
  • Separation of Concerns: Business logic remains inside the real subject, while the proxy encapsulates management, access control, and caching policies.
  • Client Transparency: Because both classes implement the same interface, client code does not need modification to switch between direct and proxied access.
