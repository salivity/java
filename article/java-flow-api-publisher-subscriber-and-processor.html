Java Flow API: Publisher, Subscriber, and Processor

The Java Flow API, introduced in Java 9, provides an official implementation of the Reactive Streams specification to handle asynchronous, non-blocking data streams with backpressure. This article examines the four core interfaces within the java.util.concurrent.Flow class—Publisher, Subscriber, Subscription, and Processor—explaining their distinct responsibilities and how they collaborate to manage data flow predictably without overwhelming downstream consumers.

Publisher: The Data Source

The Flow.Publisher<T> acts as the provider or producer of data. Its primary responsibility is to emit items of type T to registered subscribers based on their requested demand.

A Publisher exposes a single method:

  • void subscribe(Flow.Subscriber<? super T> subscriber): Registers a new subscriber to receive events.

The Publisher does not push data arbitrarily. Instead, it respects the rate at which the subscriber can process items, ensuring that the source does not flood the receiving end with unmanageable volumes of data.

Subscriber: The Data Consumer

The Flow.Subscriber<T> is the recipient or consumer of the stream. It receives items sequentially, handles errors, and reacts to stream completion.

The interface defines four lifecycle callback methods:

  • void onSubscribe(Flow.Subscription subscription): Invoked automatically by the Publisher when registration succeeds, passing a Subscription token.
  • void onNext(T item): Invoked whenever a new data item is delivered.
  • void onError(Throwable throwable): Invoked when the Publisher encounters an unrecoverable error, terminating the stream.
  • void onComplete(): Invoked when the Publisher has finished sending all items, signaling normal stream completion.

The Subscriber is responsible for initiating data requests through the Subscription it receives during setup.

Subscription: The Backpressure Controller

The Flow.Subscription represents the active connection between a single Publisher and a single Subscriber. It serves as the primary mechanism for backpressure, placing the control of data velocity directly into the consumer's hands.

The interface includes two control methods:

  • void request(long n): Instructs the Publisher to emit up to n additional items. The Publisher must not send more items than requested.
  • void cancel(): Informs the Publisher to stop sending data and clean up resources, terminating the connection.

By requiring the Subscriber to explicitly invoke request(n), the system prevents consumer memory exhaustion.

Processor: The Intermediate Transformer

The Flow.Processor<T, R> extends both Flow.Subscriber<T> and Flow.Publisher<R>. It acts as a middleman or transformation stage in a reactive pipeline, consuming data of type T, applying operations such as filtering, mapping, or aggregating, and publishing the resulting data of type R to downstream subscribers.

Because it fulfills both contracts, a Processor must properly forward backpressure demands upstream while honoring the delivery expectations of downstream consumers.

How the Components Interact

The standard lifecycle between these components follows a structured sequence:

  1. A Subscriber attaches to a Publisher using publisher.subscribe(subscriber).
  2. The Publisher creates a Subscription and passes it to the consumer via subscriber.onSubscribe(subscription).
  3. The Subscriber requests data by calling subscription.request(n).
  4. The Publisher delivers the requested items via subscriber.onNext(item).
  5. Steps 3 and 4 repeat until the stream concludes with subscriber.onComplete(), fails via subscriber.onError(throwable), or is canceled via subscription.cancel().
