Java Concurrency: Deadlock, Livelock, and Starvation

Multithreading in Java significantly improves application performance, but it also introduces concurrency hazards that can stall or severely degrade execution. This article explores the primary causes of deadlocks, livelocks, and thread starvation in Java concurrent systems, examining the synchronization mechanics, improper resource-handling patterns, and scheduling behaviors that trigger these distinct thread-liveness failures.

Causes of Deadlocks

A deadlock occurs when two or more threads are permanently blocked, each waiting for a monitor lock or resource held by another thread in the group. In Java, deadlocks occur when the four Coffman conditions are met simultaneously:

  1. Mutual Exclusion: At least one resource must be held in a non-shareable mode (e.g., intrinsic locks via the synchronized keyword or explicit ReentrantLock instances).
  2. Hold and Wait: A thread holds at least one lock while actively waiting to acquire an additional lock held by another thread.
  3. No Preemption: Resources cannot be forcibly confiscated from a thread; locks are only released voluntarily by the holding thread.
  4. Circular Wait: A closed chain of threads exists where Thread A waits for a lock held by Thread B, and Thread B waits for a lock held by Thread A.

The most frequent programmatic cause in Java is inconsistent lock ordering. When multiple threads acquire nested locks in different sequences, circular wait conditions emerge:

// Thread 1
synchronized (lockA) {
    synchronized (lockB) { /* work */ }
}

// Thread 2
synchronized (lockB) {
    synchronized (lockA) { /* work */ }
}

If Thread 1 acquires lockA at the same time Thread 2 acquires lockB, neither can proceed, causing a permanent freeze.

Causes of Livelocks

A livelock occurs when two or more threads continuously change their states in response to each other without making any practical forward progress. Unlike deadlocked threads, livelocked threads are not blocked; they remain in an active running state, consuming CPU cycles while trapped in an infinite loop of mutual evasion or compensation.

Primary causes in Java include:

  • Symmetrical Conflict Resolution: Implementing recovery mechanisms using Lock.tryLock() where both threads detect a potential deadlock, release their acquired locks simultaneously, wait for an identical duration, and immediately attempt re-acquisition at the same moment.
  • Correlated Message Processing: In messaging or actor patterns, two nodes or threads continuously reject and re-queue unprocessable tasks back and forth without modifying the conditions that caused the initial rejection.
  • Lack of Randomness (Jitter): Failing to introduce randomized exponential backoff when backing off from contended resources, ensuring that threads remain lockstep in their collision-and-retry cycles.

Causes of Thread Starvation

Thread starvation happens when a runnable thread is perpetually denied CPU time or access to shared resources, preventing it from completing its work. Unlike deadlock, the resource is not permanently locked; other threads continue to use it, but a specific thread is consistently passed over.

Common causes in Java systems include:

  • Non-Fair Locking Mechanisms: By default, Java intrinsic locks (synchronized) and standard ReentrantLock instances use non-fair queuing to maximize throughput. High-throughput environments can lead to "barging," where newly arriving threads acquire the lock immediately, repeatedly bypassing older threads waiting in the queue.
  • Thread Priority Misuse: Using Thread.setPriority() to grant certain threads Thread.MAX_PRIORITY can lead the underlying operating system scheduler to starve threads assigned lower priorities (Thread.MIN_PRIORITY). Java thread priorities map unpredictably to native OS schedulers and do not guarantee fair scheduling.
  • Long-Running Synchronized Blocks: Threads that perform blocking I/O operations, complex computations, or infinite polling loops inside critical sections monopolize shared locks, effectively starving any thread waiting to enter the synchronized block.
  • Improper Wait-Notify Usage: Calling notify() instead of notifyAll() inside a condition loop can wake the wrong thread. If the awakened thread cannot fulfill its condition, it goes back to sleep, potentially leaving the intended thread waiting indefinitely.
