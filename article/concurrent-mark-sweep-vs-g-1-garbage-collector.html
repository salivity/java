Concurrent Mark-Sweep vs G1 Garbage Collector

This article explores the Concurrent Mark-Sweep (CMS) garbage collector, its operational mechanics, and the technical limitations that led to its deprecation in favor of the Garbage-First (G1) collector in modern Java. CMS was designed for low-latency applications by performing garbage collection concurrently with application threads, but inherent architectural flaws—most notably memory fragmentation and unpredictable full garbage collection pauses—ultimately made it unsuitable for modern, large-heap enterprise environments. The G1 collector resolved these issues through a region-based, compacting approach with predictable pause-time targets.

What is Concurrent Mark-Sweep (CMS)?

The Concurrent Mark-Sweep collector was introduced to minimize Stop-The-World (STW) pauses in Java applications. Designed primarily for the old (tenured) generation, CMS executes the majority of its tracing and sweeping work concurrently with the application's active threads.

A CMS cycle consists of several phases:

  • Initial Mark (STW): Pauses application threads briefly to mark objects directly reachable from GC roots.
  • Concurrent Mark: Traverses the object graph concurrently while application threads continue running.
  • Concurrent Preclean: Prepares for the next pause by accounting for references modified during the concurrent mark phase.
  • Remark (STW): A final brief pause to catch any remaining reference updates that occurred during the concurrent phases.
  • Concurrent Sweep: Reclaims memory occupied by dead objects concurrently without halting the application.
  • Concurrent Reset: Prepares CMS internal data structures for the next cycle.

Why CMS Was Deprecated and Phased Out

Despite providing lower latency than earlier throughput-focused collectors like Parallel GC, CMS suffered from critical architectural limitations that caused it to be deprecated in Java 9 and fully removed in Java 14:

  1. Memory Fragmentation: CMS does not compact memory during its sweep phase. Instead, it maintains a "free list" of available memory slots. Over time, the heap becomes fragmented. When an object cannot fit into any available contiguous memory block, CMS triggers a "Concurrent Mode Failure." This forced the JVM to fall back to a single-threaded, non-concurrent Full GC that halted the application for extended periods.
  2. Floating Garbage: Because application threads run concurrently during the sweep phase, newly unreachable objects created during this time cannot be collected in the current cycle. This "floating garbage" requires extra heap headroom, increasing memory overhead.
  3. High CPU Utilization: Running garbage collection threads concurrently with application workloads competes directly for processing power, which can degrade application throughput on systems with limited CPU cores.
  4. Poor Scalability with Large Heaps: As modern application heaps expanded from gigabytes to tens or hundreds of gigabytes, managing free lists and dealing with fragmentation became increasingly inefficient.

Why G1 Collector Replaced CMS

The Garbage-First (G1) collector was introduced as the default collector in Java 9 to directly address the shortcomings of CMS.

  • Region-Based Memory Layout: Unlike CMS, which uses large, contiguous physical memory spaces for young and old generations, G1 divides the heap into thousands of equal-sized independent regions. Regions are dynamically assigned young, old, or humongous roles.
  • Built-in Compaction: G1 avoids fragmentation entirely through a copy-and-compact approach. It copies live objects from multiple source regions into a single target region, leaving behind contiguous free memory.
  • Predictable Pause-Time Goals: Users can specify a target pause duration using -XX:MaxGCPauseMillis. G1 uses historical metrics to select and collect the specific set of regions containing the highest density of dead objects (the "garbage first") that can be processed within that time limit.
  • Seamless Scalability: Because G1 processes memory incrementally region-by-region rather than operating on the entire old generation at once, it scales efficiently across multi-gigabyte heaps without the catastrophic multi-second pauses typical of CMS failures.
