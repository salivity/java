Java Transaction Propagation Behaviors Explained

Transaction propagation behaviors define how transactional boundaries interact and map across method calls in enterprise Java applications. In ecosystems like Jakarta EE and the Spring Framework, these propagation rules dictate whether a business method executes within an existing physical transaction, suspends an ongoing transaction to spawn a new one, or executes without transactional management entirely. Understanding these mechanisms is essential for maintaining data consistency, preventing unexpected rollbacks, and designing clean enterprise architectures.

1. REQUIRED

REQUIRED is the default and most commonly used propagation behavior. If a transaction already exists when the method is invoked, the method joins and executes within that existing transaction. If no transaction is active, the container creates a new one. All methods participating in the same REQUIRED context share the same physical transaction, meaning a rollback in a child method marks the entire transaction for rollback.

2. REQUIRES_NEW

REQUIRES_NEW always initiates a completely new, independent transaction. If an active transaction already exists, the container suspends it until the newly spawned transaction completes. Because the new transaction commits or rolls back independently of the outer transaction, exceptions or rollbacks inside the REQUIRES_NEW block do not automatically affect the outer context, provided exceptions are properly caught and handled.

3. SUPPORTS

SUPPORTS adapts to the caller's context. If an active transaction exists, the method executes within it. If no active transaction exists, the method executes non-transactionally without error. This behavior is typically suited for read-only operations that can benefit from being part of a larger unit of work when called from a write operation, but do not strictly need transactional overhead on their own.

4. NOT_SUPPORTED

NOT_SUPPORTED ensures that the method executes non-transactionally. If an ongoing transaction exists when the method is called, the container suspends that transaction for the duration of the method's execution and resumes it afterward. This setting is optimal for long-running tasks, such as sending emails or calling external web services, where holding database locks across an active transaction is undesirable.

5. MANDATORY

MANDATORY requires an active transaction to already be present. If the method is invoked within an existing transaction, it joins and proceeds normally. However, if no active transaction exists, the container immediately throws an exception (such as TransactionRequiredException or IllegalTransactionStateException). This is used to enforce that a method must never be called as an isolated operation.

6. NEVER

NEVER enforces that the method must run strictly outside of any transactional context. If an active transaction is detected upon method invocation, the container immediately throws an exception. This propagation type acts as the polar opposite of MANDATORY and protects operations that are strictly incompatible with active database transactions.

7. NESTED

NESTED operates by utilizing JDBC savepoints when an active transaction is present. Rather than suspending the outer transaction, it executes within a child transaction boundary. If the nested transaction fails, it can roll back to its initial savepoint without causing the outer transaction to roll back entirely. If no active transaction exists, NESTED behaves like REQUIRED, creating a brand-new top-level transaction.
