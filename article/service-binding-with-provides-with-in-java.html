Service Binding with Provides With in Java

The Java Platform Module System (JPMS) introduced a declarative approach to service binding, replacing the legacy META-INF/services configuration with module-info directives. By utilizing the provides ... with syntax alongside the uses directive, Java alters how service providers are compiled, encapsulated, and instantiated at runtime. This mechanism enforces compile-time validation, allows implementation classes to remain hidden within unexported packages, supports specialized provider factory methods, and integrates directly into the module resolution graph.

Syntax and Declaration

In modular Java, a service consumer declares dependency on a service interface using the uses keyword, while the service provider declares its implementation using provides ... with:

// Service Consumer Module
module com.example.consumer {
    requires com.example.api;
    uses com.example.api.PaymentService;
}

// Service Provider Module
module com.example.provider {
    requires com.example.api;
    provides com.example.api.PaymentService with com.example.provider.CreditCardPayment;
}

The ServiceLoader API bridges the two modules at runtime by loading implementations declared in these directives:

ServiceLoader<PaymentService> loader = ServiceLoader.load(PaymentService.class);

Encapsulation Without Package Exporting

Prior to modules, service implementations located via META-INF/services required both the implementation class and its package to be public so ServiceLoader could access them through reflection.

With provides ... with, the module containing the implementation does not need to export the package hosting the implementation class. The Java runtime grants ServiceLoader deep reflection access specifically to the classes designated in the with clause. Consumers can interact with the service strictly through the public interface, preventing accidental coupling with concrete classes.

Compile-Time Verification

Legacy classpath service binding relies on text files that are not verified until runtime execution. In contrast, the Java compiler validates the provides ... with clause during compilation:

  • The compiler checks that the implementation class actually implements or extends the service interface specified in the provides clause.
  • It verifies that the implementation provides either a public no-argument constructor or a public static factory method.
  • It ensures that the referenced classes and packages exist within the module.

Flexible Instantiation with Provider Methods

The provides ... with mechanism supports a modern instantiation pattern using a static provider() method instead of requiring a public no-argument constructor:

package com.example.provider;

public class CreditCardPayment implements PaymentService {
    private CreditCardPayment() {}

    public static PaymentService provider() {
        return new CreditCardPayment();
    }
}

When ServiceLoader loads this service, it detects the public static PaymentService provider() method and invokes it. This approach enables lazy initialization, singleton caching, or dynamic delegation before the service instance is returned. The implementation class can even keep its constructor entirely private.

Module Resolution and Binding Dynamics

The module system incorporates service providers into the module graph dynamically. When compiling or running an application, passing the --bind-services flag instructs the module resolver to automatically pull in observable modules that satisfy any uses declarations.

Without --bind-services, modules providing services via provides ... with are not automatically resolved merely by being on the module path. Instead, ServiceLoader.load() dynamically locates and layers observable provider modules when queried at runtime, provided that the calling module explicitly declares a corresponding uses directive.
