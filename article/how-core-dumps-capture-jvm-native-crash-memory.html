How Core Dumps Capture JVM Native Crash Memory

When a Java Virtual Machine (JVM) crashes due to a fatal native error—such as an invalid pointer dereference in Java Native Interface (JNI) code or a segmentation fault within the HotSpot runtime itself—the underlying operating system halts the process and extracts its entire active state into a core dump. This article explains the technical mechanics behind this process, from the initial hardware fault and JVM signal handling to the kernel-level serialization of virtual memory mappings, CPU registers, and thread stacks into an Executable and Linkable Format (ELF) file for post-mortem debugging.

The Trigger: Native Faults and Signals

A native crash begins when executing native instructions violate CPU architecture or memory access rules. Common triggers include dereferencing a NULL pointer, accessing an unmapped memory page, writing to read-only memory, or running an illegal instruction.

At the hardware level, the CPU Memory Management Unit (MMU) detects the illegal access and raises a hardware interrupt. The operating system kernel translates this interrupt into a POSIX signal sent directly to the offending thread. Common fatal signals include:

  • SIGSEGV (Signal 11): Segmentation violation (invalid memory access).
  • SIGBUS (Signal 7): Bus error (alignment error or unmapped memory page).
  • SIGILL (Signal 4): Illegal instruction.
  • SIGFPE (Signal 8): Erroneous arithmetic operation (e.g., divide by zero).

The JVM Signal Interception Mechanism

The HotSpot JVM registers custom signal handlers during initialization using sigaction. Not all fatal signals indicate an unrecoverable crash; for instance, HotSpot routinely uses implicit SIGSEGV signals to handle implicit null checks in bytecode or to implement safepoint polling safely and efficiently.

When a fatal signal is intercepted, the JVM's signal handler checks whether the faulting instruction belongs to known runtime optimizations:

  1. Handled Faults: If the fault was an expected optimization, the JVM updates the program counter to redirect execution to a pre-generated fallback routine, resuming normal execution without crashing.
  2. Unrecoverable Faults: If the fault occurs within unmanaged C/C++ code (JNI libraries) or unhandled JVM internal code, the signal handler recognizes it as an actual crash.

Upon confirming a fatal crash, the JVM first attempts to generate its diagnostic error log (hs_err_pid<pid>.log). To produce the operating system core dump, the JVM restores the default signal handler (SIG_DFL) for the fatal signal and re-raises it, deliberately delegating process termination and dump generation back to the operating system kernel.

Kernel-Level Core Dump Generation

Once the OS kernel receives the re-raised fatal signal under the default action, it freezes the process and initiates the core dump routine. The generation process proceeds through several coordinated phases:

1. Halting Threads and Capturing Registers

The kernel issues a stop request to all threads belonging to the JVM process. For every thread, the kernel records the current execution context directly from the CPU registers into the process memory descriptor. This snapshot includes:

  • Instruction Pointer (RIP/PC): The exact instruction executing at the time of the fault.
  • Stack Pointer (RSP/SP): The current boundary of the native execution stack.
  • General-Purpose Registers: Current pointer values, function arguments, and calculation registers.
  • Signal Context: The memory address that triggered the fault (si_addr).

2. Scanning Virtual Memory Areas (VMAs)

The kernel traverses the process's mm_struct, which manages all mapped Virtual Memory Areas (VMAs). The JVM's memory map is typically vast and includes:

  • The Java Heap (committed pages).
  • Metaspace and CodeCache (JIT-compiled native code).
  • Thread stacks (both Java frames and native C/C++ frames).
  • The native C-heap allocated via malloc.
  • Loaded dynamic libraries (.so or .dll files) and mapped native files.

The kernel inspects the process core dump mask (configured via /proc/<pid>/coredump_filter on Linux) to determine which memory segments to serialize. By default, this usually includes anonymous private mappings, shared memory, and file-backed private mappings, while skipping clean, read-only file-backed mappings to save space.

3. Serializing to Disk

The kernel opens the destination file determined by system parameters (such as /proc/sys/kernel/core_pattern on Linux or systemd-coredump) provided that resource limits (ulimit -c) allow it.

The memory state is serialized as a standard format (ELF on Linux, Mach-O on macOS, or Minidump on Windows). In an ELF core dump, the kernel writes:

  • ELF Header: Identifies architecture, byte ordering, and file layout.
  • PT_NOTE Segments: Contains process metadata, the list of loaded shared libraries, and an array of NT_PRSTATUS structures storing the saved CPU register states and signal metadata for every thread.
  • PT_LOAD Segments: Raw byte copies of the designated Virtual Memory Areas, preserving virtual addresses so debuggers can reconstruct exact pointers.

Distinction Between Core Dumps and Java Heap Dumps

A core dump captures the entire address space of the operating system process at the byte level. It includes native code, thread states, JVM internals, unmanaged memory, and the Java heap.

In contrast, a standard Java heap dump (such as an HPROF file generated via -XX:+HeapDumpOnOutOfMemoryError) is captured via JVM software routines, containing only Java objects, classes, and references, entirely omitting CPU registers, native execution frames, and JNI allocations. The core dump serves as the lowest-level diagnostic artifact available for diagnosing total JVM failure.
