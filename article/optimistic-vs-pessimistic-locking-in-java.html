Optimistic vs Pessimistic Locking in Java

This article explores the core differences between optimistic and pessimistic database locking strategies in Java enterprise applications. It details how each concurrency control mechanism functions, demonstrates their implementation using the Java Persistence API (JPA) and Hibernate, compares their performance and scalability trade-offs, and provides guidelines for selecting the appropriate approach based on your application's read-to-write ratios and collision frequency.

Understanding Concurrency Control in Java

When multiple transactions attempt to read and modify the same database records simultaneously, data inconsistency—such as lost updates or dirty reads—can occur. Java applications interacting with relational databases via JPA or Hibernate use locking mechanisms to maintain ACID compliance and ensure data integrity.

What is Optimistic Locking?

Optimistic locking operates under the assumption that data conflicts are rare. Instead of locking records at the database level when they are read, transactions are allowed to proceed without restriction. Before committing, the application checks whether another transaction has modified the record in the meantime.

How It Works

Optimistic locking relies on a version attribute (such as an integer counter or a timestamp). When an entity is read, its current version is noted. When updating, the SQL statement includes a WHERE clause verifying the version:

UPDATE product 
SET stock = 45, version = 2 
WHERE id = 101 AND version = 1;

If another transaction has already updated the record, the version mismatch causes the update to affect zero rows, prompting the persistence provider to throw an exception.

Implementation in JPA

In Java, optimistic locking is typically implemented using the @Version annotation on an entity field:

import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.Version;

@Entity
public class Product {
    @Id
    private Long id;
    
    private String name;
    private int stock;

    @Version
    private Long version;

    // Getters and setters
}

If a conflict occurs during commit, JPA throws an OptimisticLockException. The application must handle this exception, typically by rolling back the transaction, reloading the updated data, and retrying the operation.

What is Pessimistic Locking?

Pessimistic locking operates under the assumption that concurrent conflicts are likely. It locks the targeted database record immediately upon retrieval, preventing other transactions from modifying—or in some cases reading—the data until the current transaction completes.

How It Works

Pessimistic locking utilizes native database locking mechanisms, typically translating to SQL statements with a FOR UPDATE clause:

SELECT * FROM product WHERE id = 101 FOR UPDATE;

Other transactions attempting to acquire a lock on the same record are forced to wait until the holding transaction issues a COMMIT or ROLLBACK.

Implementation in JPA

Pessimistic locks can be requested explicitly using an EntityManager or through Spring Data JPA repository methods:

// Using EntityManager
Product product = entityManager.find(
    Product.class, 
    101L, 
    LockModeType.PESSIMISTIC_WRITE
);

// Alternatively, via Query
TypedQuery<Product> query = entityManager.createQuery(
    "SELECT p FROM Product p WHERE p.id = :id", Product.class);
query.setParameter("id", 101L);
query.setLockMode(LockModeType.PESSIMISTIC_WRITE);
Product product = query.getSingleResult();

Common pessimistic lock modes include:

  • PESSIMISTIC_READ: Obtains a shared lock that prevents other transactions from updating or deleting the row, but allows concurrent reads.
  • PESSIMISTIC_WRITE: Obtains an exclusive lock that prevents other transactions from reading (with lock), updating, or deleting the row.

Key Differences

Feature Optimistic Locking Pessimistic Locking
Lock Level Application level (via version checks) Database level (via DB row locks)
Resource Retention No database locks held during processing Database locks held for the entire transaction
Conflict Detection At commit time At read/acquisition time
Failure Handling Throws OptimisticLockException requiring application retry logic Blocked threads wait or encounter lock acquisition timeouts
Deadlock Risk None High, if multiple records are locked in inconsistent orders
Throughput High, especially in read-heavy workloads Lower, restricted by thread blocking and connection pool limits

When to Use Which Strategy

Choose Optimistic Locking When:

  • Read operations heavily outnumber write operations: Web applications, content management systems, and product catalog browsing.
  • Transactions span user think-time: Long-lived user workflows where holding an active database connection and row lock is unfeasible.
  • High throughput is critical: Eliminates database lock overhead and avoids connection pool starvation.

Choose Pessimistic Locking When:

  • Collision probability is high: Financial transactions, inventory reservations, or ticket-booking systems where multiple users contend for the same item simultaneously.
  • The cost of retrying is prohibitive: Scenarios where rolling back and repeating complex business workflows would degrade performance more than waiting for a lock.
  • Immediate consistency is non-negotiable: Strict serialization of updates must be enforced directly at the database layer.
