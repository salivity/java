Java Module System: Package Exports and Dependencies

The Java Platform Module System (JPMS), introduced in Java 9, enforces strong encapsulation and reliable configuration across application components. This article explains how JPMS utilizes the module-info.java descriptor to explicitly control which packages are accessible to outside consumers via the exports directive, how it declares compile-time and runtime requirements via the requires directive, and how it completely hides internal implementation details to prevent unauthorized access.

The Module Descriptor

At the core of modularization is the module-info.java file, located at the root of a module's source tree. This file defines the module's identity, its incoming dependencies, and its outgoing package permissions. By default, every package inside a module is strictly encapsulated, meaning that types inside those packages—even those declared with the public access modifier—are completely invisible to other modules unless explicitly made accessible.

Controlling Public APIs with exports

To make a package accessible to external modules, you must explicitly declare it using the exports keyword:

module com.example.service {
    exports com.example.service.api;
}

In this example, only the public and protected classes and interfaces within com.example.service.api are accessible to outside modules. Any subpackages, such as com.example.service.api.internal, are not automatically exported and remain invisible.

JPMS also supports qualified exports, which restrict access to specific, named modules:

module com.example.service {
    exports com.example.service.internal to com.example.test, com.example.admin;
}

Qualified exports allow library designers to share utility or integration code with trusted partner modules without exposing those packages to the general public.

Managing Internal Dependencies with requires

When a module depends on another module's exported packages, it must explicitly state that dependency using the requires directive:

module com.example.client {
    requires com.example.service;
}

This declaration provides reliable configuration. The Java compiler and runtime verify the entire module graph during initialization. If a required module is missing, cyclical, or conflicts with another dependency, the application fails immediately at startup rather than throwing a NoClassDefFoundError deep into runtime execution.

To pass dependencies downstream, modules can use requires transitive. This exposes the required module's public packages to any other module reading the host module:

module com.example.client {
    requires transitive com.example.service;
}

Encapsulating Internal Implementations

Packages within a module that are not exported are strictly internal. Historically, developers relied on naming conventions (like .internal. packages) to signal that a package was private, but this did not stop external code from importing those classes or using reflection to access them.

Under JPMS, non-exported packages cannot be accessed at compile time, and runtime reflection into these packages via setAccessible(true) is blocked by default. If deep reflection is required (such as for dependency injection or serialization frameworks like Spring or Jackson), a module can selectively grant reflection access using the opens directive:

module com.example.service {
    opens com.example.service.model to com.fasterxml.jackson.databind;
}

This approach allows frameworks to perform reflection at runtime while keeping the package completely hidden from regular compilation and API usage. Through this combination of exports, requires, and opens, the Java Module System provides strict boundaries that enforce architectural integrity and secure internal dependencies.
