Java Compact Strings: Optimizing Latin-1 Byte Storage

Compact Strings is a memory-optimization feature introduced in Java 9 via JEP 254 that reduces the heap footprint of String objects by up to 50%. Historically, Java stored string data using a UTF-16 char array, allocating two bytes per character regardless of whether the extra byte was needed. Compact Strings replaces this implementation with a more flexible byte array coupled with an encoding flag, allowing the Java Virtual Machine (JVM) to store Latin-1 characters using just a single byte per character.

The Problem: UTF-16 Inefficiency

Prior to Java 9, the internal representation of the java.lang.String class relied on a 16-bit char array:

private final char[] value;

Because char types in Java are 16 bits (two bytes) long, every character required two bytes of heap memory. Studies of production JVM heaps revealed that string data typically accounts for 25% to 40% of an application's total live memory. Furthermore, the vast majority of these strings consisted entirely of Latin-1 characters (characters whose code points range from 0x0000 to 0x00FF, covering basic Latin and standard ASCII). Consequently, the high byte of every 16-bit character was consistently 0x00, meaning half of the allocated string memory was wasted.

The Solution: A byte[] with an Encoding Coder

To address this inefficiency, Java 9 redesigned the internal storage of String to use a byte array alongside a single-byte encoding identifier:

private final byte[] value;
private final byte coder;

The coder field acts as a metadata flag that determines how the bytes in value must be decoded. Java defines two primary coder values:

  • LATIN1 (Value 0): Used when all characters in the string fit within the ISO-8859-1 (Latin-1) character set (code points 0–255).
  • UTF16 (Value 1): Used when at least one character in the string requires a code point greater than 255.

How Latin-1 Optimization Works

When a String is instantiated, the runtime inspects the character values to determine the appropriate encoding:

  1. Scanning and Detection: If a string contains only characters whose integer representations are \(\le 255\), the JVM assigns the coder field to LATIN1.
  2. Single-Byte Packing: Each character is stripped of its leading zeros and stored directly as a single 8-bit byte inside the value array. A 10-character Latin-1 string requires an array of 10 bytes instead of the previous 20 bytes.
  3. UTF-16 Fallback: If any character in the string requires more than 8 bits (such as Cyrillic, Chinese, Japanese, or emoji characters), the JVM sets coder to UTF16. The string is then stored as standard UTF-16, consuming two bytes per character just as it did in Java 8 and earlier.

Performance and Garbage Collection Benefits

Because the switch between Latin-1 and UTF-16 happens internally, Compact Strings requires zero code changes from developers. The optimization delivers several operational advantages:

  • Reduced Memory Footprint: Applications that heavily manipulate text or store large collections of ASCII/Latin-1 strings see an immediate 10% to 15% reduction in overall heap memory usage.
  • Lower Garbage Collection Pressure: Smaller objects mean the JVM fills heap generations more slowly, leading to fewer and shorter Garbage Collection (GC) pauses.
  • CPU Cache Efficiency: Storing characters in single-byte formats increases cache density. More string data fits into CPU L1 and L2 caches, improving throughput. While reading single bytes requires low-level shifting operations, hot methods are optimized with JVM intrinsics and SIMD (Single Instruction, Multiple Data) instructions, ensuring no loss in runtime speed.
