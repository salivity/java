How CopyOnWriteArrayList Ensures Thread-Safe Iteration

The CopyOnWriteArrayList class in Java achieves thread-safe iteration without explicit synchronization locks by utilizing an immutable snapshot mechanism. When an iterator is instantiated, it binds directly to the underlying array as it exists at that exact millisecond. Any subsequent write operations, such as adding or removing elements, create a fresh copy of the array rather than modifying the existing one, allowing active iterators to traverse the original, untouched array safely without encountering ConcurrentModificationException.

The Snapshot Mechanism

At the core of CopyOnWriteArrayList is a single reference to an internal array declared as volatile:

private transient volatile Object[] array;

When a thread invokes iterator(), the list provides an iterator holding a direct reference to this internal array at that specific moment. This captured array reference acts as a static "snapshot" of the data.

Because the reference points to a fixed-size, unmodifiable view of elements, the iterator can step through the indices from start to finish without needing to acquire locks or check for concurrent modifications. The state of the snapshot never changes during the lifecycle of that iterator.

The Copy-on-Write Strategy for Mutations

Thread safety during write operations is decoupled from the read and iteration paths. When a thread performs a mutation (such as add(), set(), or remove()):

  1. The modifying thread acquires an internal lock (typically via a ReentrantLock or synchronized block) to prevent conflicting concurrent writes.
  2. The current array is cloned into a new array with an adjusted size or modified elements.
  3. The mutation is applied directly to the new array copy.
  4. The volatile internal array reference is updated to point to the newly created array.
  5. The lock is released.

Because of the volatile modifier, any subsequent calls to iterator() or get() will immediately see the updated array. However, any iterator created prior to the reference update continues traversing the original array. The original array remains completely unaffected by the write operation and is eventually reclaimed by the garbage collector once all iterators referencing it complete execution.

Consequences and Trade-Offs of Lock-Free Iteration

This design yields distinct functional characteristics:

  • Immunity to ConcurrentModificationException: Since the underlying array used by an active iterator is never modified in place, iteration is guaranteed to complete cleanly.
  • Fail-Safe Iteration: Iterators provide weakly consistent views. They reflect the state of the list when the iterator was created and do not reflect subsequent modifications made by other threads.
  • Unsupported Iterator Mutations: Methods like remove(), set(), and add() on the iterator instance throw UnsupportedOperationException because modifying the snapshot would violate the design principle.
  • Performance Profile: Reads and iterations have zero locking overhead, making them exceptionally fast. However, writes incur high memory allocation and CPU costs due to array duplication, making CopyOnWriteArrayList suitable primarily for collections where read operations dramatically outnumber write operations.
