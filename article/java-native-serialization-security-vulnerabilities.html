Java Native Serialization Security Vulnerabilities

Java native serialization is a mechanism designed to convert an in-memory object graph into a binary byte stream and reconstruct it later via deserialization. While architecturally convenient, it is widely considered one of the most dangerous vulnerability vectors in modern enterprise software. The protocol's fundamental design flaw—executing code during the recreation of objects before the application can validate incoming data—frequently enables attackers to achieve remote code execution (RCE), launch denial-of-service (DoS) attacks, and bypass security controls.

Execution Before Validation

The primary security flaw in native Java serialization lies in how ObjectInputStream.readObject() functions. When an application accepts a serialized byte stream, the Java Virtual Machine (JVM) allocates memory and reconstructs the object graph automatically.

During this reconstruction, the JVM invokes internal methods—most notably readObject(), readResolve(), and finalize()—before the application layer ever receives the deserialized object. This means any security checks, such as type casting or value assertions, occur too late. The malicious payload executes its initial logic during the stream parsing phase, giving the application no opportunity to inspect or reject the data beforehand.

Gadget Chains and Remote Code Execution

Deserialization vulnerabilities rarely require custom malicious classes to be transferred over the wire. Instead, attackers use "gadget chains"—sequences of classes already present on the application's classpath that execute specific behaviors when deserialized.

A gadget is an existing class with an implementation of readObject() (or another magic method) that triggers downstream method invocations. Attackers assemble these gadgets into a chain:

  1. Kickoff Gadget: An entry class that executes a method upon deserialization (e.g., calling hashCode() or equals() on a map entry).
  2. Intermediate Gadgets: Classes that pass data between methods, often leveraging reflection, proxy mechanisms, or common utilities.
  3. Sink Gadget: A terminal class that executes arbitrary code, invokes operating system commands (such as Runtime.getRuntime().exec()), or writes malicious files to the disk.

Because popular third-party libraries (such as older versions of Apache Commons Collections, Spring Framework, or Groovy) contain suitable gadgets, an attacker only needs one vulnerable deserialization endpoint to exploit the entire application classpath.

Massive and Uncontrolled Attack Surface

Native Java serialization treats the entire JVM classpath as a potential attack surface. As long as a class implements the java.io.Serializable marker interface (or inherits it), it can be instantiated during deserialization.

In a typical enterprise application, the classpath includes tens of thousands of classes across hundreds of dependencies. Securing this surface is nearly impossible because application developers do not control the internal implementations of their third-party dependencies. A dependency update that introduces a previously benign class can inadvertently introduce a functional gadget chain.

Resource Exhaustion and Denial of Service

Beyond arbitrary code execution, Java native serialization is vulnerable to structural abuse that causes denial of service. Attackers can craft "deserialization bombs"—compact payloads consisting of deeply nested or cyclic object graphs.

When the JVM attempts to reconstruct these structures, the parsing logic can trigger exponential CPU cycles or exhaust the heap memory, causing the entire application to crash without ever completing the deserialization process.

Structural Irreparability and Modern Replacements

The Java platform architects have openly acknowledged that native serialization was a fundamental design mistake. Because the mechanism bypasses normal constructors and breaks object encapsulation, it cannot be completely secured while maintaining backward compatibility.

While defenses like serialization filters (java.io.ObjectInputFilter) introduce allowlists and denylists to restrict which classes can be reconstructed, they require ongoing maintenance and can still be circumvented by novel gadget chains. Consequently, the industry standard is to eliminate native Java serialization entirely in favor of data-only serialization formats, such as JSON, Protocol Buffers, or FlatBuffers, which do not couple data transmission with executable object behavior.
