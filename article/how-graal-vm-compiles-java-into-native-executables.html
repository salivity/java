How GraalVM Compiles Java into Native Executables

This article explains the step-by-step process of how GraalVM transforms standard Java bytecode into standalone native executables using Ahead-of-Time (AOT) compilation. By replacing the traditional Java Virtual Machine (JVM) dynamic runtime model with static analysis, a closed-world assumption, and an embedded runtime known as Substrate VM, GraalVM produces compact, instant-starting binaries tailored to specific operating systems and processor architectures.

Ahead-of-Time (AOT) Compilation vs. Traditional JIT

In a standard Java execution model, the JVM interprets bytecode at runtime and uses Just-In-Time (JIT) compilation to turn hot code paths into machine instructions. GraalVM Native Image bypasses this runtime compilation phase entirely. It performs Ahead-of-Time (AOT) compilation during the build process, translating Java bytecode directly into target-specific machine code before the application is ever launched.

Static Analysis and the Closed-World Assumption

The foundation of the Native Image build process is static points-to analysis operated under the "closed-world assumption."

Under this assumption, GraalVM asserts that all classes, methods, and fields that will ever be accessed at runtime must be known and reachable during the build phase:

  1. Reachability Analysis: The compilation process begins at predefined entry points, typically the application's public static void main method.
  2. Call-Tree Traversal: The static analyzer traces all reachable code execution paths, including application code, third-party libraries, and JDK base modules.
  3. Dead Code Elimination: Any class, method, or code path that cannot be reached through this iterative traversal is stripped away, significantly reducing the final binary size.

Build-Time Initialization and Heap Snapshotting

GraalVM can execute static initializers during the native compilation phase rather than delaying them until runtime.

When a class is designated to be initialized at build time, its static initialization blocks run, static fields are populated, and the resulting objects are placed in the build-time heap. GraalVM then snapshots this state directly into the native executable's data section. When the application starts, this pre-initialized heap state is mapped directly into memory, eliminating startup overhead.

Substrate VM: The Embedded Runtime

A native executable cannot run without essential runtime services such as memory management, thread scheduling, and garbage collection. Because the full JVM is discarded, GraalVM bundles a lightweight component called Substrate VM directly into the generated binary.

Substrate VM is itself written mostly in Java and compiled alongside the application. It provides:

  • Garbage Collection: Minimal, low-latency garbage collectors (like the default Serial GC or G1-like alternatives in the Enterprise/Oracle GraalVM editions).
  • Thread Management: Direct mapping to operating system threads.
  • Deoptimization/Signal Handling: Primitives to handle hardware and OS-level signals.

Machine Code Generation via Graal Compiler

Once the reachable code is determined and the runtime environment is configured, the core Graal execution engine takes over. The Graal compiler—a high-performance, dynamic compiler written in Java—parses the collected bytecode into an Intermediate Representation (IR).

It applies standard and advanced compiler optimizations, such as aggressive method inlining, loop unrolling, and escape analysis. Finally, the backend translates the optimized IR into machine-specific assembly (such as x86-64 or ARM64) and writes an OS-compliant binary format (ELF on Linux, Mach-O on macOS, or PE on Windows).

Handling Dynamic Java Features

Because the closed-world assumption requires all code to be discoverable at build time, dynamic features such as reflection, Java Native Interface (JNI), dynamic proxies, and resource loading require explicit declarations.

Developers specify these dynamic elements using JSON configuration files or by running the GraalVM Native Image Tracing Agent. The agent runs the application on a standard JVM, records all reflective calls and dynamically loaded classes, and generates the necessary metadata so the AOT compiler can include them in the analysis and final binary.
