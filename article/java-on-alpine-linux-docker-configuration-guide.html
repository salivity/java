Java on Alpine Linux: Docker Configuration Guide

Alpine Linux is widely favored for containerized applications due to its minimal footprint and security-oriented design, but running the Java Runtime Environment (JRE) on it introduces unique challenges because Alpine uses musl libc instead of standard glibc. This guide outlines how developers configure Alpine Linux base images to run Java, detailing package installation via Alpine's native package manager, utilizing specialized multi-platform OpenJDK distributions, and employing multi-stage Docker builds with jlink to produce minimal, production-ready images.

Installing Java via the Alpine Package Manager

The most straightforward method to run Java on Alpine is through its native package manager, apk. Alpine provides pre-compiled OpenJDK packages built directly against musl libc.

To configure an Alpine image using this approach, use the following Dockerfile pattern:

FROM alpine:3.19

# Install OpenJDK headless JRE to minimize image size
RUN apk update && \
    apk add --no-cache openjdk17-jre-headless

# Configure Java environment variables
ENV JAVA_HOME=/usr/lib/jvm/java-17-openjdk
ENV PATH="$JAVA_HOME/bin:$PATH"

CMD ["java", "-version"]

Using the -headless package variant avoids downloading graphical libraries (such as X11 or AWT dependencies), keeping the final image lean.

Using Pre-Configured Alpine-Based Java Images

Rather than building directly on pure alpine, official Java providers distribute certified builds compiled specifically for Alpine Linux. These images resolve low-level compatibility issues, include optimal JVM flag defaults, and provide tested CA certificates.

Common vendor images include:

  • Eclipse Temurin: eclipse-temurin:17-jre-alpine
  • Amazon Corretto: amazoncorretto:17-alpine
  • BellSoft Liberica: bellsoft/liberica-openjdk-alpine:17 (BellSoft actively maintains Alpine/musl support in OpenJDK under the Portola project)

Example Dockerfile:

FROM eclipse-temurin:17-jre-alpine

WORKDIR /app
COPY target/application.jar app.jar

# Run as a non-root user for security
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

ENTRYPOINT ["java", "-jar", "app.jar"]

Creating Custom Runtimes with jlink

To achieve the smallest possible container footprint, developers combine a full Alpine OpenJDK image with the Java Linker tool (jlink) in a multi-stage Docker build. This strips away unused Java modules, generating a tailored runtime.

# Stage 1: Build the custom minimal runtime
FROM eclipse-temurin:17-jdk-alpine AS builder

RUN $JAVA_HOME/bin/jlink \
    --add-modules java.base,java.logging,java.sql \
    --strip-debug \
    --no-man-pages \
    --no-header-files \
    --compress=2 \
    --output /custom-runtime

# Stage 2: Create the minimal production image
FROM alpine:3.19

ENV JAVA_HOME=/opt/java/runtime
ENV PATH="$JAVA_HOME/bin:$PATH"

# Copy runtime from builder
COPY --from=builder /custom-runtime /opt/java/runtime

WORKDIR /app
COPY target/application.jar app.jar

CMD ["java", "-jar", "app.jar"]

Handling musl vs. glibc Compatibility

Standard Java binaries distributed as .tar.gz packages (such as official Oracle builds) require glibc. Attempting to execute a standard glibc Java binary directly on an Alpine image results in file not found errors caused by missing dynamic linkers.

If a proprietary third-party Java distribution lacking native musl support must be used, compatibility can be achieved by installing gcompat or manually embedding glibc binaries:

RUN apk add --no-cache gcompat

While gcompat resolves simple binary dependencies, native musl-compiled OpenJDK distributions remain the standard recommendation for production stability and performance.
