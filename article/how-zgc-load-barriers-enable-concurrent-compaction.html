How ZGC Load Barriers Enable Concurrent Compaction

The Z Garbage Collector (ZGC) in Java achieves sub-millisecond pause times by performing virtually all of its memory management tasks concurrently with application threads. Central to this capability is concurrent compaction—the process of relocating live objects to defragment memory without stopping the world. This article explores how ZGC pairs load barriers with colored pointers to safely relocate objects on the fly, resolve stale references, and maintain data consistency with minimal execution overhead.

The Challenge of Concurrent Compaction

In traditional garbage collectors, compaction requires pausing application threads (a "Stop-the-World" phase). When an object moves from one memory address to another, every reference pointing to that object across the entire heap must be updated before the application resumes; otherwise, application threads would access stale or corrupted memory.

ZGC eliminates these long pauses by allowing Java threads to continue running while objects are actively being relocated. To accomplish this safely, ZGC must ensure that whenever an application thread accesses an object that has moved—or is in the process of moving—the thread always receives the updated, correct memory address. This synchronization is managed via load barriers.

What Is a Load Barrier?

A load barrier is a small snippet of machine code inserted by the Just-In-Time (JIT) compiler directly into the execution path whenever an application thread loads an object reference from the heap (for example, evaluating obj.field).

Importantly, load barriers in ZGC only intercept reference loads from the heap; they do not trigger when reading primitive values (like int or boolean) or when loading references from local variables on the thread stack. Because reference loads are extraordinarily frequent, the load barrier is heavily optimized to execute with minimal CPU cost during normal operations.

Colored Pointers and State Detection

ZGC encodes metadata directly into the reference pointer itself using unused reference bits, a technique known as colored pointers. These bits indicate the state of the referenced object:

  • Marked0 / Marked1: Signifies whether the object is reachable in the current GC cycle.
  • Remapped: Signifies whether the reference has already been verified to point directly to the object’s new location, bypassing the need for relocation checks.

When a thread loads a reference, the load barrier performs a fast bitwise test on these color bits against a globally tracked "good" state mask.

  • Fast Path: If the reference bits match the current "good" mask (meaning the reference is already updated and valid), the barrier does nothing further. The CPU executes this check in just a couple of instructions.
  • Slow Path: If the reference bits are "bad", execution enters the barrier's fallback routine to resolve the reference before the application code can use it.

Supporting Concurrent Compaction: The Relocation Flow

When ZGC decides to compact a memory page, the page is placed into a relocation set. The load barrier manages concurrent access during this phase through the following steps:

  1. Detection: An application thread loads a reference pointing to an object residing on a page marked for relocation. The load barrier detects that the reference does not have the "Remapped" bit set.
  2. Forwarding Table Lookup: The load barrier queries the page's forwarding table to see if the object has already been relocated by the GC worker threads:
    • If already relocated: The barrier retrieves the object’s new address.
    • If not yet relocated: The application thread itself allocates space in a new memory page, copies the object, and updates the forwarding table atomically using a compare-and-swap (CAS) operation.
  3. Self-Healing: Once the new address is known, the load barrier updates the reference field in the heap with the new address and colors it as "Remapped." This step is called self-healing. Any future reads from this specific heap location will immediately take the fast path.
  4. Return New Reference: The barrier returns the new, relocated address to the calling thread, ensuring the application never interacts with stale memory.

Conclusion

Load barriers make concurrent compaction practical by shifting the burden of reference updates from a mandatory global pause to an on-demand, distributed mechanism. By relying on colored pointers for near-zero-cost fast path validation and using self-healing updates on the slow path, ZGC ensures memory consistency while keeping application pause times consistently under one millisecond, regardless of heap size.
