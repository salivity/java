Why Was Biased Locking Removed in Java?

Biased locking was an optimization introduced in Java 6 to eliminate the overhead of synchronization when an object was accessed primarily by a single thread. While highly effective for legacy applications relying on older collections, evolution in CPU hardware and modern programming patterns gradually reduced its benefits while elevating its costs. In JDK 15, JEP 374 disabled and deprecated biased locking, setting the stage for its eventual removal due to heavy safepoint overhead during lock revocation, declining performance gains from cheaper modern atomic operations, and the massive maintenance burden it imposed on the HotSpot runtime.

The Original Purpose of Biased Locking

In early versions of Java, foundational APIs like Vector, StringBuffer, and Hashtable synchronized every operation by default. Even when these classes were used in single-threaded environments, threads continuously paid the performance cost of atomic Compare-And-Swap (CAS) operations to acquire and release object monitors.

Biased locking solved this by assuming an object would only ever be locked by one thread. The first thread to acquire the lock would "bias" the object's header (the mark word) toward itself. Subsequent locking and unlocking actions by this same thread required only a cheap identity check against the thread ID stored in the mark word, completely bypassing atomic operations and memory bus synchronization.

Cheaper Atomic CPU Operations

Biased locking was designed in an era where atomic CPU operations—such as the LOCK CMPXCHG instruction on x86 architectures—were computationally expensive and significantly impacted the CPU memory bus.

As modern multi-core processor architectures advanced, the hardware penalty for executing atomic instructions dropped substantially. The gap between a plain store/check operation (used by biased locking) and an uncontended CAS operation shrank so dramatically that the raw performance improvement gained from biasing became negligible for most modern workloads.

The Shift in Modern Java Concurrency

Modern Java programming practices shifted away from monolithic synchronization. Developers rarely rely on synchronized legacy collections, preferring:

  • Unsynchronized alternatives like ArrayList and StringBuilder for thread-local logic.
  • High-performance concurrency constructs from the java.util.concurrent package (such as ConcurrentHashMap and lock-free data structures) for multi-threaded workflows.

Because applications now rarely synchronize on objects accessed by only one thread, the scenarios where biased locking provided a noticeable advantage largely disappeared.

The Performance Cost of Revocation

Biased locking was only fast as long as a single thread locked the object. If another thread attempted to acquire a biased lock, the bias had to be "revoked" before the lock could be upgraded to a lightweight or heavyweight monitor.

Revoking a bias was exceptionally expensive. It required:

  1. Bringing all threads in the JVM to a global safepoint (a "stop-the-world" pause).
  2. Inspecting the thread stacks to determine if the biasing thread was still holding the lock.
  3. Updating the object header to remove the bias or re-bias it.
  4. Resuming the application.

In applications with reactive architectures, thread pools, or frequent handoffs of objects between worker threads, these revocation pauses caused unpredictable tail-latency spikes and severe throughput degradation. The cost of frequent revocations often far exceeded the micro-benchmarked gains of uncontended locks.

Code Complexity and Future JVM Innovations

Biased locking was deeply integrated into HotSpot's synchronization subsystem, complicating the C++ codebase across the interpreter, the C1/C2 JIT compilers, and memory management subsystems.

Maintaining this complex logic consumed valuable engineering resources and actively hindered newer JVM initiatives:

  • Project Loom (Virtual Threads): Virtual threads detach the concept of a Java thread from an OS thread, creating a mismatch with the thread-affinity assumptions built into biased locking.
  • Project Lilliput: Aimed at shrinking Java object headers from 64/128 bits down to 32 bits or less, Lilliput required reclaiming bits in the mark word that had been dedicated to tracking bias state and thread IDs.

By deprecating and removing biased locking, the OpenJDK team eliminated complex edge cases, stopped-the-world revocation pauses, and technical debt, simplifying the JVM's synchronization engine for modern multi-threaded architectures.
