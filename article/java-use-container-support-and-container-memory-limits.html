Java UseContainerSupport and Container Memory Limits

Historically, the Java Virtual Machine (JVM) was oblivious to containerized environments, reading available resources directly from the host operating system rather than the container. The UseContainerSupport flag modernizes this behavior by enabling the JVM to inspect Linux Control Groups (cgroups), allowing it to accurately detect container-level memory limits and allocate appropriate heap sizes to prevent out-of-memory crashes.

The Problem with Legacy JVM Memory Detection

In early versions of Java, the JVM retrieved available system memory and CPU cores directly from Linux kernel paths like /proc/meminfo and /proc/cpuinfo. When running inside a Docker or Kubernetes container, these files reflect the total capacity of the physical host node, not the resource constraints enforced on the container.

Consequently, a Java process running in a container restricted to 2 GB of RAM on a 64 GB host would configure its default maximum heap size based on the 64 GB host limit. If the JVM attempted to allocate memory beyond the container's 2 GB limit, the Linux Out-of-Memory (OOM) Killer would terminate the container immediately.

How UseContainerSupport Detects Limits

Introduced in Java 10 and backported to Java 8u191, -XX:+UseContainerSupport is enabled by default. It changes how the JVM initializes system ergonomics by querying the Linux control groups (cgroups) virtual filesystem rather than the host's global metrics.

The detection workflow operates through several steps:

  1. Subsystem Detection: Upon startup, the JVM checks /proc/self/mountinfo or /proc/self/cgroup to determine whether the process is bound to a cgroup hierarchy and identifies whether the host is running cgroups v1 or cgroups v2.
  2. Reading Limits:
    • In cgroups v1: The JVM inspects /sys/fs/cgroup/memory/memory.limit_in_bytes to read the hard memory limit applied to the container.
    • In cgroups v2: The JVM inspects /sys/fs/cgroup/memory.max to fetch the memory boundary.
  3. Validating Real Limits: The JVM compares the read value against the host's physical RAM. If the cgroup file contains an unlimited sentinel value (such as max or an excessively large number equal to or exceeding physical memory), the JVM falls back to the host's physical memory boundaries.
  4. Ergonomic Allocation: Once a valid container limit is established, the JVM applies its default memory ergonomics against that container limit. By default, the maximum heap size is configured to approximately 25% of the detected container memory, unless overridden by flags like -XX:MaxRAMPercentage.

CPU Detection via Cgroups

Beyond memory, UseContainerSupport applies the same logic to processing power. The JVM parses CPU quotas (cpu.cfs_quota_us and cpu.cfs_period_us in v1, or cpu.max in v2) to determine the exact number of active processor cores allocated to the container. This prevents the runtime from spinning up excessive garbage collection or ForkJoin threads based on the host's overall core count.

Configuration and Tuning

Because the flag is enabled by default in all modern Java releases, developers do not need to pass -XX:+UseContainerSupport explicitly. Instead, memory sizing is typically fine-tuned using relative sizing parameters:

  • -XX:InitialRAMPercentage: Sets the initial heap size as a percentage of the container limit.
  • -XX:MaxRAMPercentage: Sets the maximum heap size as a percentage of the container limit (commonly set to 70–80% in microservices to reserve non-heap memory).
  • -XX:MinRAMPercentage: Sets the maximum heap size for systems with small amounts of memory.

If necessary, container awareness can be disabled using -XX:-UseContainerSupport, forcing the JVM to revert to inspecting the underlying host metrics.
