Java RowSet and CachedRowSet Offline Operations

This article explains the purpose of Java's RowSet interface and examines how the CachedRowSet implementation operates in a disconnected, offline mode. You will learn the limitations of traditional ResultSet objects, the advantages provided by the RowSet framework, and the step-by-step lifecycle of fetching, modifying, and synchronizing database records without maintaining an active database connection.

The Purpose of the RowSet Interface

Introduced in the javax.sql package, the RowSet interface extends java.sql.ResultSet to make tabular data more flexible, component-friendly, and easier to use across distributed architectures. While a standard JDBC ResultSet maintains an open connection to the database and is tightly coupled to the underlying driver, the RowSet interface introduces significant design improvements:

  • JavaBeans Compliance: RowSet implementations follow the JavaBeans model. They provide standard getter and setter methods, support properties, and implement an event-listener model that notifies registered components when the cursor moves or data changes.
  • Scrollability and Updatability by Default: Unlike basic ResultSet objects, which are often forward-only and read-only depending on driver capabilities, standard RowSet implementations are scrollable and updatable by default.
  • Connected vs. Disconnected Modes: The interface supports two operational models. Connected implementations (such as JdbcRowSet) keep a persistent connection open, acting as wrappers around traditional ResultSet objects. Disconnected implementations (such as CachedRowSet, WebRowSet, and FilteredRowSet) fetch their data into memory and immediately sever the database connection.

How CachedRowSet Operates Offline

CachedRowSet is the foundational disconnected RowSet implementation. It stores tabular data entirely in memory, eliminating the need to keep physical database connections open during long-running client operations or user interactions.

The offline operation of CachedRowSet follows a distinct four-phase lifecycle:

1. Connection and Population

To retrieve data, CachedRowSet configures its connection properties (such as JDBC URL, username, and password) and executes a query via its execute() method. Alternatively, it can be populated directly from an existing ResultSet using the populate(ResultSet rs) method.

Once the data is copied from the database into the memory of the CachedRowSet, the underlying physical database connection, statement, and original ResultSet are closed immediately.

2. In-Memory Manipulation

Because the connection is closed, the application works entirely in an "offline" state. The client can perform all standard navigation and modification tasks locally:

  • Navigate bidirectionally (next(), previous(), absolute()).
  • Read values using standard accessor methods.
  • Update existing rows using updateString(), updateInt(), etc., followed by updateRow().
  • Insert new rows using moveToInsertRow(), setting values, and invoking insertRow().
  • Delete rows using deleteRow().

During this phase, CachedRowSet tracks both the original values retrieved from the database and the modified values in internal data structures.

3. Serialization and Network Transport

Because standard ResultSet objects maintain an active network socket with the database, they cannot be serialized across a network. In contrast, CachedRowSet objects are serializable. This allows an enterprise backend to query a database, populate a CachedRowSet, close the connection, and send the data across network boundaries (such as via RMI or HTTP) to thin clients or remote services for display and editing.

4. Reconnection and Synchronization

Once offline modifications are complete, the client pushes changes back to the database by invoking the acceptChanges() method. This triggers an automated synchronization process:

  1. Re-establishing Connection: The CachedRowSet uses its internal metadata to reopen a connection to the data source.
  2. Conflict Detection: It employs a SyncProvider (such as the default RIOptimisticProvider) to detect concurrency conflicts using optimistic locking. It compares the original values cached during the initial query against the current values present in the database.
  3. Data Propagation: If no other transaction has modified the target records in the database, the CachedRowSet executes the necessary UPDATE, INSERT, or DELETE SQL statements to apply the changes.
  4. Conflict Handling: If another user altered the underlying records while the CachedRowSet was offline, a SyncProviderException is thrown, allowing the application to resolve conflicts using compensation logic.
  5. Connection Closure: The temporary database connection is automatically closed once synchronization finishes.
