Java Custom Validation with ConstraintValidator

This article explains how custom constraint validation operates in Java using the Jakarta Bean Validation API and the ConstraintValidator interface. It covers the creation of custom annotations, the lifecycle and implementation of the ConstraintValidator interface, and the internal workflow the validation engine executes to validate data models at runtime.

The Role of Custom Constraint Validation

Java Bean Validation (Jakarta Validation) provides standard annotations like @NotNull and @Size, but domain-specific rules often require custom logic. Custom validation operates by linking a custom annotation to an implementation of the ConstraintValidator interface, which contains the execution logic to evaluate incoming values.

1. Defining the Custom Annotation

The process begins with defining a custom validation annotation. This annotation must be annotated with @Constraint to link it directly to the validator class responsible for checking the rule.

@Target({ ElementType.FIELD, ElementType.PARAMETER })
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = PhoneNumberValidator.class)
@Documented
public @interface ValidPhoneNumber {
    String message() default "Invalid phone number format";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

The validatedBy attribute instructs the validation provider (such as Hibernate Validator) which class executes the validation logic.

2. Implementing the ConstraintValidator Interface

The ConstraintValidator<A, T> interface requires two generic type parameters:

  • A: The annotation type being handled (e.g., ValidPhoneNumber).
  • T: The type of data being validated (e.g., String).

The interface contains two primary methods:

  • initialize(A constraintAnnotation): Invoked by the validation engine after the validator is instantiated. It allows the validator to read and store configuration attributes defined in the annotation instance. In modern Bean Validation versions, this method has a default empty implementation.
  • isValid(T value, ConstraintValidatorContext context): Contains the core validation logic. It accepts the target value to validate and returns a boolean—true if the value satisfies the constraint, or false if it violates it.
public class PhoneNumberValidator implements ConstraintValidator<ValidPhoneNumber, String> {

    @Override
    public void initialize(ValidPhoneNumber constraintAnnotation) {
        // Initialization logic or reading annotation parameters
    }

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null) {
            return true; // Best practice: let @NotNull handle null checks
        }
        return value.matches("\\d{10}");
    }
}

3. How the Validation Engine Operates at Runtime

When validation is triggered on an object (either explicitly via Validator.validate() or automatically via frameworks like Spring Boot with @Valid):

  1. Discovery: The validator inspects the class metadata, identifying fields, methods, or class-level targets decorated with constraint annotations.
  2. Validator Resolution: The engine inspects the @Constraint(validatedBy = ...) meta-annotation. It locates and instantiates the designated ConstraintValidator class. In managed environments like Spring or CDI, the validator can use dependency injection for services or repositories.
  3. Initialization: The framework calls the initialize() method, passing the annotation instance so the validator can capture dynamic properties (such as regex patterns or thresholds).
  4. Evaluation: The framework passes the property's actual runtime value to isValid().
  5. Context Manipulation: If validation fails, the validator can use the ConstraintValidatorContext argument to disable default error messages and construct dynamic, parameterized violation messages.
  6. Result Handling: If isValid() returns false, the engine constructs a ConstraintViolation object and adds it to the set of violations. If all validators return true, execution proceeds normally.
