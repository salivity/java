Defensive Copying in Java: Protecting Mutable State

Defensive copying is a programming technique in Java used to protect a class's internal state from unintended modifications by external code. When a class stores mutable objects, simply assigning references in constructors or returning them from getter methods breaks encapsulation by allowing callers to modify private fields directly. This article explains the mechanics of defensive copying, demonstrates how it prevents data corruption through incoming and outgoing object references, and outlines best practices for maintaining strict immutability.

The Vulnerability of Shared Mutable State

Encapsulation requires that an object manage its own state and prevent unauthorized external alterations. Declaring fields as private final is often insufficient when those fields reference mutable types, such as arrays, collections, or legacy classes like java.util.Date.

When an object receives a reference to a mutable object in its constructor and assigns it directly to an internal field, the caller retains access to that exact same instance in memory. Any subsequent modification made by the caller instantly changes the internal state of the newly created object, bypassing validation rules and breaking class invariants. A similar vulnerability occurs when a getter method returns a direct reference to an internal mutable field; the receiving code can mutate the object's internal data without invoking any setter or domain method.

How Defensive Copying Works

Defensive copying mitigates these risks by creating independent duplicates of mutable objects at critical boundary points: during object construction and during state retrieval.

1. Inbound Defensive Copying (Constructors)

When accepting mutable objects into a constructor, you must create a clone or a new instance of that object and store the copy rather than the original reference.

public final class Period {
    private final Date start;
    private final Date end;

    public Period(Date start, Date end) {
        // Create copies before validating or storing
        this.start = new Date(start.getTime());
        this.end = new Date(end.getTime());

        if (this.start.compareTo(this.end) > 0) {
            throw new IllegalArgumentException("Start must be before end");
        }
    }
}

In this pattern, defensive copies are created before validating parameters. This sequence protects the class against Time-Of-Check to Time-Of-Use (TOCTOU) attacks, where another thread might alter the mutable parameters in the brief window between validation and assignment.

2. Outbound Defensive Copying (Accessors)

When exposing internal mutable fields via getter methods, you must return a new copy rather than the internal reference itself.

public Date getStart() {
    return new Date(this.start.getTime());
}

public Date getEnd() {
    return new Date(this.end.getTime());
}

By returning a new instance, any mutation performed by the caller (such as calling .setTime(...)) modifies only their local copy, leaving the original object's internal state intact.

Defensive Copying with Collections

Collections are inherently mutable and require special care. For collections, defensive copying can be achieved by instantiating a new collection or by returning an unmodifiable view:

  • In Constructors: Use copy constructors or factory methods, such as new ArrayList<>(providedList) or List.copyOf(providedList).
  • In Getters: Return Collections.unmodifiableList(internalList) or List.copyOf(internalList) to prevent callers from invoking mutating methods like .add() or .clear().

Best Practices and Alternatives

While defensive copying preserves encapsulation, creating unnecessary objects can introduce memory and performance overhead.

To minimize the need for defensive copying:

  • Favor Immutable Types: Use modern immutable alternatives whenever available. For example, replace java.util.Date with classes from the java.time package (Instant, LocalDate, LocalDateTime), which are immutable by design and can be safely shared without copying.
  • Document Exceptions: If performance constraints make copying prohibitive, clearly document that the caller must transfer ownership of the object and must not modify it after passing it to the class.
