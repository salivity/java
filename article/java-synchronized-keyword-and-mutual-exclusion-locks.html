Java Synchronized Keyword and Mutual Exclusion Locks

In Java, the synchronized keyword provides mutual exclusion by utilizing intrinsic locks (also known as monitors) built into every Java object. When a thread enters a synchronized block or method, it must acquire the target object's monitor, forcing any other competing threads into a blocked state until the lock is released. This article explains the low-level mechanics behind this process, including object headers, JVM bytecode instructions, reentrancy handling, and memory visibility guarantees.

The Concept of Intrinsic Locks

Every object in Java is intrinsically associated with a monitor. A monitor acts as a mutually exclusive lock that guards critical sections of code. When execution reaches a synchronized context, the Java Virtual Machine (JVM) checks the state of the monitor belonging to the reference object:

  • For synchronized instance methods, the lock is held on the current instance (this).
  • For synchronized static methods, the lock is held on the java.lang.Class object associated with the class.
  • For synchronized blocks, the lock is held on whichever object reference is explicitly passed to the statement (e.g., synchronized(lockObject)).

Bytecode Implementation

The JVM enforces synchronization differently depending on whether it is applied to a method or a code block.

1. Synchronized Blocks

When compiling a synchronized block, the Java compiler emits two specific bytecode instructions:

  • monitorenter: Executed when entering the block. The executing thread attempts to gain ownership of the monitor associated with the referenced object.
  • monitorexit: Executed when leaving the block. The compiler automatically inserts multiple monitorexit instructions—one for normal execution flow and others wrapped inside an implicit exception handling table to guarantee the lock is freed even if an unhandled exception occurs.

2. Synchronized Methods

Synchronized methods do not use monitorenter and monitorexit instructions directly in their code array. Instead, the compiler adds the ACC_SYNCHRONIZED flag to the method's access flags in the constant pool. When a thread invokes a method with this flag, the JVM automatically acquires the appropriate monitor before running the method body and releases it when the method completes (normally or abruptly).

The Role of the Object Header (Mark Word)

At the memory level, the JVM tracks the state of an object's lock using its Mark Word, which is part of the object header. The Mark Word stores runtime metadata, including hash codes, garbage collection age, and lock state bits.

Depending on JVM optimizations and thread contention, the lock transitions through several states:

  1. Biased Locking: The lock is dedicated to a single thread without atomic operations until another thread contends for it.
  2. Lightweight Locking: If contention occurs without blocking, the thread creates a BasicObjectLock in its execution stack and attempts a Compare-And-Swap (CAS) operation to point the object's Mark Word to its stack frame.
  3. Heavyweight Locking: If contention persists, the lock inflates into a heavyweight monitor managed by the underlying operating system. At this stage, blocked threads are descheduled and placed into a wait queue managed by OS mutexes.

Lock Reentrancy and the Counter

Java's mutual exclusion locks are fully reentrant. An intrinsic lock maintains a reference to the owner thread and an acquisition counter:

  1. When a thread acquires the lock, the monitor records the thread's ID, and the counter is set to 1.
  2. If the same thread attempts to acquire the lock again (such as calling another synchronized method on the same object), the JVM recognizes the thread identity and simply increments the counter.
  3. Each exit decrements the counter. The lock is only completely released and made available to other competing threads when the counter drops to 0.

Memory Visibility and Happens-Before

Beyond mutual exclusion, the synchronized keyword enforces memory consistency. Under the Java Memory Model (JMM), acquiring a lock automatically invalidates the local CPU cache, forcing the thread to reload variables from main memory. Conversely, releasing a lock forces all modified variables to be flushed back to main memory.

This behavior creates a formal happens-before relationship: any action taken by a thread prior to releasing a lock is guaranteed to be visible to any other thread that subsequently acquires the same lock.
