Shenandoah GC: Ultra-Low Pause Times in Java

The Shenandoah Garbage Collector (GC) achieves ultra-low, deterministic pause times in Java by executing the vast majority of its memory reclamation work concurrently with running application threads. Unlike traditional collectors that pause the application during object evacuation and compaction, Shenandoah moves objects and updates references simultaneously with user code. This architectural design ensures that stop-the-world (STW) pauses are typically measured in milliseconds or sub-milliseconds, remaining virtually independent of the total heap size.

The Core Challenge: Concurrent Evacuation

In standard JVM garbage collectors like Parallel GC or the original implementations of G1 GC, marking live objects can happen concurrently, but the evacuation phase—moving surviving objects to compact heap memory—requires pausing all mutator (application) threads. Because moving an object changes its memory address, stopping application threads prevents them from accessing stale or invalid memory locations.

Shenandoah eliminates this limitation by performing object evacuation concurrently. It allows application threads to read and write to objects even while those exact objects are being relocated to new memory regions.

Load-Reference Barriers

The primary mechanism enabling concurrent evacuation is the Load-Reference Barrier (LRB). Introduced to replace the older Brooks pointer model, the LRB intercepts heap reads to ensure mutator threads always access the most up-to-date version of an object.

When an application thread attempts to access an object reference, the LRB performs a fast check:

  1. If the target object is not in the collection set (regions being evacuated), execution continues with zero overhead.
  2. If the object is in the collection set and has already been evacuated, the barrier transparently redirects the pointer to the new memory address (the "to-space" copy).
  3. If the object has not yet been evacuated, the running thread assists the GC by copying the object itself using an atomic compare-and-swap (CAS) operation, updates the forwarding pointer, and then proceeds with the access.

This self-healing and cooperative model guarantees thread safety and data consistency without halting the entire application.

The Shenandoah GC Cycle

Shenandoah splits garbage collection into distinct phases, keeping pauses brief and deterministic:

  1. Init Mark (STW): A brief pause to scan the root set (thread stacks, global variables).
  2. Concurrent Marking: Traverses the live object graph across the heap concurrently with mutator threads to determine reachable objects.
  3. Final Mark (STW): A short pause to flush pending marking tasks and choose the regions with the most garbage (the collection set).
  4. Concurrent Evacuation: Worker threads and mutators actively copy live objects out of the collection set into free regions.
  5. Init Update Refs (STW): An extremely brief pause ensuring that all GC and mutator threads have finished relocating objects.
  6. Concurrent Update References: Iterates over the entire heap concurrently, updating every stale pointer that still refers to the old memory addresses.
  7. Final Update Refs (STW): A final, brief pause to update root references and reclaim the fully evacuated regions.

Trade-offs for Ultra-Low Latency

Shenandoah trades raw application throughput and CPU overhead to eliminate latency spikes. The continuous execution of load-reference barriers and concurrent worker threads requires extra CPU cycles, which can slightly reduce peak computational throughput compared to throughput-oriented collectors like Parallel GC. However, for systems where responsiveness, predictable latency SLAs, and large heap sizes (from gigabytes to terabytes) are paramount, Shenandoah successfully delivers pause times that remain consistently low.
