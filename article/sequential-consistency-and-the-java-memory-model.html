Sequential Consistency and the Java Memory Model

This article explores the concept of sequential consistency in concurrent computing and examines how it is addressed by the Java Memory Model (JMM). It defines sequential consistency, explains the conditions required for a system to satisfy this model, and clarifies whether Java guarantees sequentially consistent execution when programs contain data races.

What Is Sequential Consistency?

Sequential consistency is a consistency model first formally defined by Leslie Lamport in 1979. It serves as an intuitive benchmark for concurrent systems, describing how developers naturally expect multithreaded programs to execute.

A system is sequentially consistent if it satisfies two core conditions:

  1. Program Order: The operations of each individual processor or thread appear to execute in the exact order specified by the program code.
  2. Single Global Order: All operations appear to execute in a single, total, interleaved order that is observed identically by every thread in the system.

In a sequentially consistent environment, memory acts like a centralized global storage unit with a switch that connects to one thread at a time. Every read operation immediately sees the value written by the most recent write operation in this global execution sequence.

The Java Memory Model and Sequential Consistency

Modern hardware architectures and optimizing compilers regularly reorder instructions, utilize store buffers, and rely on local CPU caches. Enforcing global sequential consistency for every memory operation imposes severe performance penalties. Consequently, the Java Memory Model (JMM) does not enforce sequential consistency across all executions by default.

Instead, the JMM provides a formal guarantee known as Sequential Consistency for Data-Race-Free (SC-DRF) programs. If a Java program is correctly synchronized—meaning it contains no data races—the JMM guarantees that the execution will appear sequentially consistent.

Synchronization in Java is achieved using primitives such as the synchronized keyword, volatile variables, and classes from the java.util.concurrent package. These constructs establish happens-before relationships, ensuring that memory writes by one thread become visibly ordered to reads by other threads.

Does the JMM Guarantee Sequential Consistency for Data Races?

No, the Java Memory Model does not guarantee sequential consistency for programs that contain data races.

A data race occurs when:

  • Two or more threads concurrently access the same memory location (variable).
  • At least one of these accesses is a write.
  • The accesses are not ordered by a happens-before relationship.

When a data race is present, the JMM permits compilers to reorder instructions, CPUs to flush caches asynchronously, and threads to observe actions in different orders. For example, if Thread A writes to variable x and then to variable y, Thread B may observe the update to y before it observes the update to x. This directly violates the program order requirement of sequential consistency.

What the JMM Guarantees Under Data Races

Although sequential consistency is abandoned in the presence of data races, the JMM does not allow arbitrary behavior. Java still enforces certain safety boundaries:

  • Type Safety: The runtime prevents memory corruption. A thread will never read an arbitrary bit-pattern that violates object typing.
  • Out-of-Thin-Air Safety: A variable will only hold a value that was actually written to it by some thread, or its default initial value (such as 0 or null). Values cannot materialize out of nowhere.
  • Primitive Integrity: With the exception of non-volatile 64-bit primitives (long and double on some 32-bit platforms), reads and writes to primitive references are atomic.

In summary, the Java Memory Model only guarantees sequential consistency for data-race-free programs. Once a program exhibits a data race, sequential consistency is lost, leading to non-intuitive reorderings and visibility anomalies.
