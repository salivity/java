Certificate Revocation in Java Trust Managers

This article provides an overview of how certificate revocation checking functions within standard Java trust managers. By default, standard Java Secure Socket Extension (JSSE) trust managers do not check certificate revocation during TLS handshakes to prevent latency and network failure vulnerabilities. However, the underlying Public Key Infrastructure for X.509 (PKIX) validation engine natively supports both Certificate Revocation Lists (CRLs) and the Online Certificate Status Protocol (OCSP). Below is an explanation of the default behavior, the configuration properties required to enable checking, the verification workflow, and modern enhancements such as OCSP stapling.

Default Behavior

Standard Java TLS client connections rely on the TrustManagerFactory using the default algorithm (typically PKIX). While the PKIX engine is fully capable of validating revocation status, revocation checking is explicitly disabled by default.

If revocation checking is left disabled, the trust manager only validates the certificate's validity dates, its digital signature path against a trusted root in the cacerts or configured truststore, and constraints such as basic constraints or key usage. A revoked certificate with a valid signature and valid timeframe will be accepted.

Enabling Revocation Checking via System Properties

To activate revocation checking in standard JSSE trust managers without altering application code, you must set specific system and security properties:

  1. Enable TLS-Level Revocation: Set the system property com.sun.net.ssl.checkRevocation=true. This instructs the JSSE PKIX trust manager to pass the revocation flag to the underlying CertPathValidator.
  2. Enable CRL Distribution Points: Set com.sun.security.enableCRLDP=true. When enabled, the validator downloads and parses CRLs listed in the certificate's CRL Distribution Points (CRLDP) extension.
  3. Enable OCSP: Set the security property ocsp.enable=true (or via -Docsp.enable=true). This activates OCSP validation using the Authority Information Access (AIA) extension found within the certificate.

The Validation Workflow

When revocation checking is active, the trust manager executes the following process during a TLS handshake:

  1. Path Building: The trust manager builds a certificate chain from the peer's end-entity certificate back to a trusted anchor in the truststore.
  2. Order of Evaluation: The engine prefers OCSP by default if configured, falling back to CRLDP if OCSP fails or is unavailable.
  3. Fetching Revocation Data:
    • OCSP: The client sends a request to the OCSP responder URI specified in the AIA extension of the certificate. The responder replies with a cryptographically signed status: Good, Revoked, or Unknown.
    • CRL: If using CRLs, the client downloads the full CRL file over HTTP/LDAP from the CRLDP URI, validates the signature on the CRL, and checks if the certificate serial number is listed.
  4. Caching: Java maintains in-memory caches for CRLs and OCSP responses to minimize the performance overhead of querying remote servers on every connection.
  5. Decision: If any certificate in the path is marked as revoked, a CertificateException (specifically a CertPathValidatorException) is thrown, immediately aborting the TLS handshake.

Network Failures and Fallback (Soft-Fail vs. Hard-Fail)

Standard Java revocation checking implements a "soft-fail" model by default for network issues. If an OCSP responder or CRL server is unreachable, times out, or returns an HTTP error, the trust manager may log a warning and proceed with the connection.

To enforce strict validation ("hard-fail"), administrators must configure custom PKIXRevocationChecker options programmatically to avoid proceeding when revocation status cannot be definitively confirmed.

OCSP Stapling (TLS Certificate Status Request)

Since Java 9, client-side OCSP stapling is supported. Instead of the client querying the CA's OCSP responder directly, the server fetches the OCSP response in advance and "staples" it to the certificate during the TLS handshake.

To enable client-side OCSP stapling support in Java:

  • Set -Djdk.tls.client.enableStatusRequestExtension=true

When enabled, the trust manager inspects the stapled response provided by the server, eliminating the latency and availability risks associated with real-time outbound client HTTP queries.

Programmatic Configuration

For granular control, developers can configure revocation directly in code by creating custom PKIXBuilderParameters alongside a CertPathTrustManagerParameters instance:

CertPathBuilder cpb = CertPathBuilder.getInstance("PKIX");
PKIXRevocationChecker rc = (PKIXRevocationChecker) cpb.getRevocationChecker();
rc.setOptions(EnumSet.of(
    PKIXRevocationChecker.Option.ONLY_END_ENTITY,
    PKIXRevocationChecker.Option.NO_FALLBACK
));

PKIXBuilderParameters params = new PKIXBuilderParameters(trustStore, new X509CertSelector());
params.addCertPathChecker(rc);

TrustManagerFactory tmf = TrustManagerFactory.getInstance("PKIX");
tmf.init(new CertPathTrustManagerParameters(params));

This approach allows the enforcement of strict policies, such as checking only end-entity certificates or requiring specific fallback behaviors.
