How ArrayBlockingQueue Implements Bounded Buffers

In Java, ArrayBlockingQueue implements bounded buffer synchronization by combining a fixed-size circular array with the thread-coordination capabilities of ReentrantLock and two Condition variables. It provides a thread-safe, bounded FIFO (First-In, First-Out) data structure where producer threads wait when the buffer is full and consumer threads wait when the buffer is empty. This classic producer-consumer problem is resolved efficiently through explicit lock management, state-checking loops, and targeted thread signaling.

Core Components

The synchronization mechanism relies on four primary internal variables:

  1. Circular Object Array (Object[] items): The fixed-capacity backing array storing the elements.
  2. ReentrantLock (final ReentrantLock lock): A single mutual exclusion lock that guards all access to internal state, including array insertions, removals, and counter modifications. It can be configured with a fairness policy via its constructor.
  3. Condition notEmpty: A condition variable associated with lock that causes consumer threads to block when the buffer contains zero elements.
  4. Condition notFull: A condition variable associated with lock that causes producer threads to block when the array reaches its maximum capacity.

Pointers putIndex, takeIndex, and an integer count track the insertion index, removal index, and current total elements, respectively.

The Enqueue Process (Producers)

When a producer inserts an item using blocking methods like put(E e), synchronization proceeds as follows:

  1. Lock Acquisition: The thread acquires the lock using lock.lockInterruptibly().
  2. Buffer Capacity Check: The method checks if the buffer is full using a while loop: 
    while (count == items.length) {
    notFull.await();
}
    A loop is mandatory instead of an if statement to guard against spurious wakeups and state changes caused by other threads before this thread reacquires the lock.
  3. Item Insertion: Once space is available, the element is placed into items[putIndex].
  4. Pointer and Count Update: The putIndex increments. If it reaches the end of the array, it wraps around to 0 (circular buffer design). The count variable is incremented.
  5. Signaling Consumers: The method signals the notEmpty condition via notEmpty.signal(), notifying one blocked consumer that an item is ready for processing.
  6. Lock Release: The lock is released in a finally block.

The Dequeue Process (Consumers)

When a consumer removes an item via take(), the complementary process occurs:

  1. Lock Acquisition: The consumer acquires the lock using lock.lockInterruptibly().
  2. Buffer Emptiness Check: The method checks if the queue is empty: 
    while (count == 0) {
    notEmpty.await();
}
    If empty, the consumer thread releases the lock and transitions to a waiting state until signaled.
  3. Item Extraction: The item at items[takeIndex] is retrieved, and the reference in the array is set to null to facilitate garbage collection.
  4. Pointer and Count Update: The takeIndex increments, wrapping back to 0 if it reaches capacity. The count variable is decremented.
  5. Signaling Producers: The method invokes notFull.signal(), alerting one waiting producer that buffer space has been freed.
  6. Lock Release: The lock is unconditionally released in a finally block.

Circular Buffer Mechanics

ArrayBlockingQueue avoids shifting elements when items are removed. Instead, it moves its internal pointers putIndex and takeIndex sequentially through the array. When either index reaches the end of the backing array (items.length), it resets to index 0. This makes insertion and removal operations \(O(1)\) while eliminating the memory overhead of node allocations.

Single-Lock Architecture Trade-Off

Unlike LinkedBlockingQueue, which uses two separate locks for reading and writing, ArrayBlockingQueue relies on a single ReentrantLock for both operations. Because producers and consumers share modifications to the array indices and the single count variable, sharing one lock minimizes memory footprint and simplifies concurrency invariants. The trade-off is higher contention, as producers and consumers cannot mutate the queue concurrently.
