Why Swallowing InterruptedException Is an Anti-Pattern

In Java concurrency, swallowing an InterruptedException—catching the exception and neither rethrowing it nor restoring the thread's interrupt status—is a dangerous anti-pattern that sabotages thread coordination. This article explains the mechanics of thread interruption in Java, the specific runtime failures caused by ignoring interrupted exceptions, and the correct patterns to ensure responsive, resilient multithreaded applications.

Understanding Thread Interruption

Thread interruption in Java is a cooperative cancellation mechanism, not a preemptive halt. Calling Thread.interrupt() sets a boolean flag on the target thread signaling that it should stop what it is doing.

When a thread is blocked in an interruptible method—such as Thread.sleep(), Object.wait(), or BlockingQueue.take()—the JVM detects the interrupt, clears the thread's interrupted status flag, and throws an InterruptedException.

The Anti-Pattern: Swallowing the Exception

The anti-pattern occurs when a developer catches the exception with an empty block or merely logs it without taking corrective action:

// Anti-Pattern: Swallowing InterruptedException
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    // Empty catch block or just logging
    logger.error("Interrupted", e);
}

Because the JVM clears the interrupted status when throwing the exception, simply logging it or doing nothing completely erases the evidence that the interruption ever occurred.

Why Swallowing InterruptedException Causes Failures

1. It Breaks Cooperative Cancellation

When an upstream caller (such as a thread pool or task runner) cancels a task, it expects the task to detect the signal and exit cleanly. By swallowing the exception, the task resumes execution as if nothing happened, ignoring shutdown instructions and running indefinitely.

2. It Prevents Graceful Shutdown of ExecutorServices

Frameworks like ExecutorService rely on interruption to shut down worker threads when calling shutdownNow(). If tasks running inside those workers swallow interrupts, the executor cannot stop its worker threads, preventing application exit or causing hung deployments.

3. It Creates Zombie Threads and Resource Leaks

Threads that fail to honor interruption continue to consume CPU, memory, and database connections long after their owning component has attempted to destroy them.

4. It Masks Context from Callers Up the Stack

Code higher up in the call stack may need to execute rollback logic, clean up file handles, or report task cancellation. Swallowing the exception hides this context entirely.

How to Correctly Handle InterruptedException

There are two primary ways to handle an InterruptedException correctly:

1. Propagate the Exception

If the current method's signature can be modified, rethrow the exception so callers can decide how to handle it.

public void processQueue() throws InterruptedException {
    // Let the caller handle the cancellation
    queue.take();
}

2. Restore the Interrupted Status

If implementing an interface where the method signature cannot be changed (such as Runnable.run()), restore the thread's interrupt status using Thread.currentThread().interrupt().

public void run() {
    try {
        while (!Thread.currentThread().isInterrupted()) {
            performWork();
            Thread.sleep(1000);
        }
    } catch (InterruptedException e) {
        // Restore interrupted status
        Thread.currentThread().interrupt();
    } finally {
        cleanUpResources();
    }
}

Restoring the flag ensures that code higher in the call stack or the thread pool itself can still inspect Thread.currentThread().isInterrupted() and handle the shutdown request appropriately.
