Hardening Java Deserialization Against RCE

Insecure Java deserialization occurs when untrusted data is processed by an application to recreate objects, often allowing attackers to leverage existing classes on the classpath to achieve remote code execution (RCE). Hardening deserialization requires a defense-in-depth approach that minimizes the acceptance of serialized binary objects, enforces strict validation before instantiation, audits runtime dependencies, and restricts the execution environment. The following practices provide effective, production-ready safeguards to secure Java applications against serialization-based exploits.

1. Avoid Native Java Serialization

The most reliable defense against deserialization attacks is to avoid java.io.Serializable and standard ObjectInputStreams entirely. Where possible, migrate communication protocols and persistence layers to structured, data-only formats such as JSON, Protocol Buffers, FlatBuffers, or Avro. When using third-party parsers like Jackson or Fastjson, explicitly disable polymorphic type handling (such as Jackson's default typing) to ensure incoming payloads cannot instantiate arbitrary classes.

2. Implement Look-Ahead Deserialization Filters

When native serialization is unavoidable, enforce look-ahead validation using Java's built-in filtering mechanisms introduced in JEP 290 and enhanced in JEP 415. Standard deserialization instantiates objects before application logic can validate them; look-ahead filters evaluate class names, array sizes, and graph depths prior to object creation.

  • Use strict allowlists: Define an ObjectInputFilter that accepts only the explicit set of classes required by the business logic, rejecting all others (!*).
  • Configure global filters: Set the JVM-wide filter property via the jdk.serialFilter system property or in the conf/security/java.security file to protect the application globally.
  • Limit graph depth and array allocations: Configure limits on graph depth, maximum references, and stream size to prevent Denial of Service (DoS) attacks involving recursive object structures.

3. Eliminate and Audit Gadget Chains on the Classpath

Attackers execute arbitrary code by chaining together methods ("gadgets") present in common libraries on the application's classpath, such as specific versions of Apache Commons Collections, Spring, or Groovy.

  • Regularly scan dependencies: Utilize Software Composition Analysis (SCA) tools to detect and patch libraries known to contain deserialization gadget chains.
  • Minimize the classpath: Practice classpath hygiene by removing unused dependencies and packaging applications as minimal modular runtimes via jlink. A smaller classpath drastically reduces the likelihood that an attacker can construct an executable gadget chain.

4. Apply Cryptographic Integrity Controls

If serialized data must be transmitted across untrusted network boundaries or stored in client-accessible states (such as cookies or tokens), treat the payload as untrusted until its integrity is cryptographically verified:

  • Sign serialized objects using an HMAC or digital signature before transmission.
  • Verify the signature using a secure, constant-time comparison before passing the raw byte stream to ObjectInputStream.
  • Rotate signing keys regularly and avoid hardcoding cryptographic secrets in the codebase.

5. Restrict Execution Privileges

Apply principle-of-least-privilege controls to the underlying system to contain the impact if an exploit bypasses application-level defenses:

  • Container Isolation: Run the JVM inside an unprivileged container with a read-only root filesystem and dropped capabilities.
  • Operating System Controls: Restrict outbound network access from application servers to prevent reverse shells, which are typical payloads in successful RCE exploits.
  • OS-Level Sandboxing: Use SELinux, AppArmor, or minimal dedicated OS user accounts to limit the application's ability to spawn subprocesses or access sensitive host directories.
