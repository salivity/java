Unified JVM Logging and -Xlog Flag Configuration

Unified JVM Logging is a standardized framework introduced in Java 9 to replace fragmented legacy logging options with a single, coherent command-line interface. This article explores the architecture of Unified JVM Logging and details how to configure the -Xlog flag to capture precise runtime metrics—such as garbage collection, safepoint pauses, and JIT compilation events—to effectively identify bottlenecks and tune Java application performance.

What is Unified JVM Logging?

Prior to Java 9, HotSpot JVM components used disjointed, ad-hoc command-line flags to generate diagnostic information (for example, -XX:+PrintGCDetails, -XX:+PrintGCDateStamps, and -XX:+PrintCompilation). Unified JVM Logging (introduced via JEP 158) consolidated all HotSpot subsystem logging into a unified infrastructure controlled exclusively via the -Xlog flag.

This subsystem provides a consistent syntax for routing logs, filtering by subsystem, controlling log severity levels, formatting log metadata, and managing file rotation.

The -Xlog Command Syntax

The general syntax for the -Xlog option follows this pattern:

-Xlog:[selectors]:[output]:[decorators]:[output-options]

Each component operates as follows:

  1. Selectors (tag1[+tag2...][=level]): Defines what to log and at what verbosity.
    • Tags: Identify the JVM component (e.g., gc, safepoint, class, jit, os, compiler). Using + requires all specified tags to match; using * acts as a wildcard for any tag combinations containing the base tag (e.g., gc*).
    • Levels: Determine verbosity. Available levels in ascending order are off, trace, debug, info, warning, and error. The default level is info.
  2. Output: Specifies destination. Options are stdout, stderr, or file=<path>. If omitted, output defaults to stdout.
  3. Decorators: Specify the metadata prepended to each log message. Common decorators include:
    • time (ISO-8601 calendar timestamp)
    • uptime (time since JVM launch)
    • pid (process identifier)
    • tid (thread identifier)
    • level (log level)
    • tags (associated tags)
  4. Output-Options: Configures log file behavior, specifically file rotation:
    • filesize=<size> (e.g., 100M)
    • filecount=<number> (number of rotated files to retain)

Configuring -Xlog for Performance Tuning

Performance tuning requires targeted diagnostic data without overwhelming disk I/O. Below are the most critical -Xlog configurations used to tune JVM performance.

1. Garbage Collection (GC) Monitoring

Garbage collection pauses directly affect application throughput and latency. To capture detailed GC behavior, memory pool changes, and individual collection phases:

-Xlog:gc*,gc+phases=debug:file=/var/log/jvm/gc.log:time,uptime,pid:filecount=5,filesize=100M
  • gc*: Captures high-level GC events and ergonomics.
  • gc+phases=debug: Logs time spent in individual sub-phases of collectors like G1, ZGC, or Shenandoah, revealing which phase causes high tail latencies.
  • time,uptime,pid: Allows log correlation with host operating system events and Application Performance Monitoring (APM) tools.

2. Safepoint and Stop-the-World (STW) Pauses

Applications may encounter latency spikes caused by safepoint operations unrelated to GC, such as biased lock revocation, code deoptimization, or thread dumps.

-Xlog:safepoint=debug:file=/var/log/jvm/safepoints.log:uptime,tags,level:filecount=3,filesize=50M

This configuration logs:

  • Time taken to bring all application threads to a safepoint ("time to safepoint" / tts).
  • The duration threads remained stopped.
  • The specific operation that triggered the safepoint.

3. JIT Compilation Activity

JIT compilation consumes CPU and can cause temporary performance degradation during application warmup or after phase changes.

-Xlog:jit+compilation=info:file=/var/log/jvm/jit.log:time,uptime:filecount=3,filesize=50M
  • Tracks method compilation levels (C1 vs. C2).
  • Highlights aggressive recompilations, deoptimizations, and code cache pressure.

Best Practices for Production Logging

  • Use Asynchronous Logging: Synchronous disk writes during logging can stall JVM threads. Starting in Java 17, use the -Xlog:async flag alongside -XX:AsyncLogBufferSize=<bytes> to offload I/O writes to an intermediate ring buffer managed by a background thread.
  • Always Rotate Log Files: In production environments, never log directly to unbounded files. Explicitly define filecount and filesize to avoid consuming all available disk space.
  • Keep Verbosity Controlled: Avoid using trace in production, as the volume of generated data can saturate CPU and memory buses. Reserve debug and trace for isolated environments or targeted, temporary investigations.
