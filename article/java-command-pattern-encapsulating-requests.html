Java Command Pattern: Encapsulating Requests

The Command design pattern encapsulates a request as a stand-alone object containing all the information needed to perform an action. This article explores how the pattern functions within Java systems, breaking down its core architectural components, demonstrating how it decouples request senders from execution logic, and highlighting practical implementation techniques, including object-oriented and functional approaches in modern Java.

The Core Mechanism of Encapsulation

In standard object-oriented programming, direct communication requires the caller (the sender) to know the specific method signature and type of the callee (the receiver). The Command pattern breaks this coupling by introducing an abstraction layer between the two.

Instead of invoking a method directly, the caller interacts exclusively with a generic Command interface. The request itself—including the target receiver, the action to execute, and any parameter values—is packaged inside a dedicated object instance.

Key Structural Components

The Command pattern in Java relies on five primary roles:

  1. Command Interface: Defines the contract for execution, typically exposing a single method such as void execute() or void undo().
  2. Concrete Command: Implements the Command interface. It holds a reference to the receiver and internal state (method arguments) necessary to complete the operation.
  3. Receiver: The business object that contains the actual logic required to fulfill the request.
  4. Invoker: The object that holds the command and triggers its execution (e.g., a UI button, a job scheduler, or a thread pool). The invoker knows nothing about the receiver.
  5. Client: The component responsible for instantiating the receiver, creating the concrete command object, and binding them together before passing the command to the invoker.

Implementation in Java

A minimal implementation demonstrates how these objects interact:

// 1. Command Interface
public interface Command {
    void execute();
}

// 2. Receiver
public class TextEditor {
    public void saveDocument() {
        System.out.println("Document saved to disk.");
    }
}

// 3. Concrete Command
public class SaveCommand implements Command {
    private final TextEditor editor;

    public SaveCommand(TextEditor editor) {
        this.editor = editor;
    }

    @Override
    public void execute() {
        editor.saveDocument();
    }
}

// 4. Invoker
public class ToolbarButton {
    private Command command;

    public void setCommand(Command command) {
        this.command = command;
    }

    public void click() {
        if (command != null) {
            command.execute();
        }
    }
}

In this structure, ToolbarButton does not depend on TextEditor. The button only invokes execute() on whatever Command it holds, making the button completely reusable across different domains.

How State and Context Are Retained

Because commands are objects, they can maintain state within Java's heap memory:

  • Parameter Preservation: Parameters needed for the operation are passed into the command’s constructor and stored in final fields. When execute() is called later, the command already has the context it needs.
  • Undo/Redo Mechanisms: By storing previous state inside the concrete command before changing the receiver, the object can implement an undo() method to restore the receiver's prior state.
  • Queuing and Scheduling: Command objects can be pushed to Java collections, such as BlockingQueue or LinkedList. A separate worker thread can poll these objects and run them asynchronously, decoupling the time of request creation from the time of execution.

Modern Java and Functional Interfaces

In Java 8 and later, the Command pattern integrates cleanly with functional programming. Any command interface with a single abstract method functions as a @FunctionalInterface. Standard interfaces like java.lang.Runnable and java.util.function.Consumer act as built-in command contracts.

Instead of writing verbose concrete command classes for simple tasks, Java systems can use method references and lambdas:

ToolbarButton saveButton = new ToolbarButton();
TextEditor editor = new TextEditor();

// Using a method reference as a command
saveButton.setCommand(editor::saveDocument);
saveButton.click();

Lambda expressions reduce boilerplate while preserving the core benefit of the pattern: converting an operation on a target receiver into a first-class, transferable Java object.
