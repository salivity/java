Java wait, notify, and notifyAll Thread Coordination

Java provides inter-thread communication mechanisms built directly into the java.lang.Object class through the wait(), notify(), and notifyAll() methods. This article explains how these methods interact with Java object monitors, how threads transition between execution states and wait-sets, why these operations require synchronization, and the proper patterns for avoiding common concurrency pitfalls such as deadlocks and spurious wakeups.

The Anatomy of an Object Monitor

Every object in Java is associated with an intrinsic monitor consisting of two critical components:

  1. The Monitor Lock (Mutex): Ensures exclusive execution of synchronized blocks so that only one thread can hold the lock at any given time.
  2. The Wait-Set: An internal queue where threads park themselves while waiting for a specific condition or state change.

Because thread coordination relies directly on manipulating this monitor, a thread must hold the object's monitor lock before calling wait(), notify(), or notifyAll(). Calling any of these methods outside of a synchronized context throws an IllegalMonitorStateException.

How wait() Operates

When a thread invokes wait() on an object:

  • Lock Release: The calling thread atomically releases the monitor lock on that object.
  • State Transition: The thread yields its execution state and is placed into the object's internal wait-set.
  • Dormancy: The thread remains dormant and will not be scheduled for CPU execution until another thread targets it with a notification, the specified timeout expires (if using wait(long timeout)), or it is interrupted.

Once awakened, the thread does not immediately resume execution. It transitions from the wait-set to the monitor's contention queue to re-acquire the lock before continuing from the exact point after the wait() call.

How notify() and notifyAll() Operate

Both notify() and notifyAll() signal threads in the wait-set that a state change may have occurred:

  • notify(): Wakes up a single thread arbitrarily chosen by the Java Virtual Machine from the object's wait-set. The chosen thread moves to the entry set to compete for the lock.
  • notifyAll(): Wakes up all threads currently residing in the object's wait-set, moving all of them to the entry set where they will compete for the monitor lock.

Calling either method does not immediately yield the lock. The notifying thread continues to execute and retains monitor ownership until it explicitly exits the synchronized block or method. Only then can the awakened threads compete to acquire the lock.

The Standard Guarded Block Pattern

Threads can awaken without an explicit notification due to system-level events, an occurrence known as a spurious wakeup. Additionally, in multi-consumer scenarios, another thread may consume the state change before a newly awakened thread acquires the lock.

To prevent execution on an invalid state, wait() must always be wrapped in a while loop that re-checks the predicate condition:

synchronized (lock) {
    while (!condition) {
        lock.wait();
    }
    // Perform actions appropriate to the condition
}

Choosing Between notify() and notifyAll()

While notify() carries lower overhead because it avoids the "thundering herd" problem where multiple threads contend for a single lock, it is only safe when:

  1. All waiting threads are waiting for the exact same condition.
  2. Only one thread can benefit from the condition becoming true.

If threads are waiting on different conditions on the same monitor, or if multiple threads can proceed upon a state change, notify() can lead to missed signals and indefinite deadlocks. In most general concurrency implementations, notifyAll() is the safer and preferred choice.
