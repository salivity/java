Why Finalizers Failed and Were Deprecated in Java

Java finalizers (finalize()) were originally introduced to provide a safety net for cleaning up native resources before an object is reclaimed by the garbage collector. However, severe design flaws—including unpredictable execution timing, lack of execution guarantees, heavy performance overhead, and critical security vulnerabilities—made them inherently unreliable. As a result, finalizers were deprecated in Java 9 and marked for removal in subsequent releases in favor of safer, explicit alternatives.

Unpredictable Scheduling and Latency

The fundamental flaw in Java's finalization mechanism is its lack of promptness. The garbage collector (GC) triggers finalization only when memory pressure demands reclamation, not when a resource runs out. External system resources like file handles, database connections, and sockets are finite and non-memory-related. If an application opens hundreds of files without explicit closing, relying on finalizers will exhaust OS-level handles long before the JVM triggers a garbage collection cycle to reclaim the enclosing Java objects.

No Guarantee of Execution

The Java Virtual Machine provides no guarantee that a finalizer will ever execute. If an application exits normally, crashes, or halts before the GC visits an unreachable object, the finalizer will simply never run. Historic attempts to enforce execution on shutdown, such as System.runFinalizersOnExit, were inherently unsafe due to deadlocks and were quickly deprecated. Writing critical cleanup logic in a finalizer invariably introduces data loss and resource leaks.

Performance Degradation

Objects implementing finalize() require special handling from the garbage collector, severely degrading throughput:

  • Delayed Reclamation: An object with an active finalizer cannot be collected immediately upon becoming unreachable. It is placed into a finalization queue, meaning it survives at least one additional garbage collection cycle and often gets promoted to older generations.
  • Allocation Overhead: Allocating objects with non-trivial finalizers is significantly slower because the JVM must track their life cycles using internal references.
  • Queuing Bottlenecks: Finalization runs on a dedicated system thread. If finalizers perform blocking operations, such as network calls or disk I/O, the queue backs up, driving the JVM toward an OutOfMemoryError.

Swallowed Exceptions and Thread Safety

When an uncaught exception is thrown inside a finalize() method, the JVM abruptly terminates the execution of that specific finalizer and silently ignores the exception. No stack trace is printed by default, and no failure signals propagate to the calling application, leaving the system in a corrupted or partially cleaned-up state that is exceptionally difficult to debug.

Security Vulnerabilities: Finalizer Attacks

Finalizers expose classes to "finalizer attacks." If an attacker passes malicious input to a constructor, causing it to throw an exception, the partially initialized object still exists in memory. Because the constructor failed, the object should be discarded. However, if the class has a finalizer, the garbage collector will still schedule finalize(). Inside finalize(), the malicious object can save a reference to this into a static field, resurrecting the broken instance and bypassing all constructor-based security validations.

Modern Alternatives

To overcome the architectural shortcomings of finalization, Java adopted deterministic and safer resource management patterns:

  • AutoCloseable and try-with-resources: Introduced in Java 7, this is the standard, deterministic way to release resources as soon as execution exits a defined scope.
  • java.lang.ref.Cleaner: Introduced in Java 9 to replace finalization for non-deterministic fallback cleanup. Cleaners decouple the cleanup action from the object instance, preventing object resurrection attacks, avoiding slow finalizer queues, and providing better control over background cleanup threads.
