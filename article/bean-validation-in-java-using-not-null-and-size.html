Bean Validation in Java: Using @NotNull and @Size

Bean Validation provides a standardized, declarative model for enforcing data integrity across modern Java applications. By replacing boilerplate imperative checks with standardized annotations like @NotNull and @Size, developers can define constraint logic directly within domain entities and Data Transfer Objects (DTOs). This article explores the mechanics of Jakarta Bean Validation, the specific roles of core constraint annotations, and how modern frameworks leverage them to streamline application architecture, prevent bugs, and maintain clean separation of concerns.

Declarative Constraint Definition

In traditional Java development, validating incoming data required repetitive, manual conditional statements scattered across controllers, service layers, and data access objects. Modern Java relies on Jakarta Validation (formerly JSR 380/Bean Validation) to shift this paradigm from imperative code to declarative metadata.

By annotating class fields directly, developers establish a single source of truth for constraints. The runtime environment—typically powered by reference implementations like Hibernate Validator—inspects these metadata tags and executes the checks automatically without requiring developers to write custom plumbing logic for basic constraints.

Core Annotations: @NotNull and @Size

While the validation specification includes dozens of annotations, @NotNull and @Size represent fundamental building blocks for controlling data boundaries:

  • @NotNull: Ensures that a target field does not evaluate to null. It is agnostic of content size or structure; an empty string "" or an empty collection [] satisfies @NotNull because the reference itself exists. In modern architectures, it is commonly paired with primitive wrappers, reference objects, and IDs to guarantee the presence of required attributes.
  • @Size: Constrains the size or length of an element within specified min and max boundaries. It supports multiple types, including CharSequence, Collection, Map, and arrays. For example, applying @Size(min = 8, max = 64) on a password field ensures length compliance, while applying it to a List<Item> restricts array payload bounds to prevent resource exhaustion attacks.

Seamless Framework Integration

The primary strength of these annotations in modern Java is how well they integrate into the broader ecosystem, particularly with Spring Boot and Jakarta EE:

  • Fail-Fast REST Endpoints: When applied to request payloads in a REST controller alongside @Valid or @Validated, the framework intercepts incoming HTTP requests before they reach application service methods. If constraints fail, the framework halts execution immediately and generates a standard HTTP 400 Bad Request containing structured validation errors.
  • JPA/Database Alignment: When applied to JPA entities, Bean Validation acts as an extra layer of defense right before database persistence or updates. This ensures that corrupted data cannot be written to the database even if it bypasses presentation-layer checks.
  • Java Record Support: Modern Java records naturally complement validation annotations. Placing annotations like @NotNull directly on record components ensures compact, immutable DTOs that validate instantly upon deserialization.

Maintainability and Error Reporting

Beyond input filtering, modern Bean Validation unifies error handling across applications. Annotations accept custom message attributes, which can be linked to internationalized resource bundles for localization:

public record UserRegistrationRequest(
    @NotNull(message = "{user.name.required}")
    @Size(min = 2, max = 50, message = "{user.name.length}")
    String username
) {}

This decoupling ensures that business rules and their corresponding client-facing messages remain centralized, self-documenting, and effortless to update as application requirements evolve.
