Purpose of Remembered Set in G1 Garbage Collector

The Remembered Set (RSet) is a core data structure in the Java Garbage-First (G1) garbage collector designed to enable independent, regional garbage collection. This article explains the fundamental purpose of the RSet, how it tracks cross-region object references, and why it is essential for minimizing Stop-The-World (STW) pause times in the Java Virtual Machine (JVM).

The Architecture of G1 GC

The G1 garbage collector divides the Java heap into hundreds or thousands of uniform, non-contiguous memory blocks called regions. Each region can be assigned a role dynamically: Eden, Survivor, or Old generation.

Instead of scanning the entire heap during a collection phase, G1 targets specific sets of regions (the Collection Set, or CSet) that contain the most reclaimable memory. To safely collect a region, the collector must identify all live objects within it. This requires knowing whether any object in an uncollected region holds a reference to an object in the region being collected.

The Problem: Cross-Region References

Without a tracking mechanism, determining whether an object inside a target region is still reachable would require scanning every other region in the entire heap. Doing so would negate the primary performance benefit of region-based collection and cause long, unpredictable garbage collection pauses.

The Role of the Remembered Set

The Remembered Set solves this problem by maintaining a "points-into" record for each region. Each region has its own dedicated RSet that tracks all memory locations outside of itself that contain references pointing into it.

When G1 collects a target region:

  1. It reads the region's RSet to identify all incoming external references.
  2. It treats these external references as additional root objects.
  3. It determines object liveness inside the region without scanning any outside regions.

How the Remembered Set Operates

The RSet works in conjunction with a global data structure called the Card Table and a mechanism called Write Barriers:

  • Card Table: The entire heap is divided into 512-byte segments called "cards."
  • Write Barriers: Whenever a thread modifies an object reference to point to another object, the JVM executes a small piece of code called a write barrier. If the source and target objects reside in different regions, the write barrier marks the source card as "dirty."
  • Concurrent Updating: Background threads (concurrent refine threads) process these dirty cards and record the reference locations into the target region's RSet.

Depending on the density of incoming references, an RSet stores data using varying granularities (sparse, fine, or coarse) to balance tracking precision with memory consumption.

Key Benefits and Trade-offs

Benefits

  • Bounded Pause Times: G1 can collect any individual region or group of regions without a full-heap scan.
  • Predictable Latency: Independent collections allow G1 to meet user-defined pause-time targets (-XX:MaxGCPauseMillis).

Trade-offs

  • Memory Overhead: RSets consume memory (often between 1% and 10% of total heap space, depending on the application's object reference graph).
  • Write Barrier Cost: Mutator threads spend slight CPU overhead intercepting reference updates to keep RSet records current.
