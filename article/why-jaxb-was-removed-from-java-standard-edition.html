Why JAXB Was Removed from Java Standard Edition

The Java Architecture for XML Binding (JAXB) API was removed from the core Java Standard Edition (Java SE) platform to decouple enterprise technologies from the base runtime, reduce platform bloat, and support a modular architecture. Initially integrated to simplify XML processing, JAXB's presence in the core JDK became redundant and problematic as the Java ecosystem shifted toward lightweight, modular deployments. This article explains the history behind its inclusion, the technical reasons for its removal in Java 11, and how modern applications manage XML binding today.

The Historical Inclusion of Java EE Modules

JAXB was originally developed as part of Java Enterprise Edition (Java EE). In an effort to make Web Services and XML manipulation easier out of the box, Sun Microsystems bundled several enterprise-centric technologies into Java SE 6. Alongside JAXB, APIs such as JAX-WS (Web Services), JTA (Transactions), and CORBA were included in the standard distribution.

While convenient at the time, bundling these specifications created an overlap between Java SE and Java EE. Developers using newer versions of these libraries often faced classpath conflicts, as the versions embedded within the JRE would clash with updated third-party versions bundled in enterprise application servers.

The Modular Shift: Project Jigsaw and JEP 320

The decision to remove JAXB became formal with Project Jigsaw in Java 9, which introduced the Java Platform Module System (JPMS). One of the primary goals of the module system was to create a smaller, configurable runtime capable of running on resource-constrained devices, microservices, and cloud containers.

Carrying legacy Java EE modules within the core platform contradicted this goal. Consequently, Java 9 placed JAXB and related enterprise libraries into isolated, deprecated modules (specifically java.xml.bind) that were not resolved by default on the classpath.

The complete elimination of the API took place in Java 11 via JEP 320 (Remove the Java EE and CORBA Modules). JEP 320 cited several clear justifications:

  • Independent Evolution: The Java EE technologies evolved at a different pace than Java SE. Maintaining them within the JDK made it difficult to release updates, security fixes, and performance improvements independently.
  • Maintenance Burden: Supporting legacy standards like CORBA and complex frameworks like JAXB imposed a high maintenance cost on the OpenJDK maintainers.
  • Platform Footprint: Removing non-essential enterprise APIs trimmed the size of the base JDK, allowing developers to build tailored runtimes via tools like jlink.

Modern Replacement and Migration

The removal from the core platform did not mean the death of JAXB; it merely shifted JAXB to where it originally belonged: an external third-party library.

Following the transfer of Java EE to the Eclipse Foundation, the API was rebranded under the Jakarta EE umbrella. Modern Java applications that require XML binding continue to use the technology by adding external dependencies to their build configuration (such as Maven or Gradle). Applications targeting modern JDKs now declare dependencies on the Jakarta XML Binding API (jakarta.xml.bind-api) alongside a compatible implementation runtime (such as Eclipse GlassFish or Apache CXF).
