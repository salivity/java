Causes of Java ClassLoader Leaks on Redeployment

In long-running Java application servers, redeploying an application without restarting the JVM frequently triggers OutOfMemoryError: Metaspace (or PermGen in older Java versions). This issue arises because the container cannot garbage collect the application’s ClassLoader due to lingering strong references held by longer-lived system or container threads, static registries, and framework caches. This article examines the mechanics behind class loader memory leaks during redeployment and details the specific code patterns and JVM interactions that cause them.

The Mechanism of ClassLoader Garbage Collection

Java application servers like Apache Tomcat, Jetty, and WildFly utilize a hierarchical class loading architecture. The server creates an isolated child class loader (often named WebAppClassLoader) for each deployed application.

Garbage collection of an application's loaded classes requires the collection of its WebAppClassLoader. However, class unloadability is governed by strict JVM rules:

  • Every Java object holds a reference to its java.lang.Class.
  • Every java.lang.Class holds a reference to its defining java.lang.ClassLoader.
  • Every java.lang.ClassLoader maintains a collection of all java.lang.Class instances it has loaded.

Because of this circular dependency, if even a single object, class, or thread from the application remains reachable by a class loader higher up in the hierarchy (such as the SystemClassLoader or a shared container loader), the entire WebAppClassLoader, along with all application classes and static data, remains rooted in memory.

Primary Causes of ClassLoader Leaks

1. Uncleaned ThreadLocal Variables

The most common cause of class loader leaks involves ThreadLocal storage used in conjunction with container thread pools. Application servers maintain worker threads that live throughout the entire lifecycle of the JVM.

When an application assigns a value to a ThreadLocal and fails to call ThreadLocal.remove() before the thread returns to the pool:

  • The thread continues to hold a reference to the ThreadLocalMap.
  • If the ThreadLocal key, value, or the thread itself references a class loaded by the application, the entire WebAppClassLoader becomes pinned.
  • Even if the key is collected via its weak reference, the value remains strongly reachable until that specific thread runs another task that happens to overwrite or clear the map entry.

2. Lingering Threads and Tasks

If an application starts background threads—using java.lang.Thread, Timer, or an ExecutorService—and does not explicitly terminate them during application shutdown:

  • The running thread remains an active GC root.
  • The thread's context class loader (Thread.getContextClassLoader()) or the thread’s Runnable implementation points directly back to application classes.
  • Common culprits include unstopped scheduling frameworks (like Quartz) or asynchronous background workers created inside third-party libraries.

3. Static JVM Registries and Singletons

When an application registers components into JVM-level singletons or standard library registries, those registrations live in the scope of the bootstrap or system class loader. Without explicit deregistration on shutdown, these registries hold application references indefinitely.

  • JDBC Drivers: Prior to JDBC 4.0, drivers registered via DriverManager.registerDriver() retained strong references in the static java.sql.DriverManager class.
  • Shutdown Hooks: Registering a hook via Runtime.getRuntime().addShutdownHook() keeps the Thread instance in a static list in java.lang.ApplicationShutdownHooks until the JVM exits.
  • JMX MBeans: Registering an MBean with the container or JVM platform MBeanServer retains references to the application class unless unregistered during context shutdown.
  • JavaBeans Introspector: The java.beans.Introspector caches bean metadata globally. Without calling Introspector.flushCaches(), cached metadata retains references to application classes.

4. Logging Frameworks

Logging frameworks often store configuration and appenders in static structures. If a logging implementation (such as Log4j or Logback) is loaded at the server or system level, but uses appenders, filters, or context selectors defined within the application archive, the higher-level logger keeps strong references to the application-level classes.

5. XML and Serialization Caching

The standard Java runtime caches certain factories and parsers for performance. Components like DocumentBuilderFactory, SAXParserFactory, and JAXBContext can retain references to the implementation classes discovered via the thread context class loader. If the runtime caches a provider loaded by the application, the JVM-level cache prevents the class loader from unloading.

Detecting and Preventing Leaks

To prevent class loader leaks, application developers must ensure all resources initialized by the application are explicitly cleaned up using lifecycle hooks, such as ServletContextListener.contextDestroyed() in servlet-based applications:

  • Always invoke remove() on ThreadLocal variables in a finally block.
  • Shut down all managed thread pools and timers.
  • Deregister JDBC drivers and JMX MBeans manually during context destruction.
  • Clear JVM-wide caches for introspectors and XML parsers.

If a leak occurs, it can be diagnosed by capturing a heap dump after redeployment and using memory analysis tools like Eclipse Memory Analyzer (MAT). Tracing the shortest path from the uncollected WebAppClassLoader to any GC root will reveal the exact reference chain keeping the deployment alive in memory.
