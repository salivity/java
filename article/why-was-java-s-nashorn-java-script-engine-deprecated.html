Why Was Java's Nashorn JavaScript Engine Deprecated?

The Nashorn JavaScript engine was introduced in Java 8 as a high-performance successor to Rhino, designed to execute dynamic JavaScript code natively on the Java Virtual Machine (JVM). However, maintaining a rapidly evolving language runtime directly within the core Java Development Kit (JDK) proved unsustainable. Consequently, Nashorn was formally deprecated in Java 11 (JEP 335) and completely removed in Java 15 (JEP 372) primarily due to the rapid evolution of the ECMAScript specification, the prohibitive cost of maintenance, and the emergence of superior polyglot solutions like GraalVM.

The Fast Pace of ECMAScript Evolution

When Nashorn was developed, JavaScript was relatively stable under the ECMAScript 5.1 standard. However, the release of ECMAScript 2015 (ES6) marked a turning point, ushering in yearly release cycles with substantial syntax additions, new language semantics, and expanded standard libraries (e.g., promises, async/await, classes, and modules). Nashorn offered only partial support for ES6 and struggled to keep pace. Continuing to update the engine to comply with annual ECMAScript specifications would have required a massive, continuous development effort that did not align with the broader goals of the OpenJDK project.

High Maintenance Costs

Nashorn was tightly coupled with JVM internals, using the invokedynamic bytecode feature introduced in Java 7 to optimize dynamic code execution. As the Java platform itself modernized with features like Project Jigsaw (the module system introduced in Java 9), maintaining a complex, standalone compiler and runtime inside the JDK became an engineering bottleneck. The OpenJDK team determined that the engineering resources required to maintain and modernize Nashorn far outweighed the benefits of shipping an integrated JavaScript runtime with the JDK.

The Rise of GraalVM and Better Alternatives

During the same period, Oracle Labs developed GraalVM and its polyglot framework, Truffle. GraalVM’s JavaScript implementation (GraalJS) was built from the ground up to support modern ECMAScript standards, offering vastly superior performance, complete compatibility with the modern JS ecosystem, and zero-overhead interoperability with Java. Because GraalVM provided an actively maintained, enterprise-ready environment for running JavaScript on the JVM, keeping a legacy engine like Nashorn in the core JDK became redundant.

Trimming Core JDK Bloat

Modern Java architecture prioritizes a leaner, modular runtime. Bundling non-essential tooling and language engines inside the standard library diverged from this philosophy. Removing Nashorn allowed the JDK maintainers to streamline releases and focus on core JVM language and platform improvements.

For applications that still rely on Nashorn, the engine was decoupled from the JDK and made available as an independent open-source dependency via Maven Central, while projects requiring modern JavaScript compatibility on the JVM are encouraged to migrate to GraalJS.
