Accessing Internal Classes via Java Open Modules

The Java Platform Module System (JPMS) enforces strong encapsulation by default, preventing external code from accessing internal APIs even through reflection. To accommodate frameworks and libraries that rely on runtime inspection, Java introduces the opens directive and the open module declaration. These mechanisms grant runtime-only deep reflective access to internal classes, methods, and fields without exposing those types at compile time.

Strong Encapsulation and the Reflection Barrier

Prior to Java 9, standard reflection using setAccessible(true) could bypass member visibility modifiers, allowing code to inspect and manipulate private elements across any package. With the introduction of JPMS, encapsulation operates at the module boundary.

If a package is not exported or opened:

  • Compile-time access is completely blocked.
  • Standard reflection fails. Attempting to call setAccessible(true) on non-public types or internal members throws an InaccessibleObjectException.

To allow frameworks like Spring, Hibernate, or serialization tools to operate without making internal APIs permanently public at compile time, Java provides explicit reflection-specific declarations in the module-info.java file.

The opens Directive

The opens keyword allows deep reflection on a specific package while keeping it hidden from compile-time dependencies.

module com.example.service {
    // Allows any module to reflectively access com.example.service.internal
    opens com.example.service.internal;
}

When a package is declared with opens:

  1. Compile Time: The package remains completely hidden. Other modules cannot import its classes or compile against them directly.
  2. Runtime: The JVM treats the package as open for reflection. External modules can load classes via reflection, inspect private and package-private elements, and invoke setAccessible(true) without triggering security violations.

Qualified Opens

For finer control, a module can restrict reflective access to specific trusted modules using a qualified opens ... to clause:

module com.example.service {
    // Only the framework module can reflectively inspect this package
    opens com.example.service.internal to org.hibernate.orm.core;
}

With this declaration, any module other than the specified target attempting deep reflection on the package will encounter an InaccessibleObjectException.

Open Modules

When an entire module consists primarily of entities, models, or components intended for dependency injection and object-relational mapping, declaring individual packages can become tedious. Java allows the entire module to be declared as an open module:

open module com.example.application {
    requires java.base;
    requires java.sql;
}

An open module automatically opens all of its packages for deep runtime reflection to all other modules. However, it still maintains compile-time encapsulation; external modules can only compile against packages that are explicitly declared with exports.

How the JVM Handles the Access at Runtime

When reflection targets a class member via Method.invoke(), Field.set(), or AccessibleObject.setAccessible(), the JVM performs a module-level check:

  1. It checks whether the target class's module is open to the caller's module.
  2. It verifies this status programmatically using methods such as Module.isOpen(String packageName, Module other).
  3. If the package containing the target class is opened (either to all modules or specifically to the caller's module), the runtime access check passes.
  4. If the package is only exported rather than opened, reflection can only access public members of public classes; non-public elements remain blocked.
  5. If the package is neither exported nor opened, all reflective attempts fail immediately.
