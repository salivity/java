Compile-Time vs Runtime Constants in Java Bytecode

This article explores the technical and structural differences between compile-time and runtime constants in Java, focusing on how the Java Virtual Machine (JVM) and the javac compiler handle them at the bytecode level. While both concepts involve the final keyword, they diverge drastically in compilation mechanics, constant pool storage, execution performance, and class-dependency coupling.

Defining the Constants

A compile-time constant is a static final field of a primitive type or java.lang.String initialized with a constant expression (such as literals, basic arithmetic, or string concatenation of literals). The compiler can fully compute the value during the compilation phase.

public class Constants {
    public static final int MAX_USERS = 100; // Compile-time constant
    public static final String PREFIX = "ID_"; // Compile-time constant
}

A runtime constant is also marked final, but its value cannot be known until the program actually executes. It is initialized using an expression evaluated at runtime, such as a method invocation, object instantiation, or system property lookup.

public class RuntimeConstants {
    public static final long START_TIME = System.currentTimeMillis(); // Runtime constant
    public static final Integer LIMIT = Integer.valueOf(50); // Runtime constant
}

Bytecode Representation of Compile-Time Constants

When code references a compile-time constant, the Java compiler executes an optimization known as constant inlining (or macro expansion). The compiler completely removes the symbolic reference to the original field and embeds the literal value directly into the consumer class's bytecode.

For primitives, the compiler uses operand-pushing instructions:

  • Small integers use iconst_<i>, bipush, or sipush.
  • Floating-point numbers, larger integers, and String literals are pushed onto the operand stack using the ldc (load constant) instruction, loading directly from the consuming class's own runtime constant pool (#cp_info).

Example Bytecode: If a class calls int x = Constants.MAX_USERS;, the generated bytecode in the calling class does not access Constants. Instead, it emits:

bipush 100
istore_1

Because the value 100 is hardcoded into the consumer's .class file, the calling class does not even trigger class loading or initialization of Constants at runtime.

Bytecode Representation of Runtime Constants

Runtime constants cannot be inlined because their values do not exist when the .class file is generated. The initialization occurs during the execution of the class initializer method (<clinit>) or the instance constructor (<init>).

When another class references a runtime constant, the compiler retains a symbolic reference to the field in the constant pool. At runtime, the JVM uses the getstatic (or getfield for instance constants) instruction to resolve and fetch the value from memory.

Example Bytecode: If a class calls long t = RuntimeConstants.START_TIME;, the generated bytecode emits:

getstatic #2 // Field RuntimeConstants.START_TIME:J
lstore_1

The JVM must resolve the Fieldref entry #2, load and initialize RuntimeConstants if not already loaded, and read the memory location of the static field.

Key Differences Summary

Feature Compile-Time Constants Runtime Constants
Bytecode Instructions iconst, bipush, sipush, ldc getstatic, getfield, invokestatic (in <clinit>)
Inlining Yes, inlined directly into consumer bytecode No, resolved dynamically via field references
Class Initialization Does not trigger declaring class initialization Triggers declaring class initialization on first access
Binary Compatibility Poor; modifying the value requires recompiling all consumer classes Strong; changing the value requires recompiling only the declaring class
Constant Value Attribute Present in the field's ConstantValue attribute in .class metadata Absent; assigned dynamically during execution
