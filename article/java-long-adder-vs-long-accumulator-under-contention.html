Java LongAdder vs LongAccumulator Under Contention

In multi-threaded Java applications, handling concurrent numeric updates efficiently is essential for application throughput. While traditional classes like AtomicLong rely on Compare-And-Swap (CAS) loops, they degrade severely under heavy thread contention due to CPU cache bouncing and repeated retries. Java 8 introduced LongAdder and LongAccumulator to solve this bottleneck by striping updates across multiple internal variables. This article explains why these classes were introduced, how they achieve superior throughput under high contention, and when to use each implementation.

The Problem with AtomicLong Under High Contention

AtomicLong works by maintaining a single volatile long value. When multiple threads attempt to update this value simultaneously, they use atomic CAS operations (compareAndSet). Under low contention, this mechanism is extremely fast and lock-free.

However, when dozens or hundreds of threads attempt to update the same memory location concurrently:

  • Only one thread succeeds per CAS attempt.
  • The remaining threads fail and must retry within a tight loop.
  • This creates severe CPU spinning and constant invalidation of CPU core caches (cache-line bouncing), causing throughput to plummet precisely when system load is highest.

How LongAdder Eliminates the Contention Bottleneck

LongAdder eliminates contention on a single memory cell by distributing updates across a dynamically sized array of individual storage cells (an internal class called Cell).

When thread contention is detected:

  1. Dynamic Striping: Instead of forcing all threads to modify a single variable, LongAdder hashes each thread to a specific slot in an internal Cell[] table.
  2. Independent Writes: Threads update their assigned Cell independently using CAS, virtually eliminating contention because threads rarely compete for the exact same memory location.
  3. Lazy Aggregation: The global total is not maintained eagerly. When the current value is required via sum(), LongAdder iterates across the base value and all active cells to calculate the current sum.

By trading higher memory usage and eventual consistency for write scalability, LongAdder maintains near-linear throughput scaling even under extreme thread contention.

The Purpose of LongAccumulator

While LongAdder is specialized strictly for additive and subtractive operations, LongAccumulator serves as its generalized counterpart.

LongAccumulator uses the exact same striped-cell architecture under the hood, but it allows developers to supply an arbitrary LongBinaryOperator along with an initial identity value:

LongAccumulator maxTracker = new LongAccumulator(Long::max, Long.MIN_VALUE);
maxTracker.accumulate(observedValue);

For the mathematical results to remain deterministic across threads, the supplied function must be:

  • Associative: f(a, f(b, c)) == f(f(a, b), c)
  • Commutative: f(a, b) == f(b, a)

Because the order of updates across cells and threads is non-deterministic, operations like running maximums, minimums, and products work reliably, while order-dependent operations will not.

Choosing the Right Tool

  • Use AtomicLong when updates are infrequent, read operations require strict sequential consistency (such as generating unique sequence IDs), or when conditional CAS operations (like compare-and-set loops) are required.
  • Use LongAdder for high-throughput write-heavy scenarios where exact, instantaneous snapshots are not required on every cycle, such as collecting metrics, counting processed requests, or tracking throughput.
  • Use LongAccumulator when you face high-contention updates that require non-additive math, such as maintaining running maximums, minimums, or accumulative factors across many concurrent threads.
