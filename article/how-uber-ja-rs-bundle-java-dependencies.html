How Uber-JARs Bundle Java Dependencies

An Uber-JAR, also known as a fat JAR, is a single Java Archive file that packages an application's compiled bytecode alongside all of its external libraries and runtime dependencies. This article explains the architectural mechanics behind Uber-JAR packaging, detailing how build tools extract and merge binary assets, resolve resource collisions, configure manifest files for standalone execution, and implement alternative class-loading strategies.

The Mechanics of JAR Flattening

In standard Java development, a typical compilation produces a JAR containing only the application's compiled classes, requiring external dependencies to be placed on the system classpath at runtime via the -cp or -classpath flag. An Uber-JAR circumvents this classpath configuration by "flattening" dependencies.

During the build phase, packaging plugins (such as the Maven Shade Plugin or Gradle Shadow Plugin) perform the following steps:

  1. Extraction: The tool unzips every upstream dependency (.jar file) identified in the project's dependency tree, extracting all compiled .class files and resource files into a temporary staging area.
  2. Aggregation: The application's own compiled classes are merged into the same directory structure.
  3. Repackaging: The build tool zips all collected classes and resources into a single archive, maintaining the standard package structure (e.g., com/example/app/Main.class sits directly alongside third-party classes like org/apache/commons/lang3/StringUtils.class).

Configuring the Manifest for Execution

For an Uber-JAR to be directly executable with the command java -jar application.jar, the archive must specify an entry point.

Build tools achieve this by generating or modifying the META-INF/MANIFEST.MF file within the archive. The packager inserts the Main-Class attribute pointing to the fully qualified class name containing the application's public static void main(String[] args) method. Because all required dependencies reside in the root directory structure of the same archive, the JVM's default system class loader can resolve every reference without referencing external directories or environment variables.

Resolving File Collisions and Relocation

Merging multiple JARs into a flat hierarchy inevitably introduces conflicts when files share the same relative path. Build plugins use two primary mechanisms to manage these collisions:

  • Resource Transformers: Certain framework configuration files—such as Service Provider Interface files in META-INF/services/ or Spring schema declarations—share identical paths across multiple libraries. Instead of overwriting them, the build tool uses append strategies to concatenate the contents into single files so all providers remain discoverable.
  • Class Shading (Relocation): When duplicate or incompatible versions of a class exist across different dependencies, packagers can "shade" them. Shading renames the package declarations of conflicting dependencies (e.g., rewriting org.objectweb.asm to hidden.org.objectweb.asm) and updates all corresponding bytecode references, eliminating namespace collisions and avoiding runtime LinkageError or NoSuchMethodError exceptions.

Alternative Approach: Nested JARs

While traditional Uber-JARs flatten all dependencies into a single namespace, alternative architectures preserve dependency integrity. For instance, Spring Boot utilizes an executable archive that keeps dependency JARs intact inside a BOOT-INF/lib/ directory.

Standard Java runtime specifications do not permit loading classes directly from nested JAR archives inside a standard JAR. To overcome this limitation, Spring Boot injects a custom class loader (LaunchedURLClassLoader) and sets the manifest's Main-Class to an internal launcher (such as org.springframework.boot.loader.JarLauncher). When executed, the launcher initializes the custom class loader, which can inspect and read classes directly from the nested JARs, avoiding flattening conflicts entirely while maintaining the convenience of a single deployable file.
