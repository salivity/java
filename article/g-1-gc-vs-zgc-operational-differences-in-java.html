G1 GC vs ZGC: Operational Differences in Java

Java application performance heavily depends on garbage collection behavior, particularly when choosing between the Garbage-First (G1) collector and the Z Garbage Collector (ZGC). This article breaks down the operational differences between G1 and ZGC, focusing on pause times, concurrency mechanisms, memory footprint, heap scaling, and generational design to help engineers choose the appropriate collector for their runtime workloads.

Latency and Pause Times

The primary operational difference between G1 and ZGC is how they manage Stop-The-World (STW) pauses:

  • G1 GC: Designed as a balance between throughput and latency, G1 allows users to set a target pause duration using -XX:MaxGCPauseMillis (defaulting to 200 ms). While it attempts to meet this soft goal, G1 still requires STW pauses for critical phases, including root scanning, remarking, and live-object evacuation. Pauses typically range from tens to hundreds of milliseconds and can scale with heap size and object mutation rates.
  • ZGC: Engineered specifically for ultra-low latency, ZGC restricts pause times to under one millisecond, regardless of whether the heap is 16 megabytes or 16 terabytes. Its pause times do not scale with heap size or the volume of live objects.

Concurrency and Evacuation

Memory compaction prevents fragmentation, but how memory is relocated differentiates these collectors:

  • G1 GC: Performs object evacuation inside an STW pause. While it marks objects concurrently with running application threads, it stops execution when moving surviving objects from one region to another to avoid race conditions.
  • ZGC: Performs virtually all work concurrently, including object relocation and pointer remapping. It achieves this using colored pointers (storing metadata bits inside the object reference itself) and load barriers (JIT-injected code that intercepts reference dereferences). When an application thread touches an object that has been moved or is slated for relocation, the load barrier dynamically updates the reference without stopping other threads.

Generational Handling

Handling short-lived versus long-lived objects dictates how efficiently a collector handles memory churn:

  • G1 GC: Inherently generational. G1 divides the heap into equal-sized virtual regions assigned dynamically as Eden, Survivor, or Tenured. It continuously collects Eden regions to exploit the weak generational hypothesis (most objects die young), maintaining high throughput for allocation-heavy applications.
  • ZGC: Originally introduced as a single-generation collector, which meant it had to scan the entire heap equally and could struggle with high allocation rates. Starting in Java 21, Generational ZGC (-XX:+ZGenerational) was introduced, splitting the heap into young and old generations while keeping pauses sub-millisecond, bridging the throughput gap with G1.

CPU Overhead and Resource Consumption

Operating these collectors incurs different hardware trade-offs:

  • G1 GC: Requires less CPU overhead because it uses standard write barriers and pauses threads during compaction. It has a lower CPU footprint for the garbage collection threads themselves, making more compute cycles available for application throughput.
  • ZGC: Uses more compute cycles due to continuous background concurrent threads and the runtime overhead of load barriers on memory reads. While pause times remain negligible, total throughput may decrease by 5% to 15% compared to G1 depending on the workload and hardware profile.

Operational Guidance

  • Choose G1 GC when maximum throughput is prioritized over absolute low latency, when CPU resources are constrained, or when latency spikes of 50 to 200 milliseconds are within acceptable service level agreements (SLAs).
  • Choose ZGC when predictable, sub-millisecond response times are mandatory, when dealing with multi-gigabyte or terabyte-scale heaps, or when tail latencies (p99/p999) directly affect user experience or financial transactions.
