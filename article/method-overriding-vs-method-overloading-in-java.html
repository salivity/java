Method Overriding vs Method Overloading in Java

In Java, polymorphism is primarily achieved through two distinct mechanisms: method overloading and method overriding. While both techniques allow methods to share the same name, they serve entirely different architectural purposes and are resolved at different stages of program execution. This article examines how Java handles method overloading at compile time through static binding compared to how it executes method overriding at runtime using dynamic method dispatch.

Understanding Method Overloading

Method overloading occurs when a class contains multiple methods with the identical name but different parameter lists. Differences can include the number of parameters, their data types, or the sequence of data types. Method overloading represents compile-time (static) polymorphism.

Java achieves method overloading entirely during the compilation phase:

  1. Signature Resolution: The Java compiler evaluates the method name along with the arguments provided at the call site. The method's return type is not considered part of its signature for overloading purposes.
  2. Static Binding: Once the compiler determines the best match based on argument types and implicit type promotions, it binds the method call directly to that specific implementation.
  3. Bytecode Generation: The compiled bytecode points specifically to the exact method signature chosen. At runtime, the Java Virtual Machine (JVM) executes the pre-determined method without needing to evaluate which version to call.
class Calculator {
    // Overloaded methods
    int add(int a, int b) {
        return a + b;
    }

    double add(double a, double b) {
        return a + b;
    }
}

Understanding Method Overriding

Method overriding occurs when a subclass defines a specific implementation of a method that is already defined in its superclass. The overriding method must retain the exact same name, argument list, and a compatible (covariant) return type, without having more restrictive access modifiers. Method overriding represents runtime (dynamic) polymorphism.

Java achieves method overriding during program execution through a process called Dynamic Method Dispatch:

  1. Virtual Method Table (vtable): For every class loaded into memory, the JVM maintains an internal lookup table known as a virtual method table. The vtable maps method declarations to their actual code addresses in memory.
  2. Inheritance Mapping: When a subclass overrides a method, its vtable entry for that method points to the subclass's implementation rather than the parent's implementation.
  3. The invokevirtual Bytecode Instruction: At compile time, Java emits the invokevirtual instruction for standard instance method invocations.
  4. Dynamic Lookup: At runtime, the JVM does not look at the type of the reference variable; instead, it checks the actual object instance stored on the heap. It uses the object’s vtable to locate and execute the overridden version of the method.
class Animal {
    void makeSound() {
        System.out.println("Animal sound");
    }
}

class Dog extends Animal {
    @Override
    void makeSound() {
        System.out.println("Bark");
    }
}

If an Animal reference points to a Dog object (Animal myDog = new Dog();), calling myDog.makeSound() resolves to Dog's implementation at runtime because the JVM inspects the underlying heap object's vtable.

Key Technical Comparisons

  • Execution Stage: Overloading is resolved at compile time via static binding, whereas overriding is resolved at runtime via dynamic dispatch.
  • Inheritance Requirement: Overloading can occur within a single class or across inherited classes, while overriding strictly requires an inheritance hierarchy between a parent and child class.
  • Method Signatures: Overloaded methods must have differing parameter lists; overridden methods must have identical parameter lists.
  • Performance: Overloaded calls execute slightly faster because the target method address is established before runtime. Overridden calls incur a negligible lookup overhead due to dereferencing the vtable during dynamic dispatch.
