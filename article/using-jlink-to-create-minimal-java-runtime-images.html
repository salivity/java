Using jlink to Create Minimal Java Runtime Images

The jlink tool, introduced in Java 9 alongside the Java Platform Module System (JPMS), is a command-line utility designed to assemble a set of modules and their dependencies into a custom, self-contained runtime image. By stripping away unused core Java classes and platform libraries, jlink allows developers to package an application alongside only the exact runtime components it needs to execute. This article explores the primary purposes of jlink, its key advantages for modern deployment environments, and how it transforms Java application packaging.

The Problem with Traditional Java Runtimes

Historically, running a Java application required deploying a full Java Runtime Environment (JRE). The monolithic JRE included every standard library—ranging from desktop GUI toolkits like AWT and Swing to enterprise technologies like CORBA and XML binding—regardless of whether the application actually utilized them. This resulted in large distribution sizes (often exceeding 200 MB), increased memory overhead, and an expanded attack surface containing unused code that still required security patching.

Core Purposes of jlink

The fundamental purpose of jlink is to create fully functional, optimized Java runtimes tailored specifically to the workload they support. Its primary roles include:

  • Drastic Footprint Reduction: A standard JDK or headless JRE can take up several hundred megabytes of disk space. With jlink, a simple microservice or command-line utility can run on a custom image as small as 30 to 50 MB, drastically reducing storage requirements.
  • Elimination of Target Dependencies: A custom runtime created by jlink includes the Java Virtual Machine (JVM) binary, the required platform modules, and the application itself. Target machines do not need Java pre-installed, eliminating version conflicts and simplifying installation scripts.
  • Attack Surface Minimization: Security vulnerabilities often reside in obsolete or unused platform libraries. By linking only explicitly declared modules, unused code is completely omitted from the final distribution, neutralizing potential attack vectors.
  • Container and Microservice Optimization: In cloud environments, smaller artifacts yield faster container image builds, quicker push/pull times across networks, and lower cold-start latency when scaling instances horizontally.

How jlink Operates

The jlink tool relies on the metadata defined in modular Java applications (module-info.java). When executed, the tool performs dependency analysis:

  1. Resolution: It reads the application's root module and traces all declared requires directives through the module graph.
  2. Pruning: It selects only the Java base runtime (java.base) and the specific standard modules required (such as java.sql or java.net.http), leaving out everything else.
  3. Optimization: It applies link-time optimizations, such as stripping debug information, compressing module resources, and generating custom class loaders.
  4. Assembly: It packages the pruned JVM, native launchers, and configuration files into an output directory that acts as a standalone runtime.

A standard invocation looks like this:

jlink \
  --module-path $JAVA_HOME/jmods:mlib \
  --add-modules com.example.app \
  --output custom-runtime \
  --strip-debug \
  --compress=2 \
  --no-header-files \
  --no-man-pages

In this command, jlink extracts the necessary modules from the JDK's packaged modules (jmods) and the application's module directory (mlib), applies compression and metadata stripping, and outputs a minimal runtime folder capable of executing the application natively.

Summary

The purpose of jlink is to modernize Java deployments by replacing bloated, general-purpose runtimes with lean, purpose-built execution environments. By linking only the dependencies an application needs, developers achieve smaller footprints, enhanced security, and optimal performance for containerized and cloud-native architectures.
