Java Card Table and Cross-Generational References

The card table is a specialized memory-management data structure used by Java’s generational garbage collectors to efficiently track references originating from older-generation objects to younger-generation objects. By maintaining an array of bytes where each entry corresponds to a fixed-size block of heap memory, the Java Virtual Machine (JVM) avoids scanning the entire Old Generation during minor garbage collection cycles. This mechanism minimizes Garbage Collection (GC) pause times while preserving the benefits of generational collection.

The Cross-Generational Reference Problem

The weak generational hypothesis posits that most Java objects die shortly after creation. To exploit this, the JVM divides the heap into generations: the Young Generation (Eden and Survivor spaces) and the Old (Tenured) Generation.

Minor GC cycles collect only the Young Generation, which keeps pause times short. However, an object residing in the Old Generation can hold a reference to an object in the Young Generation. If a Minor GC only traced roots starting from thread stacks, static variables, and the Young Generation itself, it would miss these Old-to-Young references and prematurely collect live young objects.

Scanning the entire Old Generation during every Minor GC to locate these references would eliminate the performance advantages of generational garbage collection. The card table solves this problem by identifying precisely which segments of the Old Generation contain cross-generational references.

Architecture of the Card Table

The card table is implemented as a byte array (byte[]), where each element is called a "card."

  • Memory Mapping: Each card covers a fixed-size contiguous block of the heap, traditionally 512 bytes (known as a card size).

  • Card States: A card holds a simple value representing its state. Common states include "clean" (no modified pointers) and "dirty" (one or more pointers in that 512-byte region were updated and might reference the Young Generation).

  • Index Calculation: Translating an object's memory address to its corresponding card index is accomplished using a fast bit-shift operation:

    \[\text{Card Index} = \text{Object Address} \gg 9\]

    Because 512 is \(2^9\), shifting an address right by 9 bits maps that address directly to its offset in the card table.

Tracking Changes via Write Barriers

The JVM uses a post-write barrier to update the card table whenever a reference field in an object is modified.

  1. Interception: When the application executes an assignment statement such as oldObject.field = youngObject, the Just-In-Time (JIT) compiler emits a small sequence of machine instructions directly after the store operation.
  2. Marking the Card: This write barrier computes the card table index corresponding to the memory address of oldObject and sets the card's value to a "dirty" state (typically represented by a specific byte value, such as zero).
  3. Overhead Reduction: The write barrier does not check whether the stored value is actually a Young Generation reference at the time of execution. Performing such a check in user code would introduce branch penalties and latency. Instead, it unconditionally marks the card as dirty, deferring the precise reference analysis to the garbage collector.

Card Table Processing During Minor GC

When a Minor GC is triggered, the collector uses the card table as an additional source of GC roots:

  1. Scanning the Table: The garbage collector scans the byte array of the card table instead of the multi-gigabyte Old Generation heap. Because the card table represents only a small fraction of the heap size (1 byte for every 512 bytes, or approximately 0.2% of the heap), this scan is rapid.
  2. Inspecting Dirty Cards: When the collector encounters a dirty card, it inspects only the 512-byte memory slice associated with that card. It traverses the objects within that block to find the exact references pointing into the Young Generation and treats those referenced young objects as live roots.
  3. Resetting Cards: Once the dirty region is processed and the surviving young objects are copied, the GC clears the card, marking it "clean" again until another write barrier updates it.

Through this combination of coarse-grained tracking via 512-byte pages, lightweight write barriers, and selective scanning, the card table allows Java's generational collectors to maintain reference integrity without sacrificing throughput or latency.
