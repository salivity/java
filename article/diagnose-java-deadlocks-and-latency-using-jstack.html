Diagnose Java Deadlocks and Latency Using jstack

The jstack command-line utility is an essential diagnostic tool included in the Java Development Kit (JDK) used to capture and inspect thread dumps from a running Java Virtual Machine (JVM). By providing an instantaneous snapshot of all active execution threads, their call stacks, and their synchronization states, jstack enables engineers to rapidly identify the root causes of application deadlocks, thread contention, and CPU- or I/O-related system latency without needing to restart the application.

Generating a Thread Dump

To analyze a running JVM, determine its Process ID (PID) using tools like jps or ps -ef, then run:

jstack <PID> > threaddump.txt

To include JVM-level internal locks and synchronization details, use the extended lock option:

jstack -l <PID> > threaddump.txt

Diagnosing Thread Deadlocks

A deadlock occurs when two or more threads are permanently blocked, each holding a lock that the other needs to proceed.

jstack automatically analyzes synchronization monitors and highlights deadlocks. When a deadlock is detected, the utility appends a dedicated analysis section at the bottom of the output, labeled Found one Java-level deadlock:.

Reading the Deadlock Section

The deadlock report shows the exact cycle of dependencies:

  • Thread Identity and State: Identifies which threads are locked (e.g., Thread-1 and Thread-2) and marks their status as BLOCKED.
  • Lock Ownership: Shows the specific monitor object each thread is waiting to acquire via waiting to lock <0x...> and identifies which thread currently owns that lock via which is held by "Thread-Name".
  • Stack Trace Context: Pinpoints the exact class and line number in your source code where the blocking synchronization block or lock acquisition call is located.

Resolving the issue involves reviewing the identified code paths to enforce a consistent acquisition order across all shared resources.

Diagnosing System Latency and Bottlenecks

System latency usually manifests either as thread contention, thread starvation, or CPU saturation. A single thread dump provides a snapshot, but taking three to five dumps at intervals of 5 to 10 seconds is critical to determine whether threads are making progress or remaining static.

1. High Lock Contention (BLOCKED State)

When multiple threads execute concurrently and contend for the same synchronized block or monitor, latency spikes.

  • Symptom: Many threads display the BLOCKED (on object monitor) state waiting for the same object reference address.
  • Analysis: Search the dump for the memory address associated with waiting to lock <0x...>. Locate the single thread that shows locked <0x...>. That holding thread indicates the bottleneck—often caused by a slow database query, external network call, or inefficient algorithm executed inside a synchronized block.

2. High CPU Utilization (RUNNABLE State)

When high system latency correlates with 100% CPU usage, jstack helps pinpoint the exact method consuming compute resources.

  • Run top -H -p <PID> on Linux to list individual threads consuming CPU time.
  • Identify the thread with the highest %CPU and convert its decimal Thread ID (TID) to hexadecimal.
  • Search your jstack output for the matching native thread identifier (nid=0x<hex_id>).
  • The corresponding stack trace will reveal the exact execution path running an inefficient loop, heavy computation, or non-terminating code.

3. I/O and External Service Delays (WAITING or TIMED_WAITING)

Latency can occur when an application waits indefinitely for downstream resources such as databases, microservices, or file systems.

  • Threads stuck in SocketInputStream.socketRead0() or database driver connection pools indicate network latency or slow external dependencies.
  • Threads in TIMED_WAITING (parking) or WAITING (on object monitor) that do not change state across successive thread dumps indicate unfulfilled wait conditions, exhausted thread pools, or missing timeouts.
